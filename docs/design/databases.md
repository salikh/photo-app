# The sqlite databases: location, schema, meaning

Code: `photoapp/db.py` (the app's own database: schema, migrations, connection helpers),
`photoapp/config.py` (`--state_dir`, `--hashes_db` flags), `photoapp/fileinfo.py` (reads
`--hashes_db`), `photoapp/import_ratings.py` (reads an external `--metadata_db`).

This app touches three sqlite databases, only one of which it owns:

| Database | Location | Read/write | Lifetime |
|---|---|---|---|
| [The app's state database](#the-apps-state-database) | `<state_dir>/app.sqlite` | read/write | permanent |
| [`--hashes_db`](#--hashes_db-a-precomputed-hash-cache) | wherever `hash_dir.py` wrote it | read-only | permanent, optional |
| [`--metadata_db`](#--metadata_db-a-one-off-import-source) | wherever the user points it | read-only | one-off, not part of normal operation |

## The app's state database

`<state_dir>/app.sqlite` (`db.DB_NAME`), opened via `db.open_state`/`db.connect`. `--state_dir`
defaults to `~/.local/share/photos` and also holds XMP backups and `manual_links.jsonl` (see
`docs/operations.md`). It is deliberately **not** inside `--pictures_dir`: the library is treated
as read-only (except XMP sidecars written in place), so anything the app needs to remember about
its own state lives in a completely separate location that can be deleted and rebuilt without
touching a single photo.

### It is a rebuildable cache — except for two tables

Everything in this database is derived from what's on disk (a file's metadata, a Photo's grouping,
a rating resolved from sidecars) and can be regenerated by rescanning — **except** the two tables
in `db.NOT_REBUILDABLE`: `manual_links` and `activity_log`. A manual link/unlink decision
(`manual_links`) and the undo history (`activity_log`) are user decisions that cannot be derived
from anything on disk; losing them is a real loss, not an inconvenience. `manual_links` is also
mirrored to `<state_dir>/manual_links.jsonl` specifically so it survives a lost database (see
[photo-model.md](photo-model.md)'s "Manual links" section) — `activity_log` has no such mirror,
so it is the one table where losing the database is unrecoverable. Back both up; everything else
is convenience.

### Schema, table by table

Columns that are self-explanatory from their name are not re-explained; only what needs context is
called out. Each row links to the design doc that covers that table's *why* in depth, when there
is one.

**`files`** — one row per physical file (a RAW, a camera JPEG, a TIFF export, ...). `path` is
relative to `pictures_dir` with `/` separators and is the primary key applications match against;
`hash` is a content hash used for rename/move recovery; `photo_id` links it to the Photo it belongs
to; `role` (`original`/`camera`/`tuning`/`export`) and `derived_from` describe its place within
that Photo's group; `missing` marks a file the scanner no longer finds on disk without deleting its
row (so its rating/history survives a temporarily-unmounted NAS or a later-restored file). See
[photo-model.md](photo-model.md).

**`photos`** — one row per logical picture, the unit ratings/fav/tags actually apply to.
`original_file_id`/`representative_file_id` point into `files`; `rating`/`fav`/`previous_stars` are
the combined rating (`-1` reject, `0` unrated, `1..5` picked — see
[ratings-and-xmp.md](ratings-and-xmp.md)); `rating_source` + `rating_updated_at` record whether the
database or a sidecar most recently set the current value, for the newest-wins rule;
`representative_source` (`auto`/`manual`) records whether a user overrode which file represents
this Photo; `conflict` is set when sidecars disagree with each other or with the database. See
[photo-model.md](photo-model.md) and [ratings-and-xmp.md](ratings-and-xmp.md).

**`tags`** — `(photo_id, tag)` pairs; a plain many-to-many join table, no separate tag table since
tags here are free text, not a managed vocabulary.

**`xmp_sidecars`** — one row per `.xmp` file found on disk, independent of whether it currently
matches a file (`file_id` can be `NULL` — an orphan sidecar). `mtime`/`hash` detect whether a
sidecar changed since it was last read; `rating`/`has_fav`/`tags` mirror what's parsed from it;
`backup_path` points at the pre-edit copy `docs/operations.md` describes. See
[ratings-and-xmp.md](ratings-and-xmp.md).

**`manual_links`** — an append-only log of link/unlink decisions the automatic grouping rule
cannot make on its own (**not rebuildable**, see above). `action` is `link` or `unlink`; a
decision is matched to a file primarily by `path`, with `hash` as a fallback for renamed files.
See [photo-model.md](photo-model.md)'s "Manual links" section.

**`rating_by_hash`** — `hash → (rating, fav, last_path)`, used to recover a rating by content when
a file's path changes (a rename, a re-export) rather than losing it. `rated_at` orders it against
`photos.rating_updated_at` for the newest-wins rule.

**`activity_log`** — the undo history (**not rebuildable**, see above). One row per field change
(`field` is `rating`/`fav`/`tags`), `old`/`new` values, `cause`, and `undone` marking whether it
was since reversed; `batch_id` groups rows from one batch action (e.g. batch-rating a selection) so
they undo together.

**`thumbs`** — `(file_id, size)` → where its thumbnail lives and how it was made. `source`
records which of the several render paths produced it (`existing`, `pillow`, `dcraw-embedded`,
`dcraw-half`, `dcraw-full`, `libraw`, ...) — informational, nothing currently branches on it. See
[thumbnails.md](thumbnails.md).

**`jobs`** — the shared background-job table, `id`/`kind`/`state`
(`queued`/`running`/`done`/`failed`)/`error`/`created_at`/`finished_at`. Most jobs are scoped to a
file (`file_id`); `target` (added for ticket 076) instead holds a relative directory path for a
directory-scoped job (`scan_dir`), leaving `file_id` `NULL`. Several independent `JobQueue`
instances share this one table — see [concurrency-and-jobs.md](concurrency-and-jobs.md) for why
that's safe and what the `kind`-scoping bug looked like before it was fixed. Rows do not
accumulate forever: `jobs.prune` (ticket 075, riding along with the nightly `scan_dir` batch as
its own `prune_jobs` job) deletes `done` rows older than a week and `failed` rows older than a
year, and a job that succeeds immediately deletes its own earlier failed attempts.

**`dir_mtimes`** — `dirpath → mtime`, one row per directory the scanner has processed; a directory
whose mtime hasn't changed is skipped entirely on the next scan. See
[scanning.md](scanning.md).

**`meta`** — a generic `key → value` table for small pieces of app-wide state that don't deserve
their own table, currently just the grouping rule's version number (`grouping_version`, see
[photo-model.md](photo-model.md)'s "Grouping-rule migrations" section).

### Migrations

`db.MIGRATIONS` is an ordered list of SQL scripts; `db.migrate(conn)` reads the database's current
`PRAGMA user_version` and runs every script after that index, in order, committing and bumping
`user_version` after each one. It's called on every `connect`/`open_state`, so an existing database
picks up new tables/columns automatically the next time *any* part of the app (the server, a CLI
tool, a test) opens it — there is no separate "run migrations" step to remember. A migration can be
a schema change (`CREATE TABLE`, `ALTER TABLE ... ADD COLUMN`) or a data fixup that needs to run
once (e.g. one migration forces every RAW file to be re-read after a rendering-size bug fix, by
setting `bytesize = -1` so the next scan treats it as changed). `migrate` refuses to open a database
whose `user_version` is *newer* than this build knows about, rather than silently misinterpreting
an unfamiliar schema.

## `--hashes_db`: a precomputed hash cache

An optional, external, read-only sqlite database in the format `hash_dir.py` writes, given via
`--hashes_db`. `fileinfo.load_precomputed_hashes` reads it once at startup; a scan reuses a file's
precomputed hash instead of re-hashing it when the file's mtime still matches, which matters
because hashing over the NAS is the slow part of a scan (see [scanning.md](scanning.md)). The app
never writes to this database.

## `--metadata_db`: a one-off import source

An external, read-only, Lightroom/darktable-format sqlite database, read only by
`photoapp/import_ratings.py` — a standalone command for a one-time import of ratings from another
tool's catalog into this app's `rating_by_hash`/sidecars. It plays no part in normal operation;
nothing else in the app opens it.
