# 124: Bug: rejected-deletion confirmation screen ignores subdirectories

- Type: bug
- Status: done (2026-09-26)
- Related: [120](120.md) (earlier fix that carried `recursive` into the delete-review URL),
  [072](072.md) (Delete button on the Rejected view), [088](088.md) (batch delete from a selection)
- Refs: `photoapp/static/app.js` (`renderHeader`'s Delete link, `rescan`), `photoapp/static/pages.js`
  (`deleteReviewPage`), `photoapp/static/grid.js` (`deleteSelected`), `photoapp/static/route.js`
  (`hrefPage`/`parse`), `photoapp/api.py` (`/api/photos`), `photoapp/library.py` (`list_photos`)

## What's reported

In the Rejected grid with **"This folder + subfolders"** enabled, opening the deletion confirmation
screen shows no (or too few) of the rejected photos that live in the subdirectories: the screen
does not honour the subfolders mode.

## Findings so far

The header Delete link already builds `#!delete-review?dir=<dir>&recursive=1` (ticket 120) and
`deleteReviewPage` fetches `/api/photos?...&filter=rejected&recursive=1`. Reproduced both the
header-link flow (toggling "This folder" -> "+ subfolders" in the UI) and the grid-selection flow
against the e2e harness, and both showed the subfolder's rejected photo correctly. So either the
report is a stale running instance, or it is a path not yet covered (e.g. root `.` with
`recursive=1`, the selection hand-off, hidden/dot subdirectories, or a >1000-photo truncated fetch).

## Root cause

The exact remaining path is the **truncated fetch**. The header flow fetched
`/api/photos?...&filter=rejected&limit=1000` and never paged, while `library.list_photos` clamps
`limit` to 1000. In a whole-library "This folder + subfolders" scope with more than 1000 rejected
Photos, only the first 1000 (by sort order) ever reached the confirmation screen; the rest -- often
the ones living in deeper subfolders -- silently vanished, which reads as "the screen ignores
subdirectories". Root `.` with `recursive=1`, the toggle hand-off, the selection hand-off, a direct
URL and a reload were all retested and are correct; hidden/dot subdirectories are excluded by the
grid's own scope too (ticket 054), so they cannot be the path.

## Outcome

`pages.js`'s `deleteReviewPage` now pages through `/api/photos` (`allRejectedPhotos`, using the
existing `window.__pageSize` test hook) until every rejected Photo in scope is collected, instead
of taking the first `limit=1000` page. The selection branch is unchanged (its ids are explicit).
New e2e: the toggle-driven header flow, the recursive selection hand-off, and a paged review that
lists all four rejected photos with a two-photo page size.
