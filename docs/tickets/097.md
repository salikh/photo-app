# 097: Question — merge exported file into the original's Photo, or keep it separate?

- Type: question
- Status: open
- Blocks: [098](098.md), [099](099.md), [100](100.md)
- Related: [096](096.md) (epic)
- Refs: `photoapp/manual_links.py` (`link` — merges a file into the target's `Photo`, `role`
  'tuning'|'export', currently only 'tuning' is ever actually used, from `grid.js`'s "Link 2nd as
  tuning of 1st"), `photoapp/grouping.py` (`fix_representatives` — a `Photo`'s `representative_
  file_id` decides which file's path the grid/folder view uses), `photoapp/api.py` (`/api/photos`
  filters by folder via the representative file's path — a multi-file `Photo` only shows up in the
  folder its *representative* file lives in, not every folder a member file happens to live in)

## Context

`manual_links` already has a `role='export'` link type reserved (`LINK_ROLES = ("tuning",
"export")`, and a migration comment noting it), never actually wired up by anything. Using it as-is
for exports would merge the exported file into the *same* `Photo` row as the original — exactly
like today's "Link 2nd as tuning of 1st" does for a manually-linked edit. That gets navigation
between original and export for free (the Files panel already lists every file of a `Photo` and
shows its `role`), but it also means the exported file, sitting physically in `/zoo/Pictures/
Exported/...`, would have **no `Photo` of its own there** — `/api/photos?dir=...` finds a `Photo`
by its *representative* file's path, and the representative would stay the original (elsewhere in
the library). Browsing the `Exported` folder in the grid would show nothing for it, even though the
file is really on disk there.

The user's stated goal is that exported photos should be **browseable inside the same system** —
which reads as "show up as their own grid entry in whatever folder they physically live in," not
just "reachable by clicking through from the original." That's in tension with reusing the
existing merge-into-one-Photo mechanism as-is.

## The question

When an exported file is connected to its original, should it:

- **(A) Merge into one Photo** (reuse `manual_links`' existing role='export' mechanism unchanged):
  simplest to build, reuses the Files-panel UI that already exists for 'tuning' siblings, but the
  export does not get its own grid entry in `/zoo/Pictures/Exported` — only the original's folder
  shows a `Photo` for it (unless the folder-filtering query is also changed to consider every
  member file's path, which would change behavior for every existing multi-file `Photo`, RAW+JPG
  pairs included — a much bigger, riskier change than this epic is asking for).
- **(B) Keep the exported file as its own independent Photo** (own row, own `representative_
  file_id` = itself, naturally browseable in `/zoo/Pictures/Exported`), plus a new, separate
  cross-reference (e.g. a new nullable `files.exported_from_file_id` column, or a lightweight
  table) purely for "jump to original" — the Files panel/loupe gets a new "exported from: [link]"
  affordance instead of reusing the sibling-files list.

Recommended: (B) — it's what actually satisfies "browseable inside the same system" for the
exported file itself, and avoids touching the folder-filtering behavior every other multi-file
`Photo` already relies on.
