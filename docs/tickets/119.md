# 119: Bug: Tuned RAW rendering sometimes is not applied when switching images

- Type: bug
- Status: done
- Related: [085](085.md), [102](102.md), [105](105.md)
- Refs: `photoapp/static/loupe.js`, `photoapp/api.py`, browser caching / thumbnail cache keys

## Description

After tuning a DNG rendering, navigating to the next image and then back may show an old thumbnail without tuning applied.
Sometimes the thumbnail changes after repeatedly leaving and revisiting an image in the stripe view.

## Root cause analysis pointers

- Browser HTTP caching: does `/img/Thumb/{id}` or `/img/Medium/{id}` get fetched with a stale browser cache entry before the server-side cache-clear has completed, or without a cache-busting timestamp/revision query param?
- In-memory client thumbnail cache in `loupe.js`: check if the frontend maintains an image object cache or stripe cache that is not invalidated on settings commit.
- Race condition on `POST /api/files/{id}/raw_settings` vs subsequent image load in stripe.

## Outcome

Root cause: `/img/{size}/{id}` is served with `Cache-Control: private, max-age=3600`, and the file's
`file_id` in the URL never changes, so a save only cache-busted the *currently visible* DOM nodes
(ticket 110's fix). Navigating away and back re-rendered the loupe/filmstrip with the plain URL,
and the browser served the pre-tune bytes from its cache for the rest of the hour.

Fix (server + client revision):
- New `files.thumb_rev` (migration), incremented by `raw_settings.set` and `crop.set` -- any save
  that changes the rendered bytes moves it.
- `library.list_photos`/`photo_detail` return it (`rev` / `thumb_rev`), and the two save endpoints
  return it too.
- `api.js` keeps a `fileId -> revision` map seeded from every photo/file payload (so it survives a
  full page reload) and `setRevision()` updates it on save; `imgUrl()` appends `?r=<rev>` once the
  revision is non-zero. Every image URL (loupe, zoom, preload, grid, filmstrip, row preview) goes
  through `imgUrl`, so a tuned file is requested from the server again after navigating back.
- `refreshCellThumb`/`filmstrip.refreshThumb` now rely on the revision instead of a `Date.now()`
  query param; forced re-renders (`rerenderThumbs`, retry) use a `forceUrl` helper so they don't
  double up query strings.

Tests: `tests/test_raw_settings.py` and `tests/test_crop.py` assert the revision bump (and that
`list_photos`/`photo_detail` carry it); the ticket 110 e2e was updated to the revision URLs; a new
e2e saves a crop, navigates away and back, and asserts the main image URL carries the new revision.
