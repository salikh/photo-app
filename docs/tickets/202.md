# 202: Bug: filtering by the `video` tag hung on "Loading…"

- Type: bug
- Status: done
- Priority: user report 2026-10-08
- Parent: [184](184.md); Refs: `photoapp/api.py` (`/img/{size}/{id}`, `video_thumb` job),
  `photoapp/thumb_populate.py`, `photoapp/static/{util,grid,filmstrip,loupe}.js`

## Report

Filtering by the `video` tag does not work.

## Cause

The query is right (API answers in ~0.1 s, 482 of 482 on the real folder). Reproduced against the real
library with a scratch state/thumbs dir: after choosing the tag the grid stayed on "Loading…" for the
better part of a minute and the browser never even sent the filtered request. Cause: a video's still
thumbnail was extracted *inside* the `/img/Thumb/{id}` request (an ffmpeg run, 0.5-several seconds over
the NAS, three at a time). A folder with hundreds of videos whose thumbnails were not made yet queued
hundreds of such requests, which held all of the browser's connections to the server, so the folder's
own API calls waited behind them.

## Fix

- A missing video still is no longer made in the request: the route queues a `video_thumb` job (the
  same pattern as a RAW without a preview: 404 + `Retry-After: 2`) which extracts one frame and writes
  all four sizes. A larger cached size is still downscaled directly.
- If ffmpeg is missing, or the video's thumbnails failed recently and it is unchanged
  (`video_failures`), the route answers the shared placeholder at once (`Cache-Control: no-cache`), so
  a broken video neither loops through jobs nor shows a broken image.
- Clients retry longer for a video: grid and filmstrip 120 tries, the loupe 40; the delay between
  tries is capped at 8 s (`retryImage` and the loupe's `retryOnce`; still-image behaviour is unchanged).
- Measured on the real folder: filtering shows 482 tiles within 4 s; the job queue then fills the
  thumbnails at roughly 10 per second.
