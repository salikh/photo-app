# 151: `link_exports`/`export_backfill` dhash heuristic: bonus for a same-name-different-case match

- Type: task
- Status: done
- Priority: user request 2026-09-29
- Related: [100](100.md) (`export_backfill.py`'s tier 2, the heuristic this tunes), [146](146.md)
  (`link_exports` job — same code path, scoped per directory)
- Refs: `photoapp/export_backfill.py` (`backfill_by_dhash`, `_candidate_stems`, `_dhash`,
  `_hamming`)

## What's wanted

In the dhash-matching heuristic, give a score bonus to a candidate whose filename matches the
unresolved export's except for the case of the extension (e.g. `K__5637.JPG` vs `K__5637.jpg`) —
still gated by the dhash distance threshold, not a replacement for it. Before implementing,
confirm the typical dhash-distance distribution on pairs already known to be correct (real
`exported_from_file_id` links in the live library), so the bonus is calibrated against real
numbers, not a guess.

## Investigation needed first

`_candidate_stems` already lowercases and strips the extension entirely before comparing stems, so
`K__5637.JPG` and `K__5637.jpg` (or even `K__5637.dng`) already tie on *stem* — the open question
is what a same-extension-case-insensitive match should change: likely how `results` are *ranked*
when more than one stem candidate exists (today: pure ascending dhash distance, ties broken as
"ambiguous" only on an exact distance tie), not whether a candidate is found at all.

Confirm against the real library (`/zoo`, read-only — the live `~/.local/share/photos/app.sqlite`
is a running instance's database, never write to it): for every file with a non-null
`exported_from_file_id` today (a link already trusted correct, from tier 1's exact job-log match or
a prior tier-2 run), compute the dhash Hamming distance between it and its source, and report the
distribution (min/median/mean/max, and separately for pairs whose filenames match
case-insensitively including extension vs. those that don't). This number is what calibrates
whatever bonus/threshold shape gets implemented, not a guess.

## Findings

Measured against the real library (read-only queries plus a scratch copy of the live db for the
one experiment that needed `backfill_by_dhash` to actually run; never wrote to the live
`app.sqlite`), 2026-09-29:

- **3086 already-linked `exported_from_file_id` pairs** exist today. Sampling 400 of them and
  computing the dhash Hamming distance between export and source (`export_backfill._dhash`/
  `_hamming`, via cached `Small` thumbnails): pairs whose full basename matches case-insensitively
  (incl. extension) have **median 0, mean 0.60, p75 1** (max 20, a rare outlier); pairs matching
  only by stem (different extension) have **median 1, mean 1.58, p75 2** (max 17). True matches
  cluster overwhelmingly in the 0-2 range regardless of naming.
- **1194 exported files remain unresolved** (`exported_from_file_id IS NULL`, under `Exported/`).
  Running the *current* `backfill_by_dhash` against a scratch copy of the real db: **0 of 1194
  matched** — everything easy was already claimed by earlier runs; what's left is the hard
  remainder. Classifying a random sample of 150: **31 no filename candidate at all** (a bonus
  can't help these), **68 an exact-distance tie between multiple candidates** (today: left
  unmatched as "ambiguous"), **51 a real name-matching candidate whose dhash distance is far
  outside any sane threshold** (28-39, vs. a 10 default) — almost all `IMG_NNNN.jpg`-style
  filenames from different camera-numbering batches (e.g. two unrelated iPhone imports both
  containing an `IMG_3930.JPG`), i.e. genuinely different photos that happen to share a name.
  **This last group is exactly why "still guard on the dhash similarity" matters**: a same-name
  bonus must never be large enough, or applied in a way, that lets one of these through.
- Of the 68 ties sampled, essentially all are an **exact** distance tie (0 vs 0, 2 vs 2, 4 vs 4 —
  never off-by-one) between a RAW file and its sibling JPEG in the same directory (e.g.
  `K___5637.DNG` and `K___5637.JPG`, both distance 0 from `Exported/.../K___5637.jpg`) — the export
  was almost certainly made from the already-rendered JPEG, and its name matches that JPEG's
  case-insensitively (including extension), not the DNG's. A couple of ties are two genuinely
  different files that happen to share a name in different folders (e.g. `IMGP0959.JPG` present in
  two unrelated 2012/2015 directories) — a same-name bonus correctly can't and shouldn't resolve
  those (both candidates match the name equally), and they should stay ambiguous.

**Design decision, from this data**: implement as a pure **tie-break among exactly-tied dhash
distances**, not a numeric distance adjustment applied everywhere — real near-ties (a 1-unit gap
between a named and unnamed candidate) were not observed in this data, so adjusting the general
ranking would be solving a problem that doesn't appear to exist while adding risk; a tie-break only
ever changes the outcome when the dhash distance already couldn't distinguish two candidates,
which is the cleanest way to satisfy "still guard on the dhash similarity" literally. Concretely:
among candidates tied at the minimum distance, if the set of those whose full basename matches the
export's case-insensitively (extension included) is exactly one, that one wins (no longer
"ambiguous"); otherwise (zero, or more than one such candidate) the existing ambiguous-tie
behavior is unchanged.

**Follow-up (user hint, mid-implementation)**: gate the name-match tie-break on date plausibility
too (close mtime, or a shared year-like folder), as an extra guard against a coincidental
name+dhash tie between two unrelated eras (not observed in the sampled ties, but a real enough
worry to check). Measured, not guessed:

- **mtime closeness between export and source is a strong, reliable signal for this library**:
  across the same 3086 true pairs, the export/source mtime difference is tightly bimodal — 95.9%
  within 1 day (mtimes cluster right around whatever real-world moment the pair was copied/
  migrated/exported together), 98.5% within a year, and the remaining ~1.5% (up to ~4 years) are
  still-genuine links whose mtime drifted for unrelated reasons (a re-save, a later re-copy).
- **"same year-based folder" is *not* a reliable signal for this library**, checked two ways
  before trusting it: comparing the export's own path to the candidate's path (year token matches
  for only 110/3086 = 3.6% of true pairs) and comparing the candidate's path year to the year of
  the *export's own mtime* (also only 110/3086). Spot-checked why: many exports (especially older,
  pre-app ones under paths like `Exported/2018-05-04/Pictures/Photo Archive/1600px/2012/...`) sit
  under a folder named for when the export batch was made or migrated, not the source photo's
  actual year — and file mtimes across this whole library mostly reflect copy/migration events,
  not original capture dates (confirmed by spot-checking a real tied pair: a 2012-dated and a
  2015-dated source folder for the same ambiguous `IMGP0959.JPG` name both had mtimes within ~13
  hours of each other and of the export, from what was clearly one bulk operation, not the
  camera). The year-folder check is kept anyway as a cheap fallback `OR` (harmless when it doesn't
  fire, and it's exactly what the user suggested), but mtime closeness (`_DATE_CLOSE_SECONDS`, a
  year) is the signal actually doing the work.
- **Full-library validation** (scratch copy of the real db, the new code, both the name tie-break
  and the date guard): of the 1194 previously-unresolved files, **453 now match (38%)** — closely
  matching the earlier ties/name-match estimate from the 150-file sample, confirming the design
  holds up at full scale, not just in the sample.

## Outcome

Landed. `export_backfill.backfill_by_dhash`'s ambiguous-tie handling now checks, among candidates
tied at the minimum dhash distance, whether exactly one has a basename matching the export's
case-insensitively (extension included) *and* passes `_dates_plausible` (mtime within a year, or a
shared year-like path component) — if so, that candidate wins instead of staying ambiguous. Never
touches the distance threshold itself or any non-tied comparison. `library_rows`/`unresolved`
queries now also select `mtime`, threaded through `candidates`/`results` for the date check.
`link_exports_job` (ticket 146) is unaffected (same shared function). 5 new tests in
`tests/test_export_backfill.py`: the RAW/JPEG-sibling tie resolves via the name match; a genuine
duplicate-name-in-two-places tie correctly stays ambiguous (both match the name equally); the
date guard blocks a would-be tie-break when the name-matching candidate's mtime and path give no
plausible date signal; the year-folder `OR` rescues a tie-break despite a far mtime; a
non-tied worse-distance candidate never wins on name alone. Full non-e2e suite green (443).
Validated against the real library (read-only + a scratch db copy, never touching the live
`app.sqlite`): 453 of 1194 previously-unresolved exports now link correctly.
