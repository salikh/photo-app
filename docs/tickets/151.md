# 151: `link_exports`/`export_backfill` dhash heuristic: bonus for a same-name-different-case match

## What's wanted

In the dhash-matching heuristic, give a score bonus to a candidate whose filename matches the
unresolved export's except for the case of the extension (e.g. `K__5637.JPG` vs `K__5637.jpg`) —
still gated by the dhash distance threshold, not a replacement for it. Before implementing,
confirm the typical dhash-distance distribution on pairs already known to be correct (real
`exported_from_file_id` links in the live library), so the bonus is calibrated against real
numbers, not a guess.

## Investigation needed first

`_candidate_stems` already lowercases and strips the extension entirely before comparing stems, so
`K__5637.JPG` and `K__5637.jpg` (or even `K__5637.dng`) already tie on *stem* — the open question
is what a same-extension-case-insensitive match should change: likely how `results` are *ranked*
when more than one stem candidate exists (today: pure ascending dhash distance, ties broken as
"ambiguous" only on an exact distance tie), not whether a candidate is found at all.

Confirm against the real library (`/zoo`, read-only — the live `~/.local/share/photos/app.sqlite`
is a running instance's database, never write to it): for every file with a non-null
`exported_from_file_id` today (a link already trusted correct, from tier 1's exact job-log match or
a prior tier-2 run), compute the dhash Hamming distance between it and its source, and report the
distribution (min/median/mean/max, and separately for pairs whose filenames match
case-insensitively including extension vs. those that don't). This number is what calibrates
whatever bonus/threshold shape gets implemented, not a guess.
