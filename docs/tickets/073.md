# 073: Load-adaptive background worker (auto start/stop on CPU/memory load)

- Type: task
- Status: done
- Priority: not now (user request 2026-09-22)
- Related: [066](066.md) (`populate_thumbs`, precedent for a low-priority nice/ionice worker),
  [076](076.md) (nightly per-directory scan jobs would feed this worker), [074](074.md) (the Jobs
  page progress indicator becomes much more useful once this runs continuously)
- Refs: `photoapp/jobs.py` (`JobQueue`, `_set_low_priority`), `photoapp/thumb_populate.py`
  (`Populator`, precedent for a low-priority single-worker queue), `photoapp/scan.py`
  (`NightlyScan`, precedent for a supervising daemon thread with an injectable wait for
  testability), `photoapp/__main__.py` (where daemons are started), `photoapp/config.py` (flags)

Add a permanent, always-running supervisor (started from `photoapp/__main__.py`, alongside
`NightlyScan`) that watches system CPU and memory load and starts a low-priority background
worker to drain the job queue when load is comfortably low, stopping it again when load rises
above a threshold. Today background work (`populate_thumbs.py`) only happens if a human notices
the machine is idle and runs it by hand; this makes it automatic and safe, without ever competing
with interactive use of the app or anything else running on the machine.

## Design notes / open decisions

- Reuse `jobs.JobQueue`'s existing `low_priority=True` machinery (`_set_low_priority`:
  `os.nice(19)` + `ionice -c3` on the worker thread) — this ticket only needs the start/stop
  supervision on top, not a new priority mechanism.
- Reading load without a new dependency: `os.getloadavg()` (1/5/15-minute averages, stdlib) for
  CPU; `/proc/meminfo`'s `MemAvailable` (Linux-only, consistent with the rest of this codebase) for
  memory. `psutil` would be more portable/precise but is not currently a dependency — a deliberate
  choice either way, not an accidental one.
- Flapping: a single threshold right at the boundary will start/stop repeatedly. Use two
  thresholds (a "safe to start" and a lower "must stop"), and/or require a reading to hold for
  several consecutive checks before flipping state.
- Check interval: how often to sample (e.g. every 30s) and how that trades off against reacting
  promptly to someone starting real work on the machine.
- This worker needs to coexist with `app.state.jobs` (the existing on-demand `raw_render` queue,
  deliberately normal-priority) sharing the same `jobs` table without either starving the other —
  `JobQueue._claim`'s existing kind-scoping already supports two independent queues over one table.
- Whether this subsumes `populate_thumbs.py` (ticket 066) as a standalone script — i.e. does the
  server now do this automatically (reusing `thumb_populate.Populator`), leaving the script only
  for an explicit manual catch-up run? Leaning toward yes.
- New flags in `config.py`, following the existing style (`job_workers`, `scan_workers`):
  something like `--load_worker_enabled` (default on), `--load_check_seconds`,
  `--cpu_load_threshold`, `--mem_available_threshold_percent`.

## Decisions

- Idle load can be observed from idle state, e.g. right now I see load average of 0.06, 0.16, 0.18.
Anything under 0.5 feels like sufficiently idle state. Memory load is harder to judge, right now I see
MiB Mem :   7764.7 total,   4353.9 free,   2716.9 used,   1199.9 buff/cache
MiB Swap:  15255.6 total,  11944.1 free,   3311.5 used.   5047.8 avail Mem
and this certainly is idle state. Unfortunately, some legitimate programs may use lots of memory,
e.g. chrome and claude. Maybe the thresholds for memory load can be learned with practice,
which means that the worker triggering logic should be constantly (every few minutes) log the CPU
and memory load indicators, and analyze them in Claude later by correlating with log of worker starts
and shutdowns.
- Re:  subsuming standalone role -- nope, the standalone command should be still working, but is
good to share code.

## Result (2026-09-22)

New `photoapp/load_worker.py`: `LoadAdaptiveWorker` polls `os.getloadavg()`'s 1-minute figure and
`/proc/meminfo`'s `MemAvailable` (`default_sample()`) every `--load_check_seconds`, and calls
`queue.start()`/`queue.stop()` on a `jobs.JobQueue` crossing the start/stop thresholds
(`--load_start_threshold`/`--load_stop_threshold`, `--mem_start_percent`/`--mem_stop_percent`,
defaults from the Decisions above: 0.5/1.5 load, 20%/10% memory — the memory numbers are
explicitly a first guess). Every sample is logged at vlog(3) regardless of the decision made from
it, exactly as decided, so the thresholds can be tuned later from real logs; every start/stop
transition is logged at `info` level (always visible, not just under `--verbosity`).

Reused `jobs.JobQueue`'s existing low-priority machinery and `thumb_populate.Populator` directly
(satisfies "share code, don't subsume the standalone script" -- `populate_thumbs.py` itself is
untouched and still works exactly as before). Wired into `photoapp/__main__.py`: when
`--load_worker_enabled` (default on), it builds a `Populator` and hands its `.queue` to a
`LoadAdaptiveWorker`, with `on_before_start` re-running `enqueue_missing` on every idle transition
so newly-scanned files pick up thumbnails without a manual rerun of the standalone script.

**Bug found and fixed along the way**: `jobs.JobQueue` was never designed to be `start()`ed more
than once per process (every existing caller starts it exactly once) -- its internal `_stop` event
was set by `stop()` and never cleared, so a second `start()` after a `stop()` would spawn worker
threads that see `_stop` already set and exit immediately without doing anything. The
load-adaptive worker starts/stops the *same* queue repeatedly over the life of one process, so
this needed a real fix, not a workaround: `start()` now clears `_stop` first. Covered by
`test_queue_can_be_restarted_after_stop` in `tests/test_jobs.py`.

Coexistence with the existing on-demand `raw_render` queue relies on `JobQueue._claim`'s existing
kind-scoping (each queue only ever claims its own kinds from the shared `jobs` table) plus the
nice/ionice priority drop already applied to `low_priority=True` queues -- no new mechanism was
needed for "never starves the on-demand queue", and the existing
`test_populate_thumb_jobs_appear_on_the_running_apps_jobs_page` (tests/test_jobs.py) already
demonstrates the two queues coexisting correctly over one `jobs` table.

`docs/operations.md`'s flags table and "Populating thumbnails in the background" section updated.
`tests/test_load_worker.py` (8 tests: threshold crossing, hysteresis, memory gating,
`on_before_start` behavior including an exception not blocking the start, the real
`default_sample()`, and the thread start/stop lifecycle) + the new `jobs.py` restart test: all
pass. Full suite run separately to confirm no regressions elsewhere.
