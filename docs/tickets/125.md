# 125: Export should always apply the file's crop

- Type: enhancement (refined feature request)
- Status: done (2026-09-26)
- Related: [089](089.md) (Export action), [096](096.md)-[100](100.md) (exports live in the library),
  [115](115.md) (non-destructive crop), [116](116.md) (crop/thumbnail decision)
- Refs: `photoapp/export.py` (`export_file`), `photoapp/thumbs.py` (`ensure`/`make`/`render`,
  `CROPPED_SIZES`), `photoapp/crop.py`

## What's wanted

Export currently reuses `thumbs.ensure(..., "Huge")` and copies the resulting JPEG. By ticket 116's
decision, `Medium`/`Huge` are rendered **full frame** (the loupe shades the cropped-out area), so a
cropped photo exports uncropped. The export should instead be a Huge-equivalent JPEG that **always
has the file's crop applied** (the same rectangle the grid `Thumb`/`Small` already use), since an
export is a finished, out-of-app artifact where the shaded-out margin makes no sense.

## Design notes

- A cropped export must be re-encoded (the crop is a pixel operation), not just copied: render/obtain
  the full-size image (the existing Huge path), then crop it with `crop.pixel_box(crop, W, H)` and
  write the JPEG. An uncropped export can keep the current fast copy path.
- JPEG exports are lossy copies already (Huge is a JPEG), so a second encode of the cropped copy is
  acceptable; prefer cropping from the **original** where cheap (a non-RAW original, or an existing
  lossless source) over the lossy Huge, but the full-size `previews.render`/embedded-preview path is
  fine for RAW.
- The imported export is a normal library file (tickets 098/099); it should be recorded **without**
  copying the source's crop onto it (the crop is already baked into its pixels), so a later
  scan/view of the export does not double-crop. Confirm `import_single_file` doesn't inherit it
  (crop lives on the source `files` row, so a fresh row starts NULL -- verify).
- Exports of a non-cropped file must be byte-for-byte the behaviour it has today.

## Outcome

`export.py`'s `export_file` now branches on the source's crop: an uncropped file keeps the exact
old path (`thumbs.ensure(..., "Huge")` then `shutil.copyfile`), while a cropped one calls
`thumbs.render(original, dest, None, settings, crop)` — the full-frame image is decoded and cropped
in one pass straight from the original (never the full-frame, lossy `Huge`), using the same
`crop.pixel_box` rectangle `Thumb`/`Small` use. `scan.import_single_file`'s insert carries no
`crop_*` columns, so the freshly imported export row starts all-`NULL` (verified by test). New
tests: a 40x30 JPEG cropped 25%-50% exports at 20x15; the imported export's crop columns stay
`NULL` while the source keeps its crop; and an e2e drives the Export UI over a cropped photo and
checks the written JPEG's size. Documented in `docs/design/thumbnails.md`.
