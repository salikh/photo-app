# 106: Save flow — commit LibRaw-Wasm's tuning parameters, re-render from the original DNG

- Type: task
- Status: done
- Related: [102](102.md) (epic), [105](105.md) (done)
- Refs: `photoapp/raw_settings.py` (`COLUMNS`, `validate`, `to_columns`, `set` — today's four
  persisted settings), `photoapp/api.py` (`set_raw_settings`, `raw_preview`), `photoapp/
  static/loupe.js` (`saveRawSettings` — ticket 094's commit call, unchanged in spirit: POST the
  pending values, then `thumbs.clear` and let the next request re-render)

## What's wanted

When the user clicks Save in the LibRaw-Wasm-driven tuning UI ([105](105.md)):

1. Persist the pending tuning parameters (as today, `set_raw_settings`/`raw_settings.set`).
2. Trigger the backend to re-render the *committed* thumbnails from the **original, full-quality
   DNG** (not the lossy preview DNG) using those same parameters — this is exactly what
   `set_raw_settings` already does today (`thumbs.clear` + the next request re-renders through
   `previews.render`); the only new question is whether every parameter LibRaw-Wasm exposed
   actually has a backend equivalent to re-render with.

Both already true, unchanged by 105: `saveRawSettings` still POSTs the same four values to the
same endpoint, which still does exactly the same `thumbs.clear` + next-request-re-renders dance
as before this epic. This ticket turned out to be the two design notes below, not new code.

## Design notes (resolved)

- **Parameter parity**: `photoapp/raw_settings.py` persists four things (`bright`, `wb_mode`/
  `wb_r`/`wb_g`/`wb_b`, `highlight`). **Resolved as option (a), restrict**: 105's `rawTuning.js`
  (`mapSettings`) only ever surfaces these same four to LibRaw-Wasm, mirroring `previews.py`'s
  `_postprocess_kwargs` parameter-for-parameter, so nothing new needs a backend equivalent. Not
  extended to LibRaw-Wasm's fuller surface (demosaic quality, denoising, colorspace, saturation) --
  would need new `raw_settings` columns, a schema migration, and `_postprocess_kwargs`/`raw_preview`
  updates to stay in sync, for controls the tuning UI doesn't expose yet either.
- **Drift risk**: **resolved, and it was real** -- checked directly against a real Pentax K-5 DNG
  (both rawpy and the actual vendored LibRaw-Wasm build, same nominal settings) rather than left as
  a theoretical worry. The first version of [104](104.md)'s preview DNG generator was badly wrong
  (mean green channel off by ~4x from the original's render) for two independent reasons, both
  found and fixed as part of verifying this ticket:
  1. A multi-value `BlackLevel` tag needs its `BlackLevelRepeatDim` (50713) companion tag declared,
     or LibRaw silently treats it as unset (reads back as all zeros) even though the tag itself is
     present and correctly typed.
  2. LibRaw's color pipeline turned out to ignore a DNG's own embedded `ColorMatrix1`/`ColorMatrix2`
     entirely unless the file also carries a Make/Model LibRaw recognizes from its own built-in
     camera table -- "RAW conversion is very basic" per a LibRaw maintainer
     ([libraw.org/node/2674](https://www.libraw.org/node/2674)). [104](104.md) now passes the
     source's real Make/Model through into the preview DNG when its EXIF has one (letting LibRaw use
     the *same* built-in matrix it uses for the original file, which is more accurate than trusting
     an embedded matrix anyway) and falls back to an embedded `UniqueCameraModel` + `ColorMatrix1/2`
     only when Make/Model aren't available -- confirmed the two approaches don't compose: writing
     both together (a recognized Make/Model *and* an embedded matrix) produced the same wrong colors
     as neither, so they're mutually exclusive branches, not layered.

  After both fixes, mean RGB between the local preview and the backend-committed render agree
  within ~1-2% per channel (the residual is plausibly the preview's resolution reduction, not a
  color bug) -- see `test_real_dng_preview_color_matches_the_original_closely` in
  `tests/test_raw_preview_dng.py`. The remaining residual case (no Make/Model in the source's EXIF)
  still relies on the embedded-matrix path, which is not verified to render accurately by this
  ticket's check (LibRaw's own maintainer describes that path as out of scope for LibRaw to get
  right) -- a real gap, but a narrower one than before, and it now degrades to "no recognized
  camera" behavior rather than actively wrong output for photos it *does* know.
