# 106: Save flow — commit LibRaw-Wasm's tuning parameters, re-render from the original DNG

- Type: task
- Status: open
- Related: [102](102.md) (epic)
- Blocked by: [105](105.md)
- Refs: `photoapp/raw_settings.py` (`COLUMNS`, `validate`, `to_columns`, `set` — today's four
  persisted settings), `photoapp/api.py` (`set_raw_settings`, `raw_preview`), `photoapp/
  static/loupe.js` (`saveRawSettings` — ticket 094's commit call, unchanged in spirit: POST the
  pending values, then `thumbs.clear` and let the next request re-render)

## What's wanted

When the user clicks Save in the LibRaw-Wasm-driven tuning UI ([105](105.md)):

1. Persist the pending tuning parameters (as today, `set_raw_settings`/`raw_settings.set`).
2. Trigger the backend to re-render the *committed* thumbnails from the **original, full-quality
   DNG** (not the lossy preview DNG) using those same parameters — this is exactly what
   `set_raw_settings` already does today (`thumbs.clear` + the next request re-renders through
   `previews.render`); the only new question is whether every parameter LibRaw-Wasm exposed
   actually has a backend equivalent to re-render with.

## Design notes (open)

- **Parameter parity**: `photoapp/raw_settings.py` persists four things (`bright`, `wb_mode`/
  `wb_r`/`wb_g`/`wb_b`, `highlight`). LibRaw-Wasm's settings surface, per its docs, also includes
  demosaic interpolation quality, denoising (wavelet/FBDD/median), output colorspace, and
  saturation — none of which `previews.render`/`_postprocess_kwargs` currently thread through to
  `rawpy.postprocess()`, even though rawpy/LibRaw supports equivalent kwargs for most of them
  (both wrap the same underlying library). Decide: (a) restrict the tuning UI to only the four
  parameters that already round-trip end to end (simplest, no schema change, but wastes most of
  what LibRaw-Wasm exposes), or (b) extend `raw_settings`'s columns and `_postprocess_kwargs` to
  cover the rest (matches the epic's spirit, more surface to keep in sync between the client
  library's option names and rawpy's kwarg names).
- **Drift risk**: LibRaw-Wasm and rawpy are independent bindings of the same C library and are not
  guaranteed to expose numerically identical behavior for the same nominal setting (e.g. rounding,
  default values, highlight-recovery mode numbering) — the provisional preview the user tuned
  against in the browser and the committed render the backend produces could visibly differ even
  with "the same parameters." Worth a real side-by-side check with an actual RAW file before
  treating this as a solved problem.
