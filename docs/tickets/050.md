# 050: Preload the big image data of the photos within ±2 of the current one

- Type: task
- Status: done
- Related: [027](027.md) Loupe view (current preloading), [045](045.md) Swipe navigation, [028](028.md) RAW previews and jobs, [017](017.md) thumbs.py
- Refs: user request; `photoapp/static/loupe.js` (`preload()`), `photoapp/api.py` (`/img/{size}/{id}`)

Make moving to a neighboring photo render sooner by loading the *big* image data of the photos
within two positions of the current one (`i-2`, `i-1`, `i+1`, `i+2`) ahead of time, in the browser
and, where needed, on the server.

## Today

- The loupe preloads only the `Medium` size (2000 px long edge), for the next 3 and the previous 1
  (`PRELOAD_NEXT = 3`, `PRELOAD_PREV = 1`), with `new Image().src = ...`.
- The big version (`Huge`, full size) is fetched only when the user zooms, so a zoom after navigating
  waits for the download and for a possible server-side render.
- For a RAW (DNG) the server builds every size on first request from the embedded preview (about
  1 s for the four sizes, 0.3 s of it for the full-size re-encode), so a cold neighbor is slow.

## Open design points (decide while implementing, measure first)

- What "big" means for the transition: the `Medium` image that is shown on arrival (already
  preloaded, but only ahead by 3/1), or the `Huge`/full image used for zoom, or both. Proposal:
  `Medium` for i±1 and i±2 first (cheap), then `Huge` for i±1 and i±2 at lower priority.
- Bytes: a `Huge` JPEG is 5-20 MB. A phone on mobile data must not download 4 of them per step.
  Proposal: skip the `Huge` preload when `navigator.connection.saveData` is set or the connection is
  cellular/slow, and cap the preloaded `Huge` bytes.
- Decode cost: a decoded 4928x3264 image is about 64 MB of memory. Use `img.decode()` off the main
  thread and hold at most a few decoded images; keep references only for the ±2 window.
- Fast navigation: cancel or deprioritize preloads that are no longer in the ±2 window
  (`AbortController` with `fetch`, or `fetchpriority="low"`), so holding an arrow key does not queue
  dozens of stale downloads.
- Server side: render the neighbors' sizes before the browser asks, so a cold RAW does not stall a
  swipe. Options: a `POST /api/prefetch {file_ids, sizes}` that queues background jobs (reusing the
  job queue of [028](028.md)); or let the browser's preload request do it. Watch the disk growth in
  `/zoo/Thumbs/Huge`.
- Cache headers: `Cache-Control: private, max-age=3600` is already set; check the browser actually
  serves preloaded images from its cache when the loupe requests the same URL.

## Result (2026-09-21)

Implemented in `static/preload.js` (new), wired from `static/loupe.js`; server: `render_limited` in `api.py`.

- **Window:** photos at i-2..i+2, the direction of travel first. For each: `Medium` (what is shown on arrival, decoded ahead,
  about 12 MB), then `Huge` (full size, for zoom) at low priority and only fetched into the cache; only the next photo in the
  direction of travel has its `Huge` decoded (a decoded 16 MP image is about 64 MB). After a 400 ms pause on a photo (the user
  is probably about to zoom) its own `Huge` is decoded too, one at a time.
- **Data saving:** no `Huge` preload when `navigator.connection.saveData` is set or the connection is slow (`2g`, `3g`); `Medium`
  is still preloaded.
- **Fast navigation:** what leaves the window is cancelled (`img.src = ''`) and its memory released, the current photo's own
  images are never cancelled (the viewer's `<img>` shares those requests), and closing the viewer releases everything.
- **Server:** the browser's preload requests are what make the server render cold thumbnails and RAW previews (no separate
  prefetch endpoint was needed); a semaphore limits concurrent renders to 3 so a burst of preloads cannot overload the CPU. An
  aborted request does not waste the work: the rendered file is kept on disk.
- **Tests** (`tests/e2e/test_ui.py`): exactly the window is requested and held, Medium before Huge, three away is not
  preloaded; the window follows the direction and releases what was left behind; holding an arrow key leaves no pile;
  a zoom after a pause needs no second request for the full-size image; no full-size preload on a data saver or a slow
  connection. `window.__preloadedUrls` is a test hook, not a feature.
- **Measurements** (`tools/measure_navigation.py`, 8 synthetic 4928x3264 photos, Chrome on this machine, localhost, ms, 3 runs
  each; before = the commit before this change):

  | scenario | before | after |
  |---|---|---|
  | zoom (`Z`, the full-size image), after settling | 94-101 | **14-17** |
  | next photo / two ahead, after settling | 8-15 / 12-17 | 4-15 / 9-18 |
  | four quick steps forward | 137-141 | 128-159 |
  | cold jump to the last photo, then two quick steps back | 46-54 | 57-64 |

  Honest reading: on localhost everything the old code already preloaded is a few milliseconds, so there is nothing to win
  there; the clear gain is **zoom, about 6 times faster** (the full-size download and its 16 MP decode are done ahead). The
  cold two-back jump shows no gain here (the difference is noise, and the 30 ms between the two key presses is included);
  its benefit is on a slower link or a cold RAW render, where one more photo of look-behind matters, and cannot be measured
  on localhost. To measure on a real phone or over the LAN, run the tool against a server on the LAN.
