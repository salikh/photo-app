# 050: Preload the big image data of the photos within ±2 of the current one

- Type: task
- Status: open
- Related: [027](027.md) Loupe view (current preloading), [045](045.md) Swipe navigation, [028](028.md) RAW previews and jobs, [017](017.md) thumbs.py
- Refs: user request; `photoapp/static/loupe.js` (`preload()`), `photoapp/api.py` (`/img/{size}/{id}`)

Make moving to a neighboring photo render sooner by loading the *big* image data of the photos
within two positions of the current one (`i-2`, `i-1`, `i+1`, `i+2`) ahead of time, in the browser
and, where needed, on the server.

## Today

- The loupe preloads only the `Medium` size (2000 px long edge), for the next 3 and the previous 1
  (`PRELOAD_NEXT = 3`, `PRELOAD_PREV = 1`), with `new Image().src = ...`.
- The big version (`Huge`, full size) is fetched only when the user zooms, so a zoom after navigating
  waits for the download and for a possible server-side render.
- For a RAW (DNG) the server builds every size on first request from the embedded preview (about
  1 s for the four sizes, 0.3 s of it for the full-size re-encode), so a cold neighbor is slow.

## Open design points (decide while implementing, measure first)

- What "big" means for the transition: the `Medium` image that is shown on arrival (already
  preloaded, but only ahead by 3/1), or the `Huge`/full image used for zoom, or both. Proposal:
  `Medium` for i±1 and i±2 first (cheap), then `Huge` for i±1 and i±2 at lower priority.
- Bytes: a `Huge` JPEG is 5-20 MB. A phone on mobile data must not download 4 of them per step.
  Proposal: skip the `Huge` preload when `navigator.connection.saveData` is set or the connection is
  cellular/slow, and cap the preloaded `Huge` bytes.
- Decode cost: a decoded 4928x3264 image is about 64 MB of memory. Use `img.decode()` off the main
  thread and hold at most a few decoded images; keep references only for the ±2 window.
- Fast navigation: cancel or deprioritize preloads that are no longer in the ±2 window
  (`AbortController` with `fetch`, or `fetchpriority="low"`), so holding an arrow key does not queue
  dozens of stale downloads.
- Server side: render the neighbors' sizes before the browser asks, so a cold RAW does not stall a
  swipe. Options: a `POST /api/prefetch {file_ids, sizes}` that queues background jobs (reusing the
  job queue of [028](028.md)); or let the browser's preload request do it. Watch the disk growth in
  `/zoo/Thumbs/Huge`.
- Cache headers: `Cache-Control: private, max-age=3600` is already set; check the browser actually
  serves preloaded images from its cache when the loupe requests the same URL.
