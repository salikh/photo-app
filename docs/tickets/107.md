## Problem: the compare hotkey is unusable while a slider has focus

Ticket 094's 'c' hotkey is gated behind `onKey`'s `if (isTyping(e.target) || ...) return;` guard.
A `<input type="range">` slider *is* an INPUT, so as soon as the user drags a slider (which
focuses it) and wants to immediately compare, 'c' silently does nothing — exactly the moment the
feature exists for. `isTyping`'s guard is right for letter keys (typing 'c' into a text field must
not fire a hotkey), but a bare modifier key like Shift never inserts a character into any input,
range or otherwise, so gating a modifier-only compare key behind `isTyping` is unnecessary caution,
not a real conflict.

## Feature: hover should drive comparison too, with a third state

Beyond fixing the keyboard path (user request 2026-09-24), add mouse-hover-driven comparison,
richer than today's binary tuned/committed toggle:

- Mouse inside the raw-settings sliders block → show the tuned (provisional) rendering.
- Mouse outside that block (elsewhere in the viewer/panel) → show the committed (previously saved)
  rendering — today's default `ui.img`.
- Mouse over the sibling camera JPEG's row in the Files panel → show *that* file's own thumbnail,
  a third distinct image, neither RAW rendering.

## Design notes (open — resolve during implementation)

- **Modifier key choice**: Shift is the user's own suggestion; confirm it doesn't collide with any
  existing Shift-modified behavior (`grid.js`'s Shift+Click range selection is a *click* modifier,
  a different event/context, but worth a deliberate check) before settling on it over another
  modifier (Alt, or holding right-click).
- **Hover vs. keyboard precedence**: once hover works, does the modifier key still matter, or does
  it become the fallback for input modalities without hover (touch, keyboard-only)? Keep both —
  they serve different cases — but decide which wins if both are active at once (e.g. holding
  Shift while the mouse is also outside the sliders block).
- **"Camera JPG block" scope**: exactly the hovered file's `.file` row in the Files panel, keyed
  by that row's `role` (e.g. `camera`) rather than hardcoding "the JPG" — a `Photo` can have more
  than one sibling file, so hovering *any* non-representative file's row swapping in *that* file's
  own thumbnail is the more general, more useful version of the request.
- **Interaction with zoom**: 094's overlay is hidden while pinch-zoomed (`enterZoom`); decide
  whether hover-compare should stay disabled there too, or work on the zoomed image as well.
- **Interaction with ticket 102** (if/when it lands): this hover logic should key off `ui.tuning`'s
  current state, not which renderer filled it (094's backend `raw_preview`, or 102's client-side
  LibRaw-Wasm render), so it keeps working unmodified either way.
