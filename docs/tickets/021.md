## New requirement (user, 2026-09-21): the database and the XMP files are both eligible

The authoritative rating is **the newest rating among all its sources: the app database and every sidecar
of the Photo**. Just take the newest. (Until now the sidecars alone decided and the database was only a
cache; imported and app-set ratings never overrode an XMP rating.) Requirements doc updated.

### What it means

- A rating has a time per source. Sidecar: its file mtime (as now). Database: **new**
  `photos.rating_updated_at`, the time the rating was set in the database.
- `ratings.resolve` gets the database as one more candidate next to the sidecars; the newest wins, and
  `photos.conflict` is set when the candidates disagree. The winner decides rating, fav and tags
  (proposal: the same source for all three, as today).
- **App edits** set the database and write both sidecars (023). After the write, the database time is set
  to the sidecars' mtime, so they tie and do not flip-flop; equal values never conflict.
- **Something newer in a sidecar** (edited in darktable after the app's last edit) wins on the next scan
  and the database follows.
- **Something newer in the database than in a sidecar** wins in the UI. The scan itself stays read-only
  on the library, so it does not write the sidecars; they are brought in line on the next write, or by an
  explicit sync (see the open points).
- **Time of ratings from outside.** An imported rating (022) must carry the time it was originally set,
  not "now", otherwise every import would override every sidecar. `image_metadata.py` has no such time
  yet: use the mtime of the file the rating came from (the `.prod.db` file, or the sidecar named in
  `rating_source_path`). Same for hash recovery (036): `rating_by_hash` needs `rated_at`, and a recovered
  rating keeps its original time.
- **Undo** writes the old value with the current time (a new, newest decision).
- **The database is no longer only a cache.** Ratings that exist only there (an import without
  `--write_xmp`) cannot be rebuilt from the files: back up `app.sqlite`, and update the table in
  `docs/operations.md` (which lists `photos` as rebuildable).
- Existing databases: set `rating_updated_at` from what is known: sidecar-sourced ratings from the
  winning sidecar's mtime, app-set ratings from the newest activity-log time, others 0 (oldest, so a
  sidecar wins), so nothing changes visibly at migration.

### Open design points

- **Clock skew.** The database time comes from the app machine's clock and sidecar times from the file
  server's. Compare with a small tolerance (for example 2 s) and treat "within tolerance" as a tie that
  keeps the current value.
- **Syncing the sidecars** when the database is newer: only on the next edit, or also an explicit
  "sync" (a command or a button that writes the database value to the sidecars, listing what it will
  change first). The scan must not write by itself.
- **Rejects:** answered in [053](053.md), see "Reject rule" below.
- **Fav and tags** follow the winning source (proposal), but they are also written to both sidecars on
  every edit (023), so they rarely differ.

### Reject rule (answer to [053](053.md), 2026-09-21)

darktable treats the DNG and the JPG as separate images, so a reject on one of the two sidecars often only means
"keep the other file". Therefore, when resolving a Photo:

- The winner is chosen by newest first, as above (database and sidecars).
- **If the winner is a reject that comes from a single sidecar and another sidecar of the Photo is picked
  (rating > 0), the Photo is not rejected**: its rating is the newest picked sidecar's.
- **A reject made in this app wins by being the newest.** The app writes the reject to both sidecars (and the
  database), so nothing is picked in the pair; a newer app decision always wins over older data.
- A reject against an unrated (0) sidecar has nothing to protect: plain newest-wins (assumption, see 053).
- "Picked" is any rating from 1 to 5, including darktable's default 1; `--one_star_is_unrated` only changes the display.
