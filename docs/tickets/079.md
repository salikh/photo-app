# 079: Force-rerender a photo's thumbnails from the loupe (fixes broken ones)

- Type: task
- Status: done
- Priority: not now (user request 2026-09-22)
- Related: [017](017.md) thumbs.py, [028](028.md)/[073](073.md) background rendering paths,
  [066](066.md) populate_thumbs (never overwrites an existing thumbnail, which is exactly what
  this ticket needs to override)
- Refs: `photoapp/static/loupe.js` (`renderHud`, the HUD button row, `imgUrl`/`retryOnce`'s cache-bust
  pattern), `photoapp/thumbs.py` (`make`, `ensure`, `_record` — "never overwrites" is enforced by
  `lookup` being checked first), `photoapp/api.py` (`/img/{size}/{file_id}`), `photoapp/jobs.py`

Add a button in the loupe (tucked under a "..."/"Debug" menu, next to the existing HUD buttons —
`files`, `undo`, etc.) that forces every thumbnail size of the currently open photo to be
re-rendered right away. This is the fix for a broken thumbnail that fails to render (a corrupt
cached file, a bad decode that got saved anyway) — today the only way to see a fresh render is
outside the app (delete the file from `/zoo/Thumbs` by hand).

## Why this doesn't already work

Every existing rendering path in this codebase (`thumbs.make`, `thumb_populate.populate_file`,
`ensure`) deliberately **never overwrites a thumbnail that already exists** — `thumbs.lookup` is
checked first everywhere, precisely so re-running a scan or `populate_thumbs.py` is cheap and
idempotent. That's the right default, but it means there is currently no path in the app that
regenerates a thumbnail that's already on disk, broken or not.

## Design notes

- **Force-regenerate mechanism**: delete the existing thumbnail file(s) and their `thumbs` table
  row(s) for this file's id (all four sizes, or just the broken one(s) — probably all four, since
  the user is unlikely to know which size is actually broken), then trigger a fresh render.
  Re-running `thumbs.make`/`ensure` afterward "just works" since they only skip when `lookup`
  finds something — the fix is entirely in *clearing first*, not in changing the render path.
- **"Schedules immediate rerendering"**: could mean a synchronous render (block the request, like
  today's on-demand `/img/...` route already does for a first-time thumbnail) or queuing a
  same-priority (not low-priority/background) job so the button returns promptly and the loupe
  polls or retries. Leaning toward synchronous for `Thumb`/`Small`/`Medium` (fast) and letting
  `Huge` follow the existing on-demand path, but worth confirming — a user clicking a "fix this"
  button expects to see a result quickly.
- **Cache-busting**: the browser (and the `Cache-Control: private, max-age=3600` header on
  `/img/...`) will happily keep showing the old broken image after a re-render unless the `<img>`
  `src` changes — reuse the `?r=N` query-param trick `loupe.js`'s `retryOnce` already uses for RAW
  retries.
- **Detecting failure automatically** (the alternative/upgrade the user suggested): there is
  currently no record of a thumbnail *failing* to render inline (`/img/...`'s on-demand path just
  404s or serves what it made; only the background `raw_render`/`populate_thumb` *jobs* persist a
  `failed` state with an error). Making failure visible in the UI without the user having to
  notice a broken image would need either: (a) the client detecting an `<img>` `onerror` (it
  already has `retryOnce` doing exactly this for RAW previews — extending that to flag "still
  broken after N retries" in the HUD is the cheapest option, no server change), or (b) a server-side
  signal (e.g. persisting on-demand render failures somewhere queryable, closer to how job failures
  already work). Leaning toward (a) first since it's client-only and reuses existing code, with (b)
  as a possible follow-up if broken thumbnails turn out to be common enough to want a supply-side
  view (e.g. an "attention" list) instead of only reacting to one already-open photo.

## Result (2026-09-22)

Resolved the two open design notes: **clearing only, no synchronous server-side render** — the
endpoint just deletes the cached files/rows; the very next `/img/...` request (which the frontend
triggers immediately via a cache-busted reload) regenerates through the exact same on-demand path
every other thumbnail already goes through, so no new render logic was needed at all. **Failure
auto-detection ships in this ticket**, folded into the same mechanism rather than treated as a
separate follow-up.

New `thumbs.clear(thumbs_dir, conn, file_id, file_path)`: deletes every cached size's file (if any)
and `thumbs` row for one file, logs what it cleared at `info`, and does nothing else — matches the
finding that "the fix is entirely in clearing first." `POST /api/files/{file_id}/rerender_thumbs`
(same `/api/files/{file_id}/...` family as `link`/`unlink`) calls it and returns which sizes were
cleared.

`loupe.js`: a small "⋯" button (`class="debug-menu"`, tooltip "debug: re-render this photo's
thumbnails") sits at the end of the HUD button row, calling the endpoint then cache-busting and
reloading the main image. `retryOnce`'s existing 6-retry backoff (unique to this app, not the
shared `retryImage` in `util.js`) now tracks a `brokenFileId` when every retry has failed; while
it's set, `renderHud()` swaps the small "⋯" for a prominent red "⚠ fix thumbnail" button in the
*same* position, using the *same* action — one mechanism serves both the tucked-away debug case
and the user's suggested "make it prominent when actually broken" upgrade.

Tests: `tests/test_thumbs.py` (`clear` removes files+rows, is a no-op the second time, and a
following `ensure()` regenerates normally), `tests/test_more_api.py` (the endpoint end to end,
including a 404 for an unknown file), and two e2e tests in `tests/test_ui.py` — one clicking the
debug button and confirming the thumbnail re-fetches successfully, one forcing every `/img/Medium`
request to 404 and confirming the prominent fix button appears once all 6 retries are exhausted
(this one genuinely takes ~35s of real time — the retry backoff isn't configurable, and a
Playwright fake clock can't safely fast-forward through retries that are each scheduled only after
the previous real network response comes back). All pass; full non-e2e suite (223 tests) also
still passes.
