# 095: Shift+Click range selection in the grid

- Type: task
- Status: open
- Priority: not now (user request 2026-09-24)
- Refs: `photoapp/static/grid.js` (`makeCell`'s `onclick`, ~line 84-91 — currently treats
  `e.shiftKey`/`e.ctrlKey`/`e.metaKey` identically, all three just call `toggle(id)`; `toggle`,
  ~line 96; the `check` button, ~line 76, also calls `toggle(id)` unconditionally, ignoring
  modifiers), `photoapp/static/state.js` (`state.selected` — a `Set`, no ordering; needs a new
  "last selected"/anchor field), `photoapp/static/app.js` (`clearSelection`'s Escape binding,
  ~line 195; `loadFolder`/filter changes already `state.selected.clear()`)

Today, Shift+Click, Ctrl/Cmd+Click, and clicking a cell's own ✓ button (or any click while
touch-friendly `state.selecting` mode is on) are all exactly the same: `toggle(photo.id)` on just
that one photo. There's no concept of a "last selected" anchor, so Shift+Click can't do the usual
file-manager thing — select every photo between the last one you touched and the one you just
Shift+Clicked.

## What's wanted

Shift+Click extends the selection from the **last selected photo** to the newly clicked one,
selecting every photo in between (in the grid's current display order — `state.photos`, which
follows the active sort/filter). Plain click and Ctrl/Cmd+Click keep today's single-toggle
behavior.

## Design notes (need deciding before implementing)

- **What sets the anchor**: the conventional (Explorer/Finder) rule is that the anchor is the last
  *plain* click/toggle, and stays fixed across a run of Shift+Clicks (so Shift+Click, Shift+Click
  again further down extends/shrinks from the *same* original anchor, not from wherever the
  previous Shift+Click landed) — decide whether to follow that or the simpler "anchor is always
  the most recently toggled photo, full stop" rule, which is less standard but less code.
- **First Shift+Click with nothing selected yet**: no anchor exists — falls back to a plain single
  toggle of the clicked photo (which then becomes the anchor for the next Shift+Click).
  **Ordering**: range is computed over the currently-known order in `state.photos`. Since
  `loadRest` (app.js/grid.js) appends further pages asynchronously, a Shift+Click whose anchor or
  target hasn't loaded yet (`state.loaded < state.total`) is a real edge case — decide whether to
  wait for the rest of the folder to load first, or only operate on what's currently in
  `state.photos`.
- **Range selection semantics**: does Shift+Click *add* the range to the existing selection
  (union), or replace the selection with just the new range? Standard behavior is to replace,
  except when the anchor itself is not deselected by an in-between Ctrl+Click — likely out of
  scope here; recommend starting with "replace selection with the anchor..clicked range" and
  revisiting if the user wants Ctrl+Shift combos later.
- **Anchor reset points**: `loadFolder` and any place that already calls `state.selected.clear()`
  (folder navigation, filter/sort change, Escape, the selection-bar's Clear button, `toggleSelecting`
  turning selection mode off) should also clear the anchor, so a stale anchor from a previous
  folder/filter never leaks into a new Shift+Click.
- **The ✓ button**: decide whether Shift-clicking the check button (as opposed to the cell itself)
  should also trigger range selection — likely yes, for consistency, since the event carries the
  same `shiftKey` flag; just needs its `onclick` to stop special-casing itself out of the shared
  logic.
