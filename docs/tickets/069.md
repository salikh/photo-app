## Observation

While doing the culling trial for ticket 031, the user noted: "No issues so far, except when accessing a folder
for the first time, but that is likely a different problem." Not otherwise reproduced or measured yet — this
ticket is to look into it, not a confirmed bug.

## Likely causes to check (roughly in order of likelihood)

1. **Cold thumbnails.** The first time a folder's photos are viewed, every `Thumb` the grid needs is rendered
   on demand (`thumbs.make`, ticket 017) instead of being already on disk. For a folder of RAW files this can
   mean dozens of `dcraw`/`rawpy` decodes back to back, each up to roughly a second (measured in ticket 007/050).
   Ticket [066](066.md) (background population) should make this go away over time for the whole library, but
   until it has worked through a given folder, opening it the first time is genuinely slower. Check: does the
   slowness the user saw match an unpopulated folder, and does it go away on a second visit?
2. **`/api/dirs` and `/api/photos` cost on a folder with many subfolders or photos.** `list_dirs` does two
   range-scan queries over `files`/`photos`; on a folder with a large subtree this could be slow on first
   access before OS/sqlite page caches are warm. Measure with `time.perf_counter()` around the route handlers on
   a real, previously-untouched folder.
3. **NAS directory listing / stat cost** the first time a directory is touched (cold NFS/SMB cache), independent
   of the app's own logic.
4. **Browser-side:** the grid requests many `Thumb` images at once on first load (no `loading="lazy"` throttling
   beyond what the browser already does); check the Network panel/timing on a real slow folder.

## Result (2026-09-23)

Measured directly against the real deployment (read-only: real DNG files under `/zoo/Pictures`, real
`library.py` queries against the live server's own database opened `mode=ro`; nothing was written to
`/zoo/Thumbs`, no sidecar, and the live server itself was never touched).

**Cause #1 (cold thumbnail rendering) confirmed and quantified** — `previews.embedded_preview` on 12 real
DNG files:
- Cold (first read): 103–4580 ms, several in the 1–4.5 s range
- Same files, second read (OS page cache warm): consistently 77–142 ms, avg 98 ms

That "warm" number is itself ~5x slower than `docs/design/thumbnails.md`'s existing "~0.02s" claim for an
embedded-preview extract — that number appears stale/optimistic for this machine's actual hardware (see
below) and should not be trusted as a current baseline. With `/img/{size}/{file_id}`'s existing cap of 3
concurrent on-demand renders (`render_slots`, `api.py`), a newly-opened folder of, say, 20–40 RAW files with
no cached thumbnails yet plausibly costs several seconds to tens of seconds before the grid finishes filling
in, worse under load (see below) — this matches the user's original observation well.

**Cause #2 (`/api/dirs`/`/api/photos` query cost) ruled out** — timed directly against the real database
(13,216-file `2019`, a 500-photo subfolder, `2022`): `list_dirs` 18–42 ms, `list_photos` 39–60 ms,
`filter_counts` 18–20 ms. The range-scan queries on `files.path`'s index are not the bottleneck.

**Cause #3 needs a correction, not just a check**: `/zoo` is **not** NAS-mounted, despite that being the
consistent assumption across this repo's docs and several earlier tickets (007, 027, 048's write-ups, which
are left as-is — point-in-time records). Verified on the running deployment: `mount`/`findmnt` show `/zoo`
as a local `zfs` filesystem, and `zpool status zoo` shows it is two local SATA HDDs
(`ata-ST4000DM004-2CV104...`, `ata-ST8000DM004-2U9188...`) in a mirror — physically attached, not a NAS.
The slowness is real, just from a different mechanism than assumed: ZFS overhead plus mechanical HDD seek
latency across large (20–30 MB) RAW files, not network round-trips. Corrected the two *living* docs that
asserted "NAS" as a current fact (`docs/operations.md`'s `--scan_workers` row, `docs/design/scanning.md`)
without touching the measured numbers in either (both still hold) or rewriting historical ticket logs.
Also worth noting: the machine was under real, unrelated load while measuring (other users active, load
average up to ~5), which plausibly explains some of the multi-second cold outliers — the underlying
mechanism (cold-cache disk latency) is the same either way, just worse than a fully idle machine would show.

**Cause #4 (browser eagerness) ruled out** — the grid's `<img>` already has `loading="lazy"` (`grid.js`), so
the browser already only fetches near-viewport thumbnails, not the whole folder at once.

**Conclusion**: cold-thumbnail rendering is confirmed as the cause, at a magnitude that matches what the user
felt. Ticket 073 (built earlier in this session) already improves this over time — a folder the load-adaptive
worker's background walk has reached will have its thumbnails ready before anyone opens it — but it walks in
path order with no notion of "prioritize what's currently being looked at," so a folder it hasn't reached yet
is still exactly this slow on first open. That prioritization is real, separate scope (coordinating the
on-demand render path with the background queue's ordering), not something to bolt on here, so it's filed as
its own ticket: [080](080.md).
