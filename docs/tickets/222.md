## What's wanted (as given)

"Implement non-destructive editing for JPGs too. There will be some edit settings that can be applied
to JPG non-destructively, i.e. the original JPG is untouched, the database gets new edit settings
stored along the file, and the thumbnail generation pipeline gets the code to apply the edits (and
bake them into generated thumbnails, so there is no transformation to compute when showing images in
the app). It may be a subject of research whether the edits can be applied in the canvas on the
client browser, instead of recomputing the thumbnails. Another subject of research is which
particular settings can be implemented. I'm thinking of brightness, contrast, levels (standard
3-tick slider) — monochrome, and per RGB channel. Also unsharp mask. The key factor on whether to
include is whether usefulness justifies the wait time, i.e. cheap transformations are okay, and
expensive transformations are only okay if they are very useful."

## Shape (detail in the children)

- **Same architecture as RAW tuning**: per-file settings stored on `files`, NULL/absent = default; a
  file at default takes exactly today's path (no cost, no behaviour change); a tuned file is rendered
  by `thumbs` with the edits baked into every cached size, so showing an image never computes
  anything; provisional (unsaved) edits render to memory only, like `raw_preview` (094), and Save
  commits (`thumb_rev` bump, thumbnails cleared).
- **Research done in this epic's filing** (numbers in 223/224): every point-wise edit (brightness,
  contrast, levels/gamma, per-channel levels, monochrome) is a lookup table: ~5 ms at Medium, ~50 ms
  at full 24 MP on this machine, i.e. free. Unsharp mask is the only expensive one (~1 s at full
  size, ~100 ms at Medium, ~27 ms at Small, 2 ms at Thumb) and is *cheap everywhere except Huge*.
  Client-side canvas is 10x slower than server Pillow here (software-rendered headless Chrome), so
  it is not needed for the cheap edits and is only a possible later optimisation for live preview.
- **Out of scope for the first version**: curves, local adjustments (highlights/shadows, clarity),
  noise reduction, vignette, arbitrary-angle straighten (all either expensive or UI-heavy for
  little gain), writing the edits into XMP sidecars (crop and rotation are not either), RAW files
  (they keep their own pipeline; the edit stage is built so a later ticket can reuse it).
