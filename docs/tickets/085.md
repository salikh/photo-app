Add per-file dcraw processing settings (columns + UI sliders on the Files detail view), and
regenerate a DNG's thumbnails when they change.

## Read this before scoping the work: dcraw is not the only RAW path, and it matters which one

This app has **two separate, deliberately different RAW rendering paths**
(`docs/design/thumbnails.md`), and only one of them uses `dcraw` at all:

- **On-demand** (`photoapp/previews.py`, what actually serves `/img/...` most of the time): uses
  `rawpy`/LibRaw, a Python library — no `dcraw` involved.
- **Background bulk population** (`photoapp/thumb_populate.py`, ticket 066): uses the external
  `dcraw` binary, by explicit original-plan request. This is the only place `dcraw` settings would
  apply.

Two consequences that change what "regenerate the DNG thumbnails on changes to dcraw settings"
can actually mean:

1. **`Thumb` (`extract_embedded_thumb`, `dcraw -e -c`) extracts the camera's own already-baked
   embedded JPEG** — dcraw demosaic settings (white balance, brightness, quality) have **no
   effect** on it, because nothing is being demosaiced. Adjustable settings can only meaningfully
   affect `Small`/`Medium`/`Huge` (`render_dcraw`, the actual `-c -w [-h | -q 3]` demosaic calls).
   A slider that appears to do nothing to the grid thumbnail (usually `Thumb`) will confuse
   someone unless this is designed for and explained in the UI from the start.
2. **The size a viewer actually sees most often comes from the on-demand/`rawpy` path, not
   `dcraw`** (`docs/design/thumbnails.md`: "most requests never touch the job queue"). A dcraw
   setting change would regenerate the *background-populated* cache, but the *next on-demand
   render* (e.g. after ticket 079's cache-clear-and-reload, or after the file is later evicted and
   re-requested) would go through `rawpy` again and ignore it entirely, unless this ticket also
   threads equivalent parameters through `previews.render`'s `raw.postprocess(...)` call (LibRaw
   supports similar knobs: exposure, highlight recovery, white balance). **This is the central
   scope decision, not a detail**: does "dcraw settings" mean *only* the background/dcraw path
   (simpler, but the visible effect is inconsistent and delayed), or does it mean per-file RAW
   processing parameters that both paths honor (more work, but coherent: what you dial in is what
   you actually see)? **This is now [question 090](090.md); this ticket is blocked on its
   answer.**

## Other design notes

- **Which settings (decided)**: three, each with a direct dcraw flag and a LibRaw `postprocess()`
  equivalent — the shortlist holds regardless of how 090 is answered: brightness (`-b`; LibRaw
  `bright`), white balance mode — camera / auto / manual multipliers (`-w` / `-a` / `-r`; LibRaw
  `use_camera_wb` / `use_auto_wb` / `user_wb`), highlight recovery (`-H 0-9`; LibRaw
  `highlight_mode`). Quality/interpolation (`-q`) stays out of scope — it's already size-dependent,
  not a per-file creative choice. White balance mode is a choice, not a continuous value, so its
  control is a segmented/radio control, not a slider; brightness and highlight recovery are the
  two that are actually sliders.
- **Storage**: new columns, almost certainly on `files` (a DNG's processing choice is per
  rendition, matching ticket 083's per-file metadata reasoning) — nullable, absent meaning
  "current hardcoded defaults."
- **Regeneration mechanism**: reuse ticket 079's `thumbs.clear` (delete the cached file + `thumbs`
  row, let the next request regenerate) rather than inventing a second "wipe and redo" path — a
  settings change is conceptually the same operation as "this thumbnail needs a fresh render,"
  just triggered by a slider instead of a broken-image report.
- **Requires `dcraw` to be installed** for the background path specifically
  (`thumb_populate.dcraw_available()`) — decide how the sliders behave when it is not (hidden,
  disabled with an explanation, or fine because only the on-demand/rawpy path is actually used in
  that case, if the central scope decision above chooses to unify both paths).
