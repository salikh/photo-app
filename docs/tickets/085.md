Add per-file RAW conversion settings (columns + UI sliders on the Files detail view), and
regenerate a DNG's thumbnails when they change. Per [090](090.md)'s resolution, this ticket also
carries out the prerequisite refactor: merge the on-demand (`previews.py`, `rawpy`/LibRaw) and
background (`thumb_populate.py`, external `dcraw`) RAW renderers into one, so a setting change has
the same, consistent effect regardless of which path renders a given file+size first.

## Decided scope (per 090's resolution — read this before starting)

- **One renderer, not two**: `thumb_populate.py` stops shelling out to `dcraw` for `Small`/
  `Medium`/`Huge` and calls the same `rawpy`-based render function `previews.py` uses, parameterized
  by the per-file settings below. The external `dcraw` binary is no longer required by this app for
  the settings ticket 085 originally scoped (all three have direct `rawpy` equivalents); keep it
  only as a documented fallback hook for some *future* setting that turns out to need a
  `dcraw`-only capability — not exercised by anything this ticket implements.
- **Background/online parity**: both paths look up and apply the same per-file settings row. A
  photo's `Small`/`Medium`/`Huge` thumbnail must render identically whether it was produced by an
  on-demand request or the background populator — no path may apply defaults where the other would
  apply a tuned setting.
- **Embedded-preview shortcut vs. demosaic, for every size (clarified 2026-09-23 during
  implementation — see below)**: `docs/design/thumbnails.md` turned out to already contradict this
  ticket's original framing before 090 was even asked: the *current on-demand path*
  (`previews.embedded_preview`, via `thumbs._open`) already uses the camera's own baked embedded
  JPEG — no demosaic, ~20ms — for **every** size (`Thumb`/`Small`/`Medium`/`Huge`) whenever a usable
  one exists, not just `Thumb`. Only a RAW with *no* usable embedded preview falls back to a real
  LibRaw demosaic (~0.7-1s), via the separate `raw_render` job queue. This matters because settings
  like brightness/WB/highlight-recovery have **no effect** on an embedded-preview render (nothing is
  being demosaiced) — so making them do anything for the common case requires deciding, for every
  size, when to stop taking that shortcut. Asked and resolved (recommended option, chosen): the
  shortcut stays available for **every** size, not just `Thumb`, as long as that file's settings are
  at default — the exact same rule, just no longer `Thumb`-only:
  - Used when *both* (a) every setting for this file is at default and (b) no cached file of that
    size exists yet for it (a true first render).
  - Once either is false — settings have been tuned, or a cached render already exists from
    earlier — that size goes through a real demosaic (`rawpy`/LibRaw `postprocess()`) and reflects
    the tuned settings, same as the others.
  - This keeps today's browsing speed for untouched RAW photos (the common case) unchanged, and
    only pays the demosaic cost once someone actually tunes a file's settings or forces a
    regeneration (ticket 079).
- **Which settings**: three, each with a direct dcraw flag (now unused) and its `rawpy`
  `postprocess()` equivalent: brightness (LibRaw `bright`), white balance mode — camera / auto /
  manual multipliers (LibRaw `use_camera_wb` / `use_auto_wb` / `user_wb`), highlight recovery
  (LibRaw `highlight_mode`). White balance mode is a choice, not a continuous value, so its control
  is a segmented/radio control, not a slider; brightness and highlight recovery are the two that
  are actually sliders.
- **Storage**: new columns, almost certainly on `files` (a DNG's processing choice is per
  rendition, matching ticket 083's per-file metadata reasoning) — nullable, absent meaning
  "current hardcoded defaults" (i.e. "at default" for the `Thumb` rule above is "these columns are
  all null/unset", not merely "equal to some numeric default").
- **Regeneration mechanism**: reuse ticket 079's `thumbs.clear` (delete the cached file + `thumbs`
  row, let the next request regenerate) for every affected size, including `Thumb` once the revised
  rule above says it should go through raw conversion — a settings change is conceptually the same
  operation as "this thumbnail needs a fresh render," just triggered by a slider instead of a
  broken-image report.
