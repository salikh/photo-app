# 135: Compare a target copy's catalog against this machine; four-way report

- Type: task
- Status: done
- Depends on: [133](133.md) (the relocated/consolidated catalog tool), [134](134.md) (this
  machine's export)
- Related: [131](131.md) (epic), [137](137.md) (acts on this report)
- Refs: [133](133.md)'s `catalog.py` (hash_dir.py, relocated) and `import_sha224sum.py`'s bridge
  format, `nas.txt`/`filenames.txt` (real pre-existing catalogs this should be able to read
  directly, not just catalogs the new tool built itself)

## What's wanted

A tool that takes:
- this machine's export from [134](134.md) (catalog + decisions), and
- a target copy's catalog: either built fresh with [133](133.md)'s tool against a mounted backup
  (incremental — only changed files are re-hashed on a re-run), or an already-existing catalog
  file (`hash_dir.py`-format sqlite, or a plain `sha224sum` listing via `import_sha224sum.py`, or
  `nas.txt`) if one is at hand,

and classifies every hash on the target copy into exactly one of:

1. **already have it** — the hash is in this machine's live catalog (regardless of path: a rename
   on either side is not a difference worth reporting; ticket 128 already established that a path
   is not identity, a hash is).
2. **already handled** — the hash is not in the live catalog, but *is* in the decisions export
   with `rating == -1` (rejected). Expected absence; not a problem.
3. **lost** — the hash is not in the live catalog, and the decisions export has it with
   `rating != -1` or `fav` set (it was a keeper here at some point) — or has no decision for it at
   all but *does* appear as `missing` in a stale copy of the live catalog (edge case: worth a
   decision on how strict to be here, see [136](136.md) if it turns out to need one). Recoverable
   from the target copy — this is the "went missing some other way than a deliberate reject" case
   the ticket asks to be able to find.
4. **never seen** — the hash is in neither the live catalog nor the decisions export. Genuinely
   new content this repo has never had an opinion on.

Also report the reverse direction on request (a flag): hashes in the live catalog absent from the
target copy — useful for checking whether an old backup is safe to retire (everything on it is
either superseded or was never worth keeping), not for finding anything to import.

Output: a plain, greppable report (counts per bucket up top, then one line per file: bucket, path
on the target copy, hash) — this ticket is read-only and does not move or copy anything; see
[137](137.md) for acting on it.

## Done (2026-09-27)

- `tools/archive/compare.py`: `--live` (a [134](134.md) export) + `--target_db` (a
  [133](133.md) `catalog.py`/`import_sha224sum.py` database) -> a plain, greppable, tab-separated
  report to stdout, with per-bucket counts up top. `--reverse` answers the opposite question
  (which live hashes are absent from the target copy at all), for checking whether a backup is
  safe to retire.
- Classification priority is `have` first, regardless of what a decision says -- confirmed with a
  test (a hash that is both live and has a stale reject decision on record is `have`, not
  `rejected`): the live library is authoritative over anything a past decision says. A
  rating-0-but-favorited decision is still `lost`, not `new` -- `remember_photo` (recovery.py)
  only skips writing rating_by_hash when *both* rating is 0 and fav is unset, so a fav-only
  decision is real and durable too.
- Verified against real output end to end (not just synthetic test data): a real library scanned
  with `photoapp.scan`, one photo rejected and trashed, exported with `photoapp.export_catalog`,
  compared against a real `tools/archive/catalog.py` catalog of a second directory tree
  containing the kept file, the (elsewhere-undeleted) rejected file, and a brand-new file --
  classified as `have`/`rejected`/`new` correctly.
- `tests/test_archive_compare.py`: subprocess-only (like [133](133.md)'s tests) -- importing
  `compare.py` directly registers its *required* `--live`/`--target_db` flags into the global
  `absl.flags.FLAGS`, which broke an unrelated `tests/test_config.py` test the moment both were
  loaded in the same pytest process (any later `FLAGS(argv)` call anywhere validates *every*
  registered required flag, not just the flags of the module that called it). Documented as the
  reason in the test file itself so it isn't rediscovered the hard way in [137](137.md)'s tests.
  `compare.py` deliberately has no `--output` flag (unlike [134](134.md)'s `export_catalog.py`) --
  partly to match `find_empty_dirs.py`'s existing stdout-only convention, partly because giving
  every archive tool an `--output` flag of the same name is exactly the kind of collision that bit
  the test suite here once already.
- Full non-e2e suite: 399 passed, 9 skipped (was 395 after [134](134.md); +4 from this ticket).
