## What's wanted (user request 2026-09-25)

Two new tunable parameters alongside today's brightness/white-balance/highlight-recovery:

- **Exposure**: a stops-like brightness correction applied before highlight recovery, distinct
  from the existing `bright` (a post-demosaic multiplier). Both `rawpy.postprocess()` and
  LibRaw-Wasm expose this natively and identically in shape: rawpy's `exp_shift`/
  `exp_preserve_highlights`, LibRaw-Wasm's `expShift`/`expCorrec`/`expPreser` (see the vendored
  `index.d.ts`) — same underlying LibRaw C API parameters (`params.exp_shift`, `.exp_preser`,
  `.exp_correc`), confirmed by reading both bindings' signatures directly (`rawpy.Params.__init__`,
  the vendored `LibRawSettings` type). Low technique risk: this is a well-defined, already-shared
  control on both sides, not something needing an invented mechanism.
- **Shadow-pull correction**: lifting shadow detail (a Lightroom/Camera-Raw-style "Shadows"
  slider), which is *not* a single native LibRaw parameter on either binding — LibRaw has no
  dedicated shadow-recovery algorithm. The closest native mechanism on both sides is the output
  tone curve's toe slope: rawpy's `gamma: (power, slope)` and LibRaw-Wasm's `gamm: [power,
  toeSlope]` are the same shape (both wrap `params.gamm[0]`/`gamm[1]`) — lowering the toe slope
  brightens shadows without necessarily needing a custom post-decode curve. This is a real
  technique decision, not yet validated against a real RAW file the way ticket 106 validated
  brightness/WB/highlight; worth the same kind of side-by-side check before treating it as settled
  (a naive toe-slope change could also shift midtones/overall contrast in a way a "Shadows" control
  shouldn't). An alternative worth weighing if the toe-slope feel is wrong in practice: a genuine
  post-decode tone curve applied to the demosaiced RGB output on both sides (more control, more
  code to keep in sync between the client canvas path and the server `previews.py` path).

## Scope note

This directly extends what [106](106.md) deliberately did *not* do ("restrict to today's four,"
not "extend") — adding these means: a `raw_settings` schema migration (two more nullable
columns), `_postprocess_kwargs`/`rawTuning.js`'s `mapSettings` updated in lockstep (106's drift-risk
lesson applies here too — verify with a real RAW file, not just docs), `raw_preview`'s query params
extended (kept as 105's fallback path) and `RawSettingsBody`/`set_raw_settings` accepting the new
fields, and two more slider controls in `renderRawSettingsBody`.
