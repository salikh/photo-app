# 233: Rescan becomes a job with elevated priority

- Type: task
- Status: done
- Priority: user request 2026-10-12
- Related: [076](076.md) (nightly scan as `scan_dir` jobs; left the manual Rescan out so it would
  start immediately), [140](140.md) (the separate "Scan:" status line this removes the need for),
  [073](073.md) (load-adaptive worker)

## What's wanted

"Change rescan into a type of job with elevated priority, and worker then should start when either
machine is idle enough, or when jobs with elevated priority exist. If an elevated job fails, make
sure it is not stuck in the rerun queue forever."

## Design

- `jobs.priority INTEGER NOT NULL DEFAULT 0` (migration, appended). `enqueue(..., priority=0)`;
  enqueueing a duplicate of a still-queued job with a higher priority raises the existing job's
  priority instead of adding a row. Claim order: priority, then the queue's usual order.
- New job kind `rescan` (target = directory, `options.recursive`), priority 1, enqueued by
  `POST /api/scan` and by the empty-database first scan. Its handler runs `scan_all` / `scan`, and
  fills the live `Progress` that `/api/jobs`'s `scan` key and `/api/scan/status` still report.
- Elevated jobs run on an **elevated worker thread** of the background queue: normal CPU/I/O
  priority (the regular worker is nice 19 / ionice idle, which cannot be undone per job), started
  as soon as an elevated job is enqueued (or is found queued at startup) regardless of machine
  load. The load-adaptive worker keeps governing only priority-0 work, so a rescan never waits for
  the machine to be idle, and the idle-time worker can stop while a rescan runs.
- **Failure never loops**: a failing elevated job ends `failed` (never put back to `queued`);
  `JobQueue.start()` (called on every idle transition) only requeues priority-0 jobs; a rescan
  still `running` when the app restarts is marked `failed` ("interrupted by restart") rather than
  re-run, so a scan that crashes the process cannot crash-loop it. The user just clicks Rescan again
  (dedupe only looks at queued/running jobs).
- `ScanManager` is replaced by a thin `RescanClient` (`start`, `wait`, `progress`), same call shape.
