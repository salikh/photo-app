# 123: Dot-tags unhide hidden directories and imply tag from directory name

- Type: enhancement
- Status: done
- Related: [054](054.md) (hiding dot-named folders), [087](087.md) (tag filter), [122](122.md) (free option in "filter by tag")
- Refs: `photoapp/library.py` (`_dir_condition`, `filter_condition`, `tags_in_view`), `photoapp/scan.py`, `photoapp/static/filters.js` (`matches`)

## Description

By default (ticket [054](054.md)), directories starting with `.` (such as `.picasaoriginals`, `.thumbnails`,
`.webaxs`, etc.) are hidden from the folder view chips and omitted from recursive photo listings and
counts (`_dir_condition` excludes path segments matching `.dir/%` or `%/.dir/%`).

When filtering by a tag that starts with a dot (`tag:.<name>`):
1. **Unhiding hidden directories**: Scanning/querying matching files should include the dot-starting
   hidden directories rather than filtering them out.
2. **Implied tags from directory name**: Files residing inside a hidden directory (e.g.
   `.../.picasaoriginals/...`) must be assumed to have the tag equal to the hidden directory name
   (e.g. `.picasaoriginals`), even if that tag is not explicitly written into the file's XMP sidecar
   or the database `tags` table.

This works together with ticket [122](122.md): because hidden directories are excluded from default
views, their dot-tags will not appear in the initial "aspects" list populated from the current view.
Ticket [122](122.md)'s free-form tag input provides the mechanism for users to type and filter by any
dot-tag (e.g. `.picasaoriginals`), triggering this unhide-and-match behavior.

## Design Details

- **Tag-based Unhiding in Queries**:
  - In `library.py`, when the active filter is a dot-tag (`tag:.*`), `_dir_condition` (or the query's
    scope condition) should not suppress dot-directories.
  - Subtree/recursive scans and searches for dot-tags should examine photos within the relevant
    hidden directories.
- **Virtual / Implied Directory Tags**:
  - For files under a directory starting with `.` (e.g. `foo/.bar/baz.jpg`), the directory name (`.bar`)
    acts as an implicit tag.
  - In `library.filter_condition` (SQL): match either explicit records in `tags` or check if the photo's
    path contains the hidden directory segment (`rf.path LIKE ? || '/%' OR rf.path LIKE '%/' || ? || '/%'`).
  - In frontend `filters.matches` (JS): mirror this logic so photos in the view or loupe matching the
    implicit directory tag pass filter tests.
  - Photo details (`photo_detail` and list responses) should surface implicit directory tags alongside
    explicit sidecar tags so the UI displays them.
- **Interaction with Aspects (Ticket 122)**:
  - Once a dot-tag filter is applied (via ticket 122's free-form input), `tags_in_view` for that filtered
    view can also reflect the tags present within those unhidden directories.

## Outcome

Landed. `library.implied_tags(path)` returns the dot-prefixed directory names in a file's path;
`filter_condition`'s `tag:NAME` branch ORs the explicit `tags` lookup with a path-segment match when
NAME starts with a dot (`instr('/' || rf.path || '/', '/' || ? || '/')`); and
`_scope_condition(rel_dir, recursive, include_hidden)` drops ticket 054's dot-directory exclusion when
`list_photos`' filter is a dot-tag (`_is_dot_tag`). `_photo_json` and `photo_detail` return an
`implied` list, and `filters.matches` accepts an implied tag as a match, so the loupe's leave/advance
logic agrees with the server; the HUD shows implied tags in a dashed, italic style. No scan change was
needed (hidden directories were already scanned; only the views excluded them). Tests: a
`test_library_api.py` case (default view still hides the dot dir, `tag:.name` finds and matches the
implied tag, explicit same-named tags match too, and `implied` is in the list/detail payload) and an
e2e driving ticket 122's input to filter by a dot-tag and asserting the hidden photo and its implied
HUD tag.
