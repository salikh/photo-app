# 232: Remember the Google Photos albums in the database instead of listing them from Google

- Type: task
- Status: done
- Priority: user request 2026-10-11
- Parent: [205](205.md)
- Related: [231](231.md) (the ~15 s listing this replaces), [213](213.md)

## What's wanted

"Instead of cache in memory, perhaps store the list of the albums that this app uploaded to into the
db table, and populate from there?"

## Design

- Table `gphotos_albums(id, title, item_count, last_used, synced_at)` (migration; module
  `photoapp/gphotos_albums.py`). **Every upload job records its album** (created or existing) and how
  many items went in, so the table fills itself; at startup `backfill_from_jobs` adds albums earlier
  upload jobs used (their rows still hold the id and title), with no Google call.
- `GET /api/gphotos/albums?name=` reads the table only (ranked as before) — instant, **never contacts
  Google**; it also reports `loading`, `error`, `synced_at`. The in-memory cache, the TTL and the
  warm-up on dialog open from 231 are gone.
- `POST /api/gphotos/albums/refresh` is the **only** place the album list is fetched from Google
  (~12 requests, ~15 s, background thread), syncing the table with it: adds albums made before the
  table existed, updates titles/counts, forgets albums deleted on Google. The dialog has a
  "Refresh from Google" button for it; while it runs the dialog polls the local server.
- Trade-off accepted: the table can drift from Google (an album renamed or deleted there stays
  until a refresh; a failed add to a deleted album shows in the upload job's note). This reverses
  `docs/design/google-photos.md`'s "no album bookkeeping" — updated there.
