# 147: "Move to folder" button and modal

- Type: task
- Status: done
- Priority: user request 2026-09-29
- Related: Epic [144](144.md); [145](145.md) (`POST /api/move`, `GET /api/dirs/exists`, the
  endpoints this calls)
- Refs: `photoapp/static/export.js` (the modal pattern this closely follows), `photoapp/static/
  grid.js` (`renderSelectionBar`, `removePhotos`, `batchRate`'s `enqueue()` wrapping)

## What's wanted

Item 1 of epic 144: in the selection bar (shown whenever photos are selected), a "Move to folder"
button opens a modal with a folder-name input preselected with the current folder; on confirm, if
the typed folder doesn't exist, a second modal confirms creating it before anything happens.

## Design

- New module `photoapp/static/move.js`, structured like `export.js`'s `open(ids)`/modal pair (not
  folded into `grid.js`, which is already large) — `open(ids)` builds the first modal: an
  `<input>` prefilled with `state.route.dir` (matching export.js's own default-then-`select()`
  pattern) and a "Move N photo(s)" confirm button.
- On confirm: `GET /api/dirs/exists?dir=<input value>`. If `exists`, proceed straight to `POST
  /api/move`. If not, replace the modal with a second one: "Folder '<target>' doesn't exist —
  create it?" (Cancel / Create and move); confirming that calls `POST /api/move` (which always
  creates the directory server-side, per ticket 145 — the frontend's confirm is the only gate, the
  server doesn't re-ask).
- On a successful move: `grid.removePhotos` the moved Photo objects (found via `state.photos`,
  matching `batchRate`'s own `state.photos.find`), `grid.clearSelection()`, and a toast summarizing
  how many moved / failed, pointing at the Jobs page for the rescan's progress (matching
  `export.js`'s "see the Jobs page for progress" wording) — no undo offered (epic 144 is explicit
  that this isn't wired into `state.undoStack`).
- `grid.js`: new "Move to folder" button in `renderSelectionBar`, next to "Delete" — shown
  whenever `n > 0` (unlike Delete, not gated to the rejected filter), wired to `move.open(ids,
  removePhotos, clearSelection)`.
- **Revised while implementing**: `move.js` does not import `grid.js` at all (unlike `export.js`,
  which the button in the *header*, not the selection bar, can afford to) — the button living in
  `grid.js`'s own `renderSelectionBar` means `grid.js -> move.js -> grid.js` would be a circular
  import. `open()` instead takes `removePhotos`/`clearSelection` as parameters, passed in by
  `grid.js` itself at the one call site. Also: `export.js` itself does not wrap its own flow in
  `enqueue()` either (checked before assuming it should) — `move.js` follows that same precedent,
  not the separate `batchRate` one.

## Outcome

Landed. `photoapp/static/move.js`: `open(ids, removePhotos, clearSelection)` builds the first
modal (input preselected with `state.route.dir`, `select()`ed); on confirm, `GET
/api/dirs/exists` decides whether to go straight to `POST /api/move` or show the create-folder
confirm modal first. A successful move calls `removePhotos` only for Photos that actually moved
(a Photo already in the target directory is a no-op the caller must not remove from view) and
`clearSelection`, then toasts a summary pointing at the Jobs page. `grid.js` wires a new "Move to
folder" button (shown whenever anything is selected, unlike Delete) to it. Three new e2e tests:
move to an existing folder, the create-folder confirm flow, and cancelling it leaves everything
untouched. All pass; a broader selection/export/delete e2e sweep run afterward to check the new
`grid.js` import didn't regress anything else.
