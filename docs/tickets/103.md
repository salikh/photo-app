# 103: Question — how should the lossy tuning-preview DNG be produced?

- Type: question
- Status: done
- Related: [102](102.md) (epic)
- Blocks: [104](104.md), [105](105.md), [106](106.md)
- Refs: `photoapp/previews.py` (rawpy/LibRaw wrapper — read-only; rawpy has no DNG-writing API),
  `photoapp/thumbs.py` (the existing per-size cache pattern — `thumb_path`, `_record`, the
  `thumbs` table — a plausible template for *where* a generated lossy DNG would be tracked,
  independent of *how* it gets made)

## Context

[104](104.md) needs to turn an original RAW file into a smaller, lossy-compressed DNG that
LibRaw-Wasm can still open and tune from scratch (i.e. still real, undemosaiced Bayer data — not
a pre-demosaiced preview, which would freeze white balance/highlight-recovery decisions the whole
point of this epic is to keep adjustable). `rawpy`/LibRaw (this project's only RAW dependency,
since 090) is **read-only** — it has no API to *write* a DNG, lossy or otherwise. Producing one
needs either a new dependency/tool or a different technique entirely, and this project has so far
treated "add a new external dependency" as something to check with the user first (ticket 100
deliberately avoided adding `imagehash` for exactly this reason).

## The question

How should [104](104.md) actually produce the lossy tuning-preview DNG? Options to weigh (not
exhaustive — options the user may already have a preference among, or another one entirely):

- **A. Adobe's DNG SDK** (C++, the reference implementation of DNG's own lossy-JPEG-compressed
  raw-plane format) — the "correct" DNG-native lossy compression, but a new, fairly heavy
  dependency with a real build story (no pip package; would need a Python binding or a subprocess
  wrapper around a compiled tool).
- **B. A downsampled *linear* DNG** (demosaiced once server-side at reduced resolution, repacked
  as DNG) — much easier to produce (rawpy can demosaic; something would still need to *write* the
  DNG container), but this bakes in the demosaic and loses per-pixel Bayer data, which may take
  white-balance/highlight-recovery tuning further from "real" than the epic wants — needs
  checking against what LibRaw-Wasm actually does with a linear vs. raw DNG.
- **C. A downsampled *mosaiced* DNG** (still raw Bayer data, just fewer pixels and/or a simpler,
  non-DNG-native lossy encoding of the raw plane) — keeps real per-pixel tuning but "lossy DNG" is
  then a slight misnomer (lossy mainly via resolution reduction, not DNG's own compression); still
  needs something capable of writing a valid DNG container.
- **D. Skip DNG entirely for the preview** — have LibRaw-Wasm read the *original* file directly
  but at reduced output size (`open()`'s "size reduction" setting, per its docs) instead of a
  server-generated intermediate file at all; simplest (no new writer, no new cache artifact), but
  means transferring the *original* file's full bytes to the browser regardless of its size, which
  is exactly what this epic's "not the full original DNG, too large/slow" framing wanted to avoid
  — worth confirming whether LibRaw-Wasm's size reduction actually saves transfer bytes (it likely
  only reduces *decoded* output size, not download size) before ruling this out or back in.

## Answer

The user's initial lean was Option B, on the condition of checking what LibRaw-Wasm actually
supports first. That check (LibRaw-Wasm 1.6.0's published `dist/index.d.ts` and `worker.js`,
read directly from the npm package via jsdelivr/unpkg) rules B back out and settles on a variant
of **C**:

- LibRaw-Wasm's `open(bytes, settings)` runs LibRaw's own demosaic/white-balance/highlight-recovery
  pipeline on whatever it's given; `imageData()` (the demosaiced result) and `rawImageData()` (the
  raw mosaic) are separate calls, and settings like `useCameraWb`/`useAutoWb`/`userMul`/`highlight`/
  `noInterpolation` only do anything meaningful against real, undemosaiced Bayer input. Feeding it
  Option B's pre-demosaiced linear DNG would make most of the tuning UI's controls inert against the
  *local* preview (defeating 105/106's point) even though the same settings still work correctly
  server-side at Save time against the real original — confirms the concern already raised against B
  in the options list above, this time from the library's own documented settings surface rather
  than by inference.
- `halfSize` (`-h`) is a *decode-output* flag applied inside `open()`/`imageData()` — the whole input
  buffer must already be in the browser before any setting takes effect. This confirms Option D's
  standing worry: skipping the DNG and reading the original directly would still transfer the full
  original file's bytes, the exact thing this epic exists to avoid.
- Option A (Adobe DNG SDK) is now unnecessary: rawpy already exposes everything a synthetic DNG
  needs (`raw_image`/`raw_image_visible` for the mosaic, `raw_pattern`/`color_desc` for the CFA
  layout, `black_level_per_channel`, `white_level`, `camera_whitebalance`, `rgb_xyz_matrix`) and
  [tifffile](https://github.com/cgohlke/tifffile) (pure Python + numpy, pip-installable, no build
  step, ~250KB wheel) can write those as DNG tags via `extratags` — confirmed practical elsewhere
  (e.g. the `makeDNG` tool, and Image.sc's CFA-DNG-via-tifffile discussions). This is a genuinely new
  dependency (flagged per this project's convention, matching ticket 100's imagehash caution) but by
  far the lightest of the options that can actually write a DNG, so **`tifffile` is added** (see
  `requirements.txt`).

**Decision for [104](104.md): a downsampled, still-mosaiced DNG**, built by `rawpy` (read the raw
Bayer plane + the camera metadata a DNG reader needs) piped through 2×2-block Bayer-preserving
binning (average each of the 4 same-color pixels across each 2×2-of-2×2 block, halving both
dimensions per binning pass while keeping the CFA pattern intact and periodic) down to a size cap,
then written out via `tifffile`'s DNG tag set (`CFARepeatPatternDim`, `CFAPattern`, `BlackLevel`,
`WhiteLevel`, `ColorMatrix1`, `AsShotNeutral`, `DNGVersion`, `UniqueCameraModel`, `Orientation`).
"Lossy" here means resolution reduction, same nuance C's own description already flagged — not
DNG's own lossy-JPEG raw-plane compression (that's what A would have bought, at a much higher
dependency cost, for a preview artifact where exact colorimetric precision doesn't matter: Save
([106](106.md)) always re-renders the committed thumbnails from the real original DNG server-side).
Verified against the real LibRaw-Wasm build (not just its docs) as part of implementing 104: a
generated preview DNG for a real Pentax K-5 DNG round-trips through an actual `open()` +
`imageData()`/`rawImageData()` call in a headless-Chrome smoke test.
