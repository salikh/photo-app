## What's wanted

Replace ticket 094's `schedulePreview`/`requestPreview` (which calls `GET .../raw_preview`, a real
server-side demosaic) with an in-browser render:

- On opening the tuning UI for a RAW file, fetch [104](104.md)'s lossy DNG once (not per tick) and
  hand it to LibRaw-Wasm's `open(fileBuffer, settings)`.
- Every pending-value change re-renders via LibRaw-Wasm locally (`imageData()`) instead of
  requesting a new image from the backend — no debounce needed for the *network* (there is none),
  though LibRaw-Wasm's own decode cost may still want throttling to avoid queuing renders faster
  than they complete, especially on slower/mobile devices (this app is used on tablets — see
  [043](043.md)/[060](060.md) — worth checking actual performance there before assuming desktop
  numbers hold).
- Surface whichever of LibRaw-Wasm's parameters the tuning UI exposes as controls; today's four
  (`bright`, `wb_mode`/`wb_r`/`wb_g`/`wb_b`, `highlight`) are the floor, not necessarily the
  ceiling — see [106](106.md) for what happens to any parameter beyond those four.
- Fallback: keep ticket 094's `raw_preview` endpoint working and fall back to it when LibRaw-Wasm
  fails to load or decode (unsupported browser/WASM environment, a camera model it chokes on,
  the lossy DNG isn't available yet) — the network round trip becomes the fallback path, not
  something removed.
- The tuning UI's current home (the Files panel) may move; keep this integration decoupled from
  exactly where the controls are mounted, per the user's own note when filing this epic.
