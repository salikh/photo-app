## Problem

`catalog.py` incrementally hashes a tree this app doesn't own (a backup drive, a disk image) into
its own `--db` sqlite file, with its own from-scratch mtime-based skip-if-unchanged cache. That
cache only pays off on catalog.py's *own* second run — the very first time it catalogs a tree, it
must SHA224-hash every file, which is the expensive part (measured elsewhere: a slow NAS directory
of 800 files takes ~15 minutes to hash).

Separately, ticket 111 made `photoapp`'s own scanner write `index.json` (per directory) and
`<name>.json` (per file) next to each image — including that file's `hash` — whenever
`--write_metadata_json` is on (the default for the real app). A tree cataloged by `catalog.py` is
very often *also* a tree `photoapp` has scanned at some point (the real `pictures_dir` itself, or
an rsync/cp copy of it that carried the sidecar files along) — so these JSON files, when present,
already have the hash `catalog.py` would otherwise recompute from scratch.

The user asked for `catalog.py` to support the same `--write_metadata_json` flag: read this cache
when present and reuse its `hash` when the file's mtime still matches (skipping the hash
computation), and write it too, so the hash `catalog.py` computes becomes available to a later
`photoapp` scan of the same tree, another `catalog.py` run, or a `catalog.py` run against a synced
copy elsewhere.

## Design

- Reuse `photoapp.metacache` directly for the on-disk format (`load_records`, `write_dir`,
  `record_path`) rather than re-implementing it — `tools/archive/apply.py` already imports
  `photoapp.config` via the same `sys.path` insert (`_here`/`_repo_root`) this needs for
  `photoapp.metacache`, so this isn't a new category of coupling for this tool family.
- One flag, `--write_metadata_json` (default **off** — unlike photoapp's own scanner, this tool's
  whole premise is a tree it doesn't own; writing into it should be opt-in, not a surprise),
  governing both directions together, exactly like the app's own scanner:
  - **Read**: in `process_directory`, before hashing a file, check `metacache.load_records(dirpath)`
    for that name; if its recorded `mtime` matches `os.stat`'s and it has a non-null `hash`, reuse
    that hash instead of calling `hash_file`. (Unlike `photoapp/scan.py`'s own read path, this does
    *not* require `metacache.has_all_keys` — catalog.py only ever needs the hash, and the record was
    very likely written by `photoapp` itself with the full EXIF field set catalog.py has no use
    for either way, or is fine as-is if incomplete.)
  - **Write**: after hashing (or reusing) each file in a directory, write back `hash`/`mtime`/
    `bytesize` for that file — merged into whatever record already exists for it (`load_records`
    again, or the same dict read above), not a fresh hash-only record. This matters because
    `catalog.py` has no EXIF extraction of its own: overwriting a `photoapp`-written record with a
    hash-only one would silently regress it from "complete" to "incomplete" the next time
    `photoapp`'s own scanner considers it (`metacache.has_all_keys`), forcing a needless re-read of
    that file's metadata on the app's side. A directory's `index.json` is written once at the end of
    `process_directory` via `metacache.write_dir`, matching `photoapp/scan.py`'s own per-directory
    batching.
  - A file already skipped by `catalog.py`'s own unchanged-mtime fast path (its `--db`'s cached
    file mtime still matches) does not need a metadata_json read at all — that shortcut already
    avoids the hash computation for catalog.py's own second-and-later runs. The metadata_json read
    only matters for a file catalog.py doesn't already have a matching cached mtime for.
  - `remove_missing_files`/directory-level stale-entry cleanup are untouched (they operate on
    catalog.py's own `--db`, unrelated to the on-disk JSON cache).
