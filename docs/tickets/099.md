# 099: Import and link an exported file the moment its export job finishes

- Type: task
- Status: done
- Related: [096](096.md) (epic — see its "Architecture" section: own `Photo`, `files.
  exported_from_file_id` cross-reference), [100](100.md) (the one-off backfill this makes
  unnecessary for anything exported *after* this ticket lands)
- Refs: `photoapp/api.py` (the `export` job handler registered at `add_handler("export",
  export_job)`, ~line 153; wherever it calls `photoapp.export.export_file`), `photoapp/export.py`
  (`export_file` — returns `dest` on success), `photoapp/scan.py` (`_upsert_file`, and the per-file
  metadata extraction + `grouping.regroup` it's followed by — reuse this instead of duplicating
  it), `photoapp/db.py` (`MIGRATIONS` — new `files.exported_from_file_id` column), `photoapp/
  jobs.py` (the job row already known at this point carries the exact source `file_id` — no
  heuristics needed here, unlike [100](100.md))

Once a job's `export_file` call succeeds, the handler already knows, with certainty, both the
source `file_id` (the job's own `file_id`) and the exact destination path it just wrote (`dest`,
returned by `export_file`) — no guessing required, unlike the pre-existing backfill case
([100](100.md)).

## What this ticket does

1. Right after a successful `export_file`, insert the new file into `files` using the same
   per-file metadata extraction the scanner already does for a freshly-discovered file (dimensions,
   mtime, hash, etc. — `scan._upsert_file` plus its surrounding read step), then run
   `grouping.regroup` on just that directory so the new file gets its own `Photo` the same way any
   newly-discovered file would on a normal scan — no new grouping logic needed.
2. Set `files.exported_from_file_id = <source file_id>` on the new row (098's re-export case: if
   the row already existed at that path from an earlier export of the same source, this is a
   refresh of its metadata, not a new row).
3. On partial failure (file copied, but the DB-import step then crashes or hits a busy database):
   rely on the next full scan's normal discovery to pick the file up as a plain new, unlinked
   `Photo` — acceptable, self-healing fallback; do not add new failure-recovery machinery for this.
