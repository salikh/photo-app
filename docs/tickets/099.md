# 099: Import and link an exported file the moment its export job finishes

- Type: task
- Status: open
- Blocked by: [097](097.md), [098](098.md)
- Related: [096](096.md) (epic), [100](100.md) (the one-off backfill this makes unnecessary for
  anything exported *after* this ticket lands)
- Refs: `photoapp/api.py` (the `export` job handler registered at `add_handler("export",
  export_job)`, ~line 153; wherever it calls `photoapp.export.export_file`), `photoapp/export.py`
  (`export_file` — returns `dest` on success), `photoapp/scan.py`/`photoapp/load_worker.py`
  (single-file insert into `files`, to reuse instead of waiting for the next full scan),
  `photoapp/manual_links.py` (`link` — or, per 097's answer, whatever new mechanism replaces the
  role='export' merge), `photoapp/jobs.py` (the job row already known at this point carries the
  exact source `file_id` — no heuristics needed here, unlike [100](100.md))

Once a job's `export_file` call succeeds, the handler already knows, with certainty, both the
source `file_id` (the job's own `file_id`) and the exact destination path it just wrote (`dest`,
returned by `export_file`) — no guessing required, unlike the pre-existing backfill case
([100](100.md)).

## What this ticket does

1. Right after a successful `export_file`, insert the new file into `files` (and its `Photo`, per
   097's resolution) using the same per-file metadata extraction the scanner already does for a
   freshly-discovered file (dimensions, mtime, hash, etc.) — reuse that code rather than
   duplicating it, so a later full scan sees the same row and does nothing different.
2. Connect it to the original using 097's resolved mechanism, passing the known source `file_id`
   directly (this ticket never needs filename/dhash matching — it already knows the exact pair).
3. Decide what happens on partial failure: the file was copied (export_file succeeded) but the
   DB-import or link step then fails (crash, busy database) — should the next full scan's normal
   discovery pick it up as an unlinked orphan, or does this need its own retry? A future full scan
   discovering it as a plain new file (unlinked) is an acceptable, self-healing fallback — prefer
   that over adding new failure-recovery machinery.
