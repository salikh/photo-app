# 067: Arrow up/down to step the rating in the viewer

- Type: task
- Status: done
- Priority: user request 2026-09-22, implement now
- Related: [031](031.md) Loupe keyboard handling, [046](046.md) swipe up/down (same step semantics), [063](063.md)
- Refs: `photoapp/static/loupe.js` (`onKey`, `rateStep`, already used by swipe), `photoapp/static/rating.js` (`step`)

Add `ArrowUp` = rating +1, `ArrowDown` = rating -1 as keyboard shortcuts in the viewer, matching the swipe
up/down behavior of [046](046.md) (which already calls `rateStep(delta)` — this ticket only needs to call the
same function from the keyboard handler).

## Behavior (reuses what 046 already defined, so this should be small)

- One key press = one step along -1 (reject), 0, 1..5 (clamped at both ends), via the existing `step()` /
  `rateStep()` used by the swipe gesture and by `ratings.step` on the server.
- Un-reject (`ArrowUp` from reject) restores the previous star count if the server remembered one ([024](024.md)).
- With `--one_star_is_unrated` ([049](049.md)), 1 is skipped in both directions, same as swipe and the digit keys.
- Same optimistic update / revert-on-failure / "leaves the filtered view" behavior as every other rating change
  ([056](056.md)) — free, since it goes through the existing `setRating`/`rateStep` path.
- `ArrowLeft`/`ArrowRight` keep meaning navigate (unchanged); only Up/Down are repurposed, and only inside the
  viewer (`onKey`), not in the grid.

## Result and a real bug found along the way (2026-09-22)

`ArrowUp`/`ArrowDown` now call the existing `rateStep(1)`/`rateStep(-1)` in `loupe.js`'s `onKey`, reusing
everything ticket 046 already built (clamping, un-reject, leaving a filtered view).

**Bug found while testing rapid presses**: `setRating`/`toggleFav` set the rating optimistically and
synchronously on every key press (for instant feedback), but each press also enqueues its own network request
carrying an *absolute* value; when several presses happen faster than one round trip, an *earlier* request's
response can resolve after a *later* press has already moved the rating further, and applying it
(`Object.assign(photo, r.photo)`) would silently overwrite the newer value with the older one — five quick
`ArrowUp` presses could leave the photo at 2 stars instead of 5. Fixed with a per-photo edit sequence guard
(`beginEdit`/`isLatest` in `loupe.js`, a `WeakMap`): a response only updates the displayed value if no newer
edit of that photo has started since it was sent; every step is still written and logged (undo granularity is
unchanged), only the *display* of a superseded response is skipped. This affected the existing digit-key and
swipe rating paths too, not just the new arrow keys — reproduced and verified fixed with a scripted Chrome
repro (5 rapid `ArrowUp` presses, checked the exact sequence of `{"rating": N}` request bodies sent, which was
already correct — the bug was purely in which response was allowed to overwrite the display, not in what was
sent).
