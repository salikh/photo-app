## Path change

`default_target(pictures_dir, rel_dir)` should return `pictures_dir/Exported/rel_dir` instead of
`{parent of pictures_dir}/Exported/rel_dir`. `validate_target` currently raises for *any* target
resolving inside `pictures_dir` (`"the export target cannot be inside {name}"`) — that check has to
carve out an exception for the new default (and, per the user's flexibility for the target field,
probably for any target under `pictures_dir/Exported` specifically, not `pictures_dir` in
general) while continuing to refuse exporting into some *other* part of the live library, which is
still not what this feature is for.

## Collision-safe naming

`dest_path` builds the destination filename as just `os.path.basename(thumbs.thumb_relpath(file_path))`
mirrored under `within_dir(rel_dir, file_path)`. Once exports accumulate in one library folder over
time (repeated exports, exports from different sessions/selections that happen to mirror to the
same subfolder, or the pre-existing content already in `/zoo/Pictures/Exported`), a destination
basename can collide with an unrelated existing file.

Decided scheme:

- **Re-export of the same source** (the existing `files` row at the computed dest path has
  `exported_from_file_id` already equal to this job's source `file_id`): overwrite in place — same
  path, same DB row refreshed (099 re-runs its metadata extraction on it), not a new file.
- **A genuine collision** (dest path exists and is unrelated — no `exported_from_file_id` pointing
  back to this source): disambiguate with a numeric suffix loop before the extension —
  `name.jpg`, `name-2.jpg`, `name-3.jpg`, ... — first free name wins. Simple, deterministic, and
  keeps [099](099.md)'s "which path did this job just write" bookkeeping trivial (it already has
  the exact `dest` `export_file` returns).
