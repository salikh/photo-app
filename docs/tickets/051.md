# 051: Incremental scan on subdirectories, run in sequence per year directory

- Type: task
- Status: open
- Related: [048](048.md) Full library scan, [012](012.md) Scanner, [014](014.md) Grouping
- Refs: user request; `photoapp/scan.py` (`scan`), `photoapp/fullscan.py`, `photoapp/grouping.py`

Make the scan finish and publish its results directory by directory, like the `2001` + `2026` run
did, so a long or interrupted scan leaves usable data behind. Run the full-library scan as a
sequence of scans, one per top-level (year) directory.

## Why

- `scan()` commits the file rows per directory, but everything that makes them visible runs **once
  at the end of the whole walk**: grouping into Photos, resolving ratings from sidecars, indexing
  existing thumbnails, hash recovery, marking missing files. A scan that dies before the end (the
  full scan was killed twice for low memory) leaves 92,549 files without a Photo and nothing in the
  grid, although all files and sidecars were read.
- The end-of-scan steps read whole tables regardless of scope: `grouping.regroup` selects every row
  of `files`, `ratings.refresh_dirs` scans every Photo's files, `thumbs.index_existing` loads all
  files, and `scan` loads every known sidecar up front. That is the memory spike at the end of a
  library-wide scan, and it makes each per-year run more expensive than it needs to be.
