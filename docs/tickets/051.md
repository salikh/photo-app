# 051: Incremental scan on subdirectories, run in sequence per year directory

- Type: task
- Status: done
- Related: [048](048.md) Full library scan, [012](012.md) Scanner, [014](014.md) Grouping
- Refs: user request; `photoapp/scan.py` (`scan`), `photoapp/fullscan.py`, `photoapp/grouping.py`

Make the scan finish and publish its results directory by directory, like the `2001` + `2026` run
did, so a long or interrupted scan leaves usable data behind. Run the full-library scan as a
sequence of scans, one per top-level (year) directory.

## Why

- `scan()` commits the file rows per directory, but everything that makes them visible runs **once
  at the end of the whole walk**: grouping into Photos, resolving ratings from sidecars, indexing
  existing thumbnails, hash recovery, marking missing files. A scan that dies before the end (the
  full scan was killed twice for low memory) leaves 92,549 files without a Photo and nothing in the
  grid, although all files and sidecars were read.
- The end-of-scan steps read whole tables regardless of scope: `grouping.regroup` selects every row
  of `files`, `ratings.refresh_dirs` scans every Photo's files, `thumbs.index_existing` loads all
  files, and `scan` loads every known sidecar up front. That is the memory spike at the end of a
  library-wide scan, and it makes each per-year run more expensive than it needs to be.

## Implementation notes (2026-09-21)

- `scan.scan_all` runs `_scan_subtree` once per step: the root's own files (`recursive=False`), then
  each top-level directory in sorted order. `_scan_subtree` reads the subtree and then groups,
  resolves ratings, indexes thumbnails, marks missing files and runs the recovery hook, all limited
  to that subtree, so a finished step is usable at once. `photoapp.fullscan`, `POST /api/scan`
  without a directory, and the nightly scan all use it.
- Range queries on the unique path index replace whole-table reads in `grouping.regroup`,
  `ratings.refresh_dirs`, `thumbs.index_existing`, the known-sidecar loader and the missing-file
  marking (`photoapp/paths.py`); the per-directory `LIKE 'dir/%'` lookups in the walk (which read the
  whole subtree for every subdirectory) became exact-path lookups for just the files in that
  directory; an index on `xmp_sidecars(file_id)` was added.
- The "ungrouped files left by an interrupted scan" recovery and the grouping-rule version (kept per
  top-level directory) are scoped to the scanned subtree, so each year migrates by itself.
- A year directory that disappears is marked missing by the full scan.
- Tests: `tests/test_scan.py` (equivalence with a single recursive scan, kill in the middle and
  resume, subtree-only grouping, root step, removed year, API status, and a check that a scoped scan
  issues no unbounded read of the `files` table).
- Real run (2026-09-21 15:04-15:49): 35 steps, 94,616 files, 66,352 Photos, peak memory 130 MB at every
  step. The `Lightroom` directory took 35 minutes to walk with 0 image files (a very large tree of
  non-image files); everything else was seconds to a few minutes per year.
