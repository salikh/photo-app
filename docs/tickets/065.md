# 065: Question: how should ratings that are newer in the database than in the sidecars be written to the sidecars?

- Type: question (answered)
- Status: done
- Blocks: [021](021.md)

## Context

Ticket 021 makes the newest rating from the database or any sidecar authoritative. A rating can be newer in the database (for example an import, or a recovered rating) than in the sidecars. The scan is read-only on your library and does not write sidecars, so such a rating is shown in the UI but the sidecars stay behind until something writes them.

## Question

When should the sidecars catch up?

## Options

- **On the next edit of that photo only** (proposed default: no extra feature; the Attention page lists Photos whose sidecars are behind).
- **Also an explicit sync**: a command (and a button) that lists what it would write and then writes the database rating to the sidecars of all such Photos in one reviewable step.
- **Automatically after every scan** (the scan starts writing sidecars; not recommended, it breaks the read-only scan).

## Answer

- Do not proactively write XMP files. Try to write XMP files on next image edit, and keep using the db-sourced newer rating in the meanwhile.
- Add a new ticket for future -- batch update of all XMP files that got out of sync with the latest computed state (which may come from the database,
or the newer other XMP file on multi-file photo)

## Resolution (2026-09-22)

This is option 1 ("on the next edit of that photo only"), confirmed. Checked against the actual code rather than
assumed: `curation._apply` already does exactly this, and it turns out it already covers even an edit that has
nothing to do with rating. `_apply` always includes the Photo's *current* rating (which is the db-sourced value
once ticket 021 made the database a source) in what it writes to both sidecars, and the early-return guard only
skips the write when there is truly nothing to do (no field changed *and* neither sidecar exists yet). So a
fav-only or tags-only edit on a Photo whose sidecars are "behind" also catches them up to the db-sourced rating,
with no code change needed — verified with a new test,
`test_db_newer_rating_is_written_on_the_next_edit_even_if_that_edit_is_unrelated` in `tests/test_curation.py`:
sidecars start at 2, the database is bumped to 5 with an `import`-sourced, dated rating (simulating a scan
finding the database ahead), `refresh_photo` sets `conflict=1` ("sidecars behind"); an unrelated `set_fav` call
writes rating 5 to both sidecars and clears the conflict flag; the fav toggle is the only logged/undo-able change
(the rating catch-up is not treated as a new user decision). The batch-sync idea is ticket [068](068.md).
