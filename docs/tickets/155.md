# 155: Folder rename button

- Type: task
- Status: done
- Priority: user request 2026-09-29
- Related: [144](144.md)/[145](145.md) (the per-Photo "Move to folder" epic — a different
  operation: moves selected Photos, one destination directory, files individually resolved. This
  is a whole-*directory* rename — a single filesystem `os.rename`, all-or-nothing, no per-file
  collision handling needed since the target must not already exist), [128](128.md)
  (`thumbs.move_thumbnails`/`raw_preview_dng.move`, reused per file)
- Refs: `photoapp/static/app.js` (header buttons), `photoapp/library.py` (`_norm_dir`),
  `photoapp/api.py` (`GET /api/dirs/exists`, ticket 145), `photoapp/paths.py` (`subtree_range`)

## What's wanted (as given)

In the grid view with the "all" filter, a new "Rename" button next to Select/Export/Rescan opens a
modal prefilled with the current folder's full relative path, preselected. On confirming that
input, a second modal confirms the move. If the target folder already exists, refuse (show an
error) rather than doing anything — unlike the per-Photo move feature (144/145), no
create-or-merge option. After a successful rename, immediately schedule a rescan of both the
source and destination directories on a worker, to reconcile the database.

## Design

- **A whole-directory rename is a single `os.rename`, not a per-file move.** Every file, sidecar,
  and per-file JSON cache under the old directory moves in one atomic filesystem operation just by
  renaming the directory itself — no enumeration, no collision handling, no per-file `shutil.move`
  needed (unlike ticket 145, which moves individual files to one shared destination and so does
  need all of that). This makes the whole-directory case both simpler to implement *and* safer:
  since the target is required not to already exist, there is no possibility of a name collision
  destroying something.
- **The database is updated synchronously**, not left entirely to the rescan — same reasoning as
  ticket 145 (instant UI consistency, no waiting on a scan to rediscover the move, and no
  hash-matching ambiguity to worry about, since a whole-subtree rename is a simple, certain prefix
  replace: every `files.path` under the old directory maps to the exact same relative position
  under the new one). `photoapp/paths.subtree_range` (already used by `library.py`/`grouping.py`
  for exactly this "everything under this directory" query shape) finds every affected row in one
  query; each becomes one `UPDATE files SET path = ?`. Cached thumbnails/PreviewDNG per file reuse
  `thumbs.move_thumbnails`/`raw_preview_dng.move` (ticket 128's own machinery, same as ticket 145)
  rather than a bulk cache-directory rename — reusing tested, working code beats a bespoke bulk
  move, and the cache tree is untouched by the source directory's own `os.rename` (a completely
  separate tree under `thumbs_dir`), so there's no move-ordering conflict between the two.
  `xmp_sidecars` table bookkeeping is left to the rescan this schedules afterward, same division
  of labor ticket 145/`docs/design/move.md` already established.
- **The rescan is scheduled afterward regardless** (the user's explicit ask) — a `scan_dir` job for
  both `old_rel_dir` (now empty/gone; reconciles `dir_mtimes` and catches anything the synchronous
  step missed) and `new_rel_dir` (sidecars, `index.json`, everything not updated synchronously).
- **Refusing an existing target**: `GET /api/dirs/exists` (ticket 145) is reused for a frontend
  pre-check before ever showing the confirm modal (so the user sees the error immediately, not
  after confirming something that's guaranteed to fail) — the backend re-checks too (a real 400,
  not just a frontend nicety, in case of a race). Also guards: target inside the source's own
  subtree (renaming a directory into itself), source is the pictures_dir root itself, source
  doesn't exist, source equals target.
- **Button placement/visibility**: header, next to Select/Export/Rescan, shown only when
  `route.page === 'browse' && route.filter === 'all'` — the user's own stated scope (renaming
  under a rating filter would be confusing: the folder's *entire* contents move regardless of
  filter, so showing the button only when nothing is filtered out avoids that mismatch).

## Outcome

Landed. `photoapp/static/rename.js`'s `open()` builds the input modal (prefilled with
`state.route.dir`, `select()`ed); confirming it checks `GET /api/dirs/exists` first — an existing
target shows an error toast and stops there (no second modal, unlike `move.js`'s "create it?"
flow, since a whole-directory rename has no merge story), otherwise a plain confirm modal, then
`POST /api/dirs/rename`. On success, `location.hash` follows the browser to the new directory
(keeping the current filter/sort) — the folder just browsed no longer exists at its old path.
`app.js`'s header gets a "Rename" button next to Select/Export/Rescan, shown only for
`route.filter === 'all'` (the user's own stated scope) and, additionally, only when
`route.dir !== '.'` — a small extra guard added during implementation, matching `rename_dir`'s own
refusal to touch the library root, so the button is never offered for an action guaranteed to
fail.

3 new e2e tests (happy path incl. following the URL to the new folder; existing-target error;
hidden under a rating filter), run via a background agent once the interactive session hit
transient tool-classifier trouble — all passed, full suite green (453 non-e2e, no regressions).
