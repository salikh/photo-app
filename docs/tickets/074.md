# 074: Jobs page progress indicator (totals, incomplete, completed in the last day/hour/minute)

- Type: task
- Status: open
- Priority: not now (user request 2026-09-22)
- Related: [066](066.md) (Jobs page already shows per-state counts), [073](073.md) (this becomes
  much more useful once a background worker is continuously draining the queue)
- Refs: `photoapp/api.py` (`/api/jobs`), `photoapp/jobs.py` (`JobQueue.counts`, `.list`),
  `photoapp/static/pages.js` (`jobsPage`)

The Jobs page (`pages.js` `jobsPage`) currently shows a one-line per-state count
(`queued: N   running: N   ...`) and a table of the most recent 100 jobs. Add a proper progress
summary above it:

- Total number of tasks
- Number of incomplete tasks (queued + running)
- Number of tasks completed in the last day, the last hour, and the last minute (three separate
  counts)

## Design notes

- "Completed" needs a decision: `done` only, or `done` + `failed`? Leaning toward counting both
  (both are finished, in different ways), possibly broken out separately in the UI.
- "Total" is only meaningful once [075] exists to keep the table bounded — until then it is "total
  ever enqueued", which is fine, but the UI text should say so rather than imply a live queue
  depth.
- `jobs.JobQueue.counts()` already gives a state breakdown but nothing time-bucketed; add a query
  (or a new `JobQueue` method, e.g. `completed_since(seconds)`) using the existing `finished_at`
  column (ISO local timestamp from `_now()`). Cheap: a handful of
  `COUNT(*) ... WHERE finished_at >= ?` queries, no schema change needed.
- Multiple `JobQueue` instances share one `jobs` table (see `_claim`'s kind-scoping) — decide
  whether the page reports across all queues combined (simplest, matches how `/api/jobs` already
  works) or breaks it down per kind/queue.
