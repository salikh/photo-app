# 074: Jobs page progress indicator (totals, incomplete, completed in the last day/hour/minute)

- Type: task
- Status: done
- Priority: not now (user request 2026-09-22)
- Related: [066](066.md) (Jobs page already shows per-state counts), [073](073.md) (this becomes
  much more useful once a background worker is continuously draining the queue)
- Refs: `photoapp/api.py` (`/api/jobs`), `photoapp/jobs.py` (`JobQueue.counts`, `.list`),
  `photoapp/static/pages.js` (`jobsPage`)

The Jobs page (`pages.js` `jobsPage`) currently shows a one-line per-state count
(`queued: N   running: N   ...`) and a table of the most recent 100 jobs. Add a proper progress
summary above it:

- Total number of tasks
- Number of incomplete tasks (queued + running)
- Number of tasks completed in the last day, the last hour, and the last minute (three separate
  counts)

## Design notes

- "Completed" needs a decision: `done` only, or `done` + `failed`? Leaning toward counting both
  (both are finished, in different ways), possibly broken out separately in the UI.
- "Total" is only meaningful once [075] exists to keep the table bounded — until then it is "total
  ever enqueued", which is fine, but the UI text should say so rather than imply a live queue
  depth.
- `jobs.JobQueue.counts()` already gives a state breakdown but nothing time-bucketed; add a query
  (or a new `JobQueue` method, e.g. `completed_since(seconds)`) using the existing `finished_at`
  column (ISO local timestamp from `_now()`). Cheap: a handful of
  `COUNT(*) ... WHERE finished_at >= ?` queries, no schema change needed.
- Multiple `JobQueue` instances share one `jobs` table (see `_claim`'s kind-scoping) — decide
  whether the page reports across all queues combined (simplest, matches how `/api/jobs` already
  works) or breaks it down per kind/queue.

## Todo

- [x] `/api/jobs`: add the new counts (total, incomplete, completed in last day/hour/minute)
      alongside the existing `counts`/`jobs` fields
- [x] `jobsPage` (`pages.js`): render them prominently above the existing table
- [x] Tests: counts match a scripted set of jobs with controlled `finished_at` timestamps at the

## Decisions

- "Done" and "failed" are different outcomes, so should be reported and counted separately.
- Report  page should report status for all job types. Maybe show status/counts per job type.

## Result (2026-09-22)

`jobs.JobQueue.progress()`: one query for `total`/`incomplete` (derived from the existing
per-state counts), one `GROUP BY kind, state` query for the per-kind breakdown, and one query per
time window (`last_minute`/`last_hour`/`last_day`, each `WHERE finished_at >= cutoff AND state IN
('done','failed')`) reported separately as decided. Windows are cumulative on purpose ("last day"
includes anything also in "last hour"), matching how such figures are normally read. No schema
change — uses the existing `finished_at` column.

`/api/jobs` now returns a `progress` field alongside the existing `counts`/`jobs`; `jobsPage`
renders total/incomplete, the three completed-window lines (done/failed split), and a per-kind
table (Queued/Running/Done/Failed) above the existing recent-jobs table.

Fixed one now-invalid exact-dict-equality test assertion in `test_jobs.py` that predated the new
field, and added `test_progress_buckets_by_finished_at` (scripted jobs at controlled ages against
all three window boundaries) plus assertions on the existing
`test_populate_thumb_jobs_appear_on_the_running_apps_jobs_page`. `tests/test_jobs.py`: 9 passed.
