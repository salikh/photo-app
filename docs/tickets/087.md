# 087: Fav and tag-based filter buttons in the folder view

- Type: task
- Status: open
- Priority: not now (user request 2026-09-23)
- Blocked by: [086](086.md) is not a hard blocker (fav/tag filtering works fine on one folder at a
  time) but is what makes this actually useful day to day — worth landing together or right after
- Refs: `photoapp/library.py` (`FILTERS`, `_FILTER_SQL`, `filter_condition` — `fav` already exists
  as a filter condition, just not a primary button; there is no tag filter condition at all yet),
  `photoapp/static/filters.js` (`primary`, `more`, `matches`, `MORE`), `photoapp/static/app.js`
  (`filterRow`)

Today `fav` is buried in the "more filters" `<select>` (`filters.js`'s `MORE` list) alongside
`picked`/`rated`/`conflict`. Give it a primary button like the rating filters already have. Tags
have no filter at all — `library.py`'s `FILTERS`/`filter_condition` only knows ratings, fav, and
conflict; `tags` is a separate `(photo_id, tag)` table with no filter wired to it.

## Design notes

- **Fav button**: mechanical — move `fav` from `filters.js`'s `MORE` array into `primary()`'s list,
  matching the existing `[value, text, title]` shape. `library.py` needs no change (`fav` is
  already a valid `filter_condition`). Trivial relative to the tag half of this ticket.
- **Tag filter — the actual design question**: unlike ratings (a fixed, small, known set), tags are
  free text (`docs/design/databases.md`'s `tags` table has no controlled vocabulary). "Filter
  buttons" for an open set needs a decision:
  - A fixed dropdown/list of tags **present in the current view** (query `DISTINCT tag` scoped to
    the current dir, like `filter_counts` is scoped) rather than every tag that ever existed in the
    whole library — keeps the control from growing unbounded.
  - Filtering by one tag at a time (`filter=tag:vacation`, mirroring the existing `rating:N`
    convention `filter_condition`/`RATING_FILTER_RE` already establish) is the simplest extension
    of the current single-`filter` route model — multi-tag AND/OR filtering is a bigger change and
    not asked for; don't build it speculatively.
  - Counts: `filter_counts`'s one-query-many-conditions approach doesn't fit an open set of tags
    well (it would need one SUM per tag, unbounded). A tag filter's button/dropdown entries
    probably need their own lightweight `DISTINCT tag, COUNT(*)` query instead of extending
    `filter_counts`'s fixed `COUNT_FILTERS` list.
- **Where it lives in the UI**: given ratings own the primary row, fav could join them as a
  primary button per the design note above, but tags (an open set) more naturally fit a `<select>`
  next to the existing "more filters" one — a second dropdown ("tag: …") populated from the
  per-folder tag list, not a button per tag.
