# 118: Bug: Initial client-side RAW rendering image is displayed with incorrect orientation

- Type: bug
- Status: done (resolved 2026-09-25)
- Related: [102](102.md), [105](105.md), [106](106.md)
- Refs: `photoapp/raw_preview_dng.py`, `photoapp/static/rawTuning.js`, `photoapp/static/loupe.js`

## Description

When switching to show the thumbnail based on DNG image, the thumbnail is shown correctly.
However, after the first edit to settings sliders, the client-side re-rendered image is initially shown with the orientation tag ignored.
After a few edit repeats, the image orientation is restored to normal.

## Root cause analysis

- `photoapp/raw_preview_dng.py`'s `_generate()` wrote the Bayer mosaic and various DNG tags via `tifffile.imwrite`, but omitted TIFF/EXIF tag 274 (`Orientation`).
- Because tag 274 was missing from the preview DNG, LibRaw-Wasm decoded the image with `flip=0` (unrotated landscape).
- The initial thumbnail was rendered server-side by `previews.py` directly from the original RAW file (which had orientation metadata), so it was displayed upright.
- When client-side tuning engaged on the first slider edit, `RawTuningSession.render()` decoded the orientation-less preview DNG, rendering the image unrotated into `ui.tuning`.
- When network fallback occurred or settings were saved, the backend re-rendered from the original RAW file, making it appear as though orientation restored after repeats.
- Resolution: pass the source RAW file's EXIF orientation (tag 274, falling back to `FLIP_TO_ORIENTATION[raw.sizes.flip]`) into `extratags` when generating the preview DNG in `raw_preview_dng.py`. LibRaw-Wasm now decodes the preview DNG with the proper orientation from the very first client-side render.
