# 153: `export_backfill` candidate matching misses the `xyz.DNG.jpg` naming convention

- Type: task
- Status: done
- Priority: user request 2026-09-29
- Related: [151](151.md) (the tie-break/date-guard this extends), [100](100.md) (`export_backfill`
  itself)
- Refs: `photoapp/export_backfill.py` (`_candidate_stems`, `backfill_by_dhash`)

## Problem

Asked to confirm whether `xyz.DNG.jpg` (a JPEG export literally named by appending `.jpg` to the
RAW's own full filename, rather than replacing its extension — a real, common naming convention in
this library, e.g. `Exported/2018-05-04/K___1293.DNG.jpg`) gets the same ticket-151 tie-breaking
treatment as `xyz.DNG`/`xyz.JPG`.

It does not, and the gap is earlier than tie-breaking: `_candidate_stems("xyz.DNG.jpg")` yields
`"xyz.dng"` (`os.path.splitext` only strips the outer `.jpg`), which never equals `"xyz"` (the stem
`_candidate_stems("xyz.DNG")`/`_candidate_stems("xyz.JPG")` yield) — so a `xyz.DNG.jpg` export
never even finds `xyz.DNG`/`xyz.JPG` as *candidates* at all, let alone reaches the dhash/tie-break
stage ticket 151 improved. Confirmed against the real library (read-only, no writes): 197 of the
741 exports still unresolved after ticket 151 match this `*.<RAW extension>.jpg` pattern.

## Design

- `_candidate_stems` gains a third yield: when the stem (after stripping the outer extension) itself
  ends in a known RAW extension (`photoapp.fileinfo.RAW_EXTENSIONS`), also yield the stem with that
  inner extension stripped too — `"xyz.dng.jpg"` → `"xyz.dng"` (existing) → also `"xyz"` (new),
  which ties with `xyz.DNG`/`xyz.JPG`'s own plain stem.
- The ticket-151 exact-name tie-break (`basename(candidate).lower() == basename(export).lower()`)
  still would not recognize this pattern as a "name match" (`xyz.DNG` != `xyz.DNG.jpg`) — add a
  second name-match rule alongside it: the export's name equals a candidate's own full name with
  `.jpg` appended, case-insensitively (`xyz.DNG.jpg` == `xyz.DNG` + `.jpg`). Unlike the ticket-151
  case (which usually resolves to the JPEG sibling, since a plain-named export is normally made
  from the already-rendered JPEG), this naming convention explicitly encodes the RAW's own
  filename, so it naturally resolves to the RAW candidate specifically when the RAW and its JPEG
  sibling are dhash-tied (the JPEG sibling's plain name never matches this rule either way).
  Still gated by the same date-plausibility check as any other tie-break.
- Validate against the real library the same way as ticket 151 (read-only queries, a throwaway
  scratch copy for the one experiment that needs `backfill_by_dhash` to actually run) before
  calling this done.

## Findings

Confirmed the gap is real and substantial: 197 of the 741 exports still unresolved after ticket
151 match the `*.<RAW extension>.jpg` pattern (checked read-only against the real library before
writing any code). The root cause is earlier than tie-breaking — `_candidate_stems` never finds
`xyz.DNG`/`xyz.JPG` as *candidates* at all for a `xyz.DNG.jpg` export, since `os.path.splitext`
only strips the outer `.jpg`, leaving a stem (`"xyz.dng"`) that never equals the sibling files' own
plain stem (`"xyz"`).

**Full-scale validation** (same method as ticket 151: read-only queries plus a fresh throwaway
scratch copy of the live db for the one experiment that needed `backfill_by_dhash` to actually
run — the live `app.sqlite` was never written to): of the 741 files still unresolved after ticket
151, **195 more now match (26%)** — essentially all 197 of the double-extension-pattern files
found in the read-only survey. Combined with ticket 151's 453, **648 of the original 1194
unresolved exports (54%) now link correctly** from these two tickets together.

## Outcome

Landed. `_candidate_stems` yields a third stem for a name ending `.<RAW extension>.<jpg|jpeg>`
(`photoapp.fileinfo.RAW_EXTENSIONS`) with that inner RAW extension stripped too, so
`"xyz.DNG.jpg"` ties with `"xyz.DNG"`/`"xyz.JPG"`'s own plain stem alongside its existing
`"xyz.dng"` stem. `backfill_by_dhash`'s tie-break name check is now `_name_matches` (used by both
151 and 153's patterns): an exact case-insensitive match (151, usually resolves to the JPEG
sibling), or `export == candidate + ".jpg"` case-insensitively (153, resolves to the RAW
specifically — the JPEG sibling's plain name never matches this convention either way). Both still
gated by the same dhash distance threshold and `_dates_plausible` check as before. 2 new tests in
`tests/test_export_backfill.py` (full suite: 15, up from 13). Full non-e2e suite green (445).
