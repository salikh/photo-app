# 075: Delete completed jobs older than 1 week on a full rescan

- Type: task
- Status: done
- Priority: not now (user request 2026-09-22)
- Related: [074](074.md) (the "total tasks" count this keeps bounded), [076](076.md) (changes what
  "a full rescan" means — see below)
- Refs: `photoapp/jobs.py`, `photoapp/scan.py` (`scan_all`, `NightlyScan`), `photoapp/fullscan.py`

The `jobs` table has no cleanup today — every `raw_render`/`populate_thumb` job stays forever
(`done`/`failed` included), so the Jobs page's history and the `/api/jobs` totals grow without
bound. On a full rescan, delete completed jobs whose `finished_at` is more than a week old.

## Design notes / open decisions

- "On full rescan" needs pinning down given [076]: today a full rescan is one synchronous call
  (`scan_all`, from `fullscan.py`, the nightly trigger, or the Rescan-all button). After [076], the
  nightly 3am trigger becomes "enqueue one scan job per top-level directory" rather than a single
  call — should pruning run at that nightly enqueue point, or only when `scan_all` itself actually
  finishes running end to end (e.g. via `fullscan.py`)? Leaning toward: prune once per nightly
  cycle, at the point the per-directory scan jobs are enqueued, since that is the reliable "once a
  day" trigger regardless of how long the actual scanning takes afterward.
- `done` vs. `failed`: a failed job's `error` might help someone diagnosing something recent, but a
  week-old failure is unlikely to still matter and the underlying condition (missing file, bad RAW)
  would surface again on its own if still relevant. Leaning toward pruning both.
- Never touch `queued`/`running` jobs.

## Decisions

- After 076, the pruning of old completed jobs should become a separate job that is scheduled (added to the queue) together with all rescanning jobs.
- Pruning failed jobs should also happen, but it should have longer period -- let's make that 12 months.
- If a job completes, it should automatically delete any previous failed attempts at the same job.

## Result (2026-09-22)

`jobs.prune(conn, done_days=7, failed_days=365)` (module-level function, not a `JobQueue` method,
so a job handler can call it directly with its own worker connection): two `DELETE ... WHERE
finished_at < ?` queries, one per state, with separate retention constants
(`DONE_RETENTION_DAYS`/`FAILED_RETENTION_DAYS`); logs a vlog(1) summary of what it deleted.

Wired in exactly per the Decisions, not the ticket's original "on `scan_all`" leaning:
`scan.enqueue_nightly_scan` now enqueues a `prune_jobs` job (deduped like any other — `file_id`
and `target` both `NULL`, so only one can ever be queued at a time) alongside the per-directory
`scan_dir` jobs, and a `prune_jobs` handler registered on `app.state.background_jobs` in
`api.create_app` calls `jobs.prune()`. `enqueue_nightly_scan`'s return value now counts this job
too (existing callers/tests updated).

"A job that completes deletes its own earlier failed attempts" is separate from the scheduled
prune and lives in `JobQueue._run`: right after a job is marked `done`, it deletes any other
`failed` row with the same `kind` + `file_id` + `target`. This runs on every successful job of
every kind, not just `prune_jobs`/`scan_dir` — e.g. a RAW that fails `raw_render` once (a
transient decode issue) and succeeds on a later retry no longer leaves the old failure sitting in
the table.

Tests: `tests/test_jobs.py` — `test_prune_deletes_old_done_and_older_failed_jobs` (controlled ages
at both retention boundaries, `queued` untouched regardless of age),
`test_a_successful_job_deletes_its_own_earlier_failed_attempts` (a handler that fails twice then
succeeds ends with exactly one `done` row, the two `failed` ones gone),
`test_prune_jobs_job_runs_through_the_background_queue` (end-to-end via a real `create_app`).
`tests/test_more_api.py`'s nightly-scan tests updated for the extra queued job. All pass (30 tests
across `test_jobs.py`/`test_more_api.py`/`test_load_worker.py`).

`docs/operations.md` and `docs/design/databases.md`'s `jobs` table description updated.
