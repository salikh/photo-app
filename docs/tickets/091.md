# 091: Help screen (keyboard shortcuts), opened by 'h', '?' or F1

- Type: task
- Status: open
- Refs: `photoapp/static/app.js` (the global `keydown` listener, `filters.shortcutFor` — the
  browse-view shortcuts: Shift+A/X/0..5), `photoapp/static/loupe.js` (`onKey` — the viewer's own,
  larger key set: arrows/space/backspace navigate, 0-5/x rate, f fav, t tag, z zoom, +/- zoom
  in/out, g cycle representative, u undo, i Files panel, Escape close; also `closeDeleteModal`'s
  `.confirm-modal` pattern, the closest existing example of a dismissable overlay to model this
  on), `photoapp/static/util.js` (`isTyping`, `el` — reuse both: don't open the help screen while
  a text input/tag field has focus)

Add a help overlay listing the app's keyboard shortcuts, opened by `h`, `?`, or `F1`, dismissed by
`Escape` (and, matching the delete modal's own convention, a click on the overlay backdrop).

## Design notes

- **Two different shortcut sets, shown together**: the browse/grid view (`app.js`'s listener:
  Shift+A/X/0..5 for filters, `u` undo, `Escape` clear selection) and the loupe/viewer (`loupe.js`'s
  much larger `onKey`) are separate listeners with separate key sets today, and the app has no
  single source of truth listing either — `filters.shortcutFor` computes the filter mapping but
  doesn't describe it in prose, and `loupe.js`'s `onKey` is one long `if/else if` chain with the
  key meanings only in comments. The help screen's list should be **written out explicitly**
  (label + key, grouped "Browse" / "Viewer"), not derived by introspecting the handlers — trying to
  auto-generate it from `onKey`'s chain would be more machinery than the feature is worth. Keep the
  two lists in sync by hand going forward, the same way `loupe.js`'s own inline comments already
  need to stay in sync with the code next to them.
- **Where the listener lives**: `h`/`?`/`F1` need to work from *both* contexts (browse and loupe),
  since a user might not remember which screen they're on when they reach for help. Cleanest as a
  **third, always-active listener** (alongside `app.js`'s and `loupe.js`'s existing ones, not
  merged into either), gated the same way both existing ones already gate themselves: skip when
  `isTyping(e.target)` or a modifier key is held, and — new — skip while the help screen itself, or
  the delete modal, is already open (so `Escape`/a second `h` press closes rather than stacking).
  `?` arrives as `Shift+/` in `e.key` on most layouts — match on `e.key === '?'` directly rather
  than a code+shift combination, matching how `loupe.js`'s existing single-letter checks already
  work.
- **Modal shape**: reuse `loupe.js`'s `.confirm-modal` backdrop-click-to-close pattern (`css`
  already defines the class) rather than inventing a second overlay style — a simple two-column
  key/action list, no new component needed.
- **Where the trigger works**: everywhere in the app, not just the loupe — a new user is as likely
  to want it from the folder grid as from inside a photo. Since it's a new top-level listener
  rather than folded into `loupe.js`'s viewer-only one, this falls out naturally rather than
  needing a special case.
- **Discoverability**: no request to add a visible "?" button anywhere (e.g. the header); the ticket
  as given is keyboard-only. Don't add a button speculatively.
