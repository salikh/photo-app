# 093: Render tuned RAW thumbnails once at Huge, downscale the rest from it

- Type: task
- Status: done
- Related: [085](085.md) (the adjustable per-file RAW settings this optimizes the regeneration
  cost for — filed while 085 was mid-implementation, 2026-09-23), [090](090.md) (resolved that both
  RAW rendering paths merge onto `rawpy`/LibRaw)
- Refs: `photoapp/thumbs.py` (`make` — its existing "existing file, then downscale from a larger
  *existing* size, then render from the original" lookup order already does exactly this
  opportunistically, but only when a larger size *happens* to already be cached; `SIZES`,
  `LONG_EDGE`), `photoapp/previews.py` (the demosaic call this ticket wants invoked at most once
  per settings change, not once per requested size)

`thumbs.make`'s lookup order already prefers downscaling from a larger *cached* size over a fresh
render, which is why a photo with an existing `Huge` costs only a cheap resize when `Thumb` is
requested. But it's opportunistic, not deliberate: if nothing is cached yet — the common case right
after 085's settings change clears every size — whichever size is requested *first* (grid view:
usually `Thumb`) demosaics directly at its own resolution, and each *later* request for a different
size (`Small`, `Medium`, `Huge`) triggers its own **separate** full demosaic, since there is nothing
larger cached yet to downscale from. For a RAW file, that's up to 4 full LibRaw demosaics (each
~0.7-1s per project measurements) to populate one photo's full size set, when one demosaic at full
resolution plus three cheap resizes would do.

## The idea

When a demosaic is actually needed (085's rule: settings tuned, or no cache at all), always render
at `Huge` (full resolution) first — regardless of which size was actually requested — then satisfy
the originally-requested size (and ideally pre-populate the others) by downscaling from that single
render, the same way `make` already downscales from an existing cached `Huge` today. The interesting
question the user flagged: should this route *through* the `Huge` cache file specifically (render
once, write `Huge` to disk, then have `Thumb`/`Small`/`Medium` requests find it via the existing
downscale-from-larger-cached-size lookup, no code path change needed there), or reuse the
in-memory decoded image directly to also populate the other sizes in the same request, without
waiting for a second request to discover the freshly-written `Huge` file on disk?

## Design notes (decided while implementing, 2026-09-24)

Went with the "through the cache file" shape: `thumbs.make()` keeps its one-size-in, one-path-out
contract. When it's about to demosaic a settings-tuned RAW from the original (the only expensive
case — the embedded-preview shortcut is already cheap, and a downscale from an existing cached
size never demosaics) and nothing larger is cached yet, it renders Huge first, writes it straight
into the thumbs tree, then falls through to the existing downscale-from-larger-cached-size logic
to produce the size actually asked for. `make()` stays DB-free as documented; the bonus Huge file
isn't recorded in the `thumbs` table by this code path, but `lookup()`/`best_available()` are
disk-based, so the very next request for a different size finds it on disk regardless. The row
itself self-heals the same way an on-disk-but-unrecorded thumbnail already does elsewhere in this
codebase — `index_existing()` on the next scan/populate pass, or simply the next direct request
for Huge itself, which hits `lookup`'s "existing" branch and gets recorded normally. Rejected the
"direct in-memory reuse" shape (demosaic once, write all four sizes in the same call) since it
would change `make()`'s "produce one size" contract for every caller, for a benefit this simpler
shape already gets in practice (the obvious sequence — grid `Thumb` immediately followed by a
loupe `Medium`/`Huge` — is exactly two or three separate requests, each now cheap after the first).

## Design notes (original, not yet resolved when filed)

- **Through the cache file (simpler)**: whenever `make()` is about to demosaic (not downscale, not
  an existing hit), render `Huge` first (write it, record it in `thumbs`), then re-run `make`'s own
  normal lookup for the originally-requested size — it will now find the just-written `Huge` and
  take the existing cheap-downscale path automatically. Minimal code change, but a `Thumb`-only
  request still does one demosaic (for `Huge`) instead of a smaller/faster one at `Thumb`'s own
  resolution — worth confirming that trade (paying full-resolution demosaic cost even for a `Thumb`-
  only view) is actually wanted before assuming it.
- **Direct in-memory reuse (more thorough)**: demosaic once, then derive and write `Thumb`/`Small`/
  `Medium`/`Huge` all from the one decoded image in the same call — proactively populates every
  size instead of only the one requested. Closer in spirit to `thumb_populate.py`'s background
  populator (which already fills every missing size for a file), but changes `make()`'s contract
  from "produce one size" to "produce up to four," which every caller (the on-demand `/img/{size}`
  handler, the background populator, ticket 089's export) would need to account for.
- **Scope relative to 085**: 085's own implementation does not depend on this — it's a performance
  optimization on top of whatever demosaic path 085 lands, not a correctness requirement. Land 085
  first with the straightforward "each size renders independently, `make`'s existing
  downscale-from-cached-larger-size logic reuses whatever is already there" behavior, then revisit
  this once real usage shows how often multiple sizes of the same tuned photo are actually
  requested close together (grid thumbnail immediately followed by opening the loupe is the
  obvious case: `Thumb` then `Medium`, then possibly `Huge` on zoom).
