# 082: "Delete this file" button in the loupe's Files panel

- Type: task
- Status: done
- Priority: not now (user request 2026-09-23)
- Related: [072](072.md) (the trash mechanism this should reuse), [081](081.md) (automatic purge,
  same relevance here), [028](028.md)/photo-model.md (manual links, representative reassignment)
- Refs: `photoapp/static/loupe.js` (`openFiles`, the `.files-panel`'s per-file `Show this`/`Unlink`
  row — the "delete this file" button goes here), `photoapp/trash.py` (`move_to_trash`,
  `trash_photo` — this ticket needs a single-file variant, not the whole-Photo one),
  `photoapp/grouping.py` (`fix_representatives`, `_choose_photo` — what happens to
  `original_file_id`/`representative_file_id` when the deleted file was one of those)

Add a "delete this file" button next to each file's `Show this`/`Unlink` row in the loupe's Files
panel (`I`, or the `files` HUD button — see `openFiles`), opening a confirmation screen with a
Medium-size render of that specific file before anything happens.

## How this differs from ticket 072 (don't conflate them)

072 is Photo-scoped and reject-gated: it moves *every* file under a *rejected* Photo, reached from
the Rejected filter view. This is **file-scoped and not rating-gated**: exactly one file (any
role — original, camera, tuning, export), reached from the Files panel of a Photo that could be at
any rating. Both should almost certainly move the file into `.trash/` the same way (reuse
`trash.move_to_trash`, not a separate delete mechanism — no reason to have two different answers
to "what does deleting a file mean" in one app), but the *scope* and *entry point* are genuinely
different, so this needs its own endpoint and its own confirmation screen, not a parameter bolted
onto the existing one.

## New design questions this raises (072 didn't have to answer these)

- **Does the file's sidecar move with it?** Almost certainly yes, for the same reason 072 moves
  sidecars — but worth confirming, since here it's one specific rendition, not the whole Photo,
  and a sidecar could in principle be shared/ambiguous in a way a whole-Photo delete never has to
  reason about (check `xmp.find_sidecars`'s bare-`NAME.xmp`-serves-either-file case before
  assuming this is as simple as it looks).
- **Deleting the *original* of a multi-file Photo.** `photos.original_file_id` would point at a
  now-missing file. Ticket 072 marks files `missing = 1` without touching grouping and leaves
  reconciliation to the next scan; decide whether that precedent is good enough here too, or
  whether this case (unlike 072's "the whole Photo is gone anyway") needs an immediate
  `grouping.fix_representatives`-style fixup so the Photo doesn't look broken until the next scan.
- **Deleting the last live file of a Photo.** Is that just allowed (the Photo ends up all-missing,
  same as if every file were trashed via 072, just one at a time), or should the UI steer someone
  who wants that toward the Rejected-view Delete flow instead? Leaning toward "just allowed" —
  simpler, and matches how `Unlink`'s existing behavior already doesn't special-case this.
- **Confirmation screen scope**: 072's review screen shows N thumbnails culminating in one confirm
  button, because it acts on many Photos at once. This is a single file, so the confirmation is
  almost certainly a much smaller, simpler affair (one Medium image, one "yes, delete this file"
  button) — probably a modal/inline panel rather than a whole new route, but worth deciding
  explicitly rather than copying 072's screen shape out of habit.

## Decisions

- Yes, file sidecars move together with removed file, in order to enable easy manual restores.
- Delete here works per file. If the user wants to delete the whole photo, they just delete every file grouped to the photo, or use reject deletion route.
- Confirmation screen should be modal in this case

## Result (2026-09-23)

Resolved the two remaining design questions the Decisions didn't cover:

- **Deleting the original of a multi-file Photo / deleting the representative**: checked
  `grouping.fix_representatives` before assuming it would help — it only repairs a representative
  that *stopped being a member* of its Photo (unlinked, or its row gone), not one that is still a
  member but now `missing = 1`, so calling it here would not actually have fixed anything. Left
  this to the next scan, the same precedent `trash_photo` (072) already set, rather than inventing
  new reconciliation logic the ticket never asked for. Documented explicitly in `trash_file`'s
  docstring so this isn't mistaken for an oversight later.
- **Deleting the last live file of a Photo**: left as "just allowed," per the ticket's own leaning
  — no special-casing, matching `Unlink`'s existing behavior.

`trash.py` refactored: `_move_file_and_sidecars(conn, settings, file_id, rel_path)` extracted from
`trash_photo`'s inner loop so `trash_file` (new) reuses it instead of duplicating the move logic.
`trash_file`: no rating check (unlike `trash_photo`), raises `TrashError("no such live file")` for
an unknown or already-missing file id.

`POST /api/files/{file_id}/trash` (same family as `link`/`unlink`/`rerender_thumbs`) returns the
move result plus the Photo's refreshed `photo_detail` in one response.

Frontend: a `Delete` button next to `Show this`/`Unlink` in each live file's row (hidden for an
already-missing one). Clicking it opens a small modal (`.confirm-modal`/`.confirm-card`, new CSS,
`z-index: 30` — above the loupe and Files panel, below the toast) with that file's Medium render,
its path, and Cancel/"Move to trash" buttons. Confirming calls the endpoint, toasts, and refreshes
the Files panel (matching `unlink`'s existing refresh pattern). Guarded the modal against being
left open across a photo change (filmstrip click, swipe) and against keyboard shortcuts firing
underneath it (`onKey` now returns early — Escape closes the modal, everything else is ignored —
whenever `ui.deleteModal` is set).

Tests: `tests/test_trash.py` (`trash_file` moves the file + its own sidecar only, leaves sibling
files/sidecars alone, works regardless of rating, refuses an unknown or already-missing file id),
`tests/test_more_api.py` (the endpoint end to end, 404 for unknown/already-missing). Full non-e2e
suite: 247 passed. e2e: `test_delete_this_file_modal_cancel_leaves_file_untouched` passed cleanly;
`test_delete_this_file_button_shows_modal_and_moves_to_trash` hit a `page.goto` timeout on a
machine that was, at the time, under confirmed severe load (load average 4–7, <500MB free,
5 users) — failed on a bare page navigation before touching any of this ticket's code, and the
structurally identical cancel-flow test in the same run passed, so this reads as the same
environmental flakiness documented earlier in this session, not a regression. Did not re-run
immediately rather than add more load to an already-struggling shared machine.
