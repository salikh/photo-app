# 092: Switch the active filter from inside the loupe, without leaving the current photo

- Type: task
- Status: open
- Related: [055](055.md)-[058](058.md) (the primary filter buttons this reuses), [056](056.md) (a
  photo leaving the view when its rating stops matching the *active* filter — the mechanism this
  ticket must not accidentally trigger when merely *switching to* a new filter that still contains
  the photo), [077](077.md) (replaceState, not a Back-button stop, for filter changes)
- Refs: `photoapp/static/loupe.js` (`renderHud`'s `filter-tag` span — the element to make
  clickable; `openFiles`/`closeFiles`/`ui.panel`/`closePanelOnly` — the existing "toggle a panel
  appended to `ui.stage`, closed by Escape or its own button" pattern this should copy rather than
  invent a modal; `onKey`'s `Escape` branch, currently `if (filesOpen) closeFiles(); else
  closeToGrid();`), `photoapp/static/filters.js` (`primary`, `matches` — client-side filter
  predicate already kept in sync with `library.py` for exactly this "does this photo match this
  filter" question, ticket 056/057), `photoapp/static/app.js` (`filterRow`'s `go()` — the *existing*
  filter switcher, which deliberately closes the loupe (`render()` → `loupe.close()` on a
  filter-changed route) and clears `photo: null`; this ticket's switcher must take a different path
  that keeps the loupe open and the photo unchanged), `photoapp/static/grid.js` (`loadFolder` — pure
  data, no DOM coupling, safe to call while the loupe is open without disturbing the hidden grid
  behind it; `loadRest`), `photoapp/static/state.js` (`state.photos`, `state.counts`)

Today, changing the filter (the header's filter buttons, `filterRow` in `app.js`) always closes the
loupe: the new route has `photo: null`, and `app.js`'s `render()` treats a filter change as a
different folder view, reloading the grid and requiring you to re-open a photo. There is also no
way to reach the filter buttons at all while the loupe is open — they belong to the header behind
it. Add a way to switch filters **from inside the loupe**, staying on the same photo, with the
filmstrip/prev-next context updated to the new filter's photo list.

## Design notes

- **Trigger (decided)**: make the existing `filter-tag` span in `renderHud` (`loupe.js`, "filter: ☆
  Unrated") clickable, opening a small dropdown/panel of filter choices. Today that span is only
  rendered when `state.route.filter !== 'all'` — extend it to always render (labelled "filter: All"
  when unfiltered) so there is always a click target to reach the switcher, not only when some
  non-default filter is already active.
- **Which filters are offered (decided: primary only)**: the same set as the grid's primary button
  row (`filters.primary()`: All, Rejected, Unrated, ★1-5), matching "the same filters that are
  shown as buttons ... in the folder grid view" from the request. The "more filters" `<select>`
  (picked/rated/fav/conflict) is a separate menu in the grid header, not buttons, and is out of
  scope here — don't fold it in speculatively.
- **Graying out non-matching filters (decided)**: for each candidate filter value, call
  `filters.matches(current(), value)` (already the exact client-side predicate ticket 056/057 keep
  in sync with the server) to decide whether it's selectable. A filter the current photo would not
  match is rendered disabled (grayed, `aria-disabled`, no click handler) — this is what prevents the
  "switch filter out from under yourself and jump to a random other photo" contradiction the request
  calls out; the current photo is never left behind by this switcher, only by an explicit rating
  edit (ticket 056's existing, separate mechanism).
- **Counts**: `state.counts` (already fetched per-folder, independent of the active filter, by
  whatever `grid.loadFolder` call most recently populated it — normally when the folder/loupe was
  first opened) can label each option the same way the grid buttons already do; no new endpoint
  needed.
- **Switching without leaving the photo (decided path, does *not* reuse `filterRow.go()`)**: write a
  loupe-local switch function, not `app.js`'s `filterRow.go()` (which unconditionally closes the
  loupe and drops `photo`). It should:
  1. `history.replaceState` to the new route (`{...state.route, filter: newFilter}`, `photo`
     unchanged) — replaceState, not a hash change, matching ticket 077 (a filter switch is not its
     own Back-button stop).
  2. Call `grid.loadFolder(newRoute)` directly (it's pure data — dirs/photos/counts — with no
     dependency on the grid's DOM, so this is safe to call while the grid behind the loupe stays
     unrendered) to get the new filter's photo list into `state.photos`.
  3. If the current photo isn't on the first page of the new list (large folder), `await
     grid.loadRest(newRoute)` first — the same fallback `app.js`'s `render()` already uses when
     opening the loupe on a deep link past the first page. It will always eventually be found,
     since a filter the photo doesn't match was never selectable.
  4. Update `index` to the current photo's position in the refreshed `state.photos` **without**
     calling `show()` — `show()` resets zoom/pan and reassigns `ui.img.src`, which would cause a
     visible reload/reset of a photo that, per the request, "should remain to be currently shown."
     Only `renderFilmstrip()` and `preload(...)` need to re-run against the new list, plus
     `renderHud()` for the updated filter tag.
  5. Close the picker panel.
- **Panel shape**: copy `openFiles`/`closeFiles`'s existing pattern — a `div` appended to
  `ui.stage` with `onclick`/`onpointerdown` `stopPropagation` (so it doesn't trigger the stage's
  swipe/zoom gestures), a boolean open flag, and `onKey`'s `Escape` branch extended with a third
  case (alongside the existing `filesOpen`/default) to close it. Don't build a new overlay
  component when this one already exists and fits.
- **Interaction with ticket 056**: 056 is "a photo leaving the *active* filter's view because of a
  rating edit" — unrelated to this ticket's "choosing a *different* filter to look through," but
  worth being explicit that this ticket must not reuse or trigger 056's `leaveIfNoLongerMatching`
  path; it is doing something else (changing which filter you're editing under, not reacting to an
  edit).
