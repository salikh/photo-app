# 101: Ignore files by basename pattern, starting with `._*`

- Type: task
- Status: open
- Priority: not now (user request 2026-09-24)
- Refs: `photoapp/fileinfo.py` (`is_image` — purely extension-based, `.jpg`/`.JPG`/etc.; a new
  `is_ignored` predicate belongs here, next to it), `photoapp/xmp.py` (`is_sidecar` — same gap,
  extension-only), `photoapp/scan.py` (`_scan_subtree`'s `images = sorted(n for n in filenames if
  fileinfo.is_image(n))`, ~line 238; `_sync_sidecars`'s `sidecar_names = sorted(n for n in
  filenames if xmp.is_sidecar(n))`, ~line 156; both need the same ignore check applied before
  anything else touches the name)

## The problem

`is_image`/`is_sidecar` only look at the extension, so a macOS AppleDouble resource-fork file
(`._IMG_1234.JPG`, `._K.DNG.xmp` — created automatically whenever macOS writes to a non-native
filesystem, e.g. the library mounted over SMB/AFP/NFS on the NAS) currently passes both checks and
gets scanned as if it were real content: `._IMG_1234.JPG` becomes a bogus `files`/`Photo` row (not
a decodable image — Pillow/rawpy will fail on it, or worse, silently produce garbage), and a
`._K.DNG.xmp` would be read and parsed as a sidecar for whatever file it happens to pair with by
name.

## What's wanted

A general notion of "ignored" filenames that never enter the database at all — not scanned into
`files`, not attempted as a sidecar, not counted in `progress.files_seen`/`files_processed`.
Start with one pattern: basename starts with `._`. Should be structured so a second pattern (dot-
files in general? `Thumbs.db`? `.DS_Store` — already excluded today since neither has an image
extension, but worth a moment's thought) can be added later without restructuring.

## Design notes

- Add `is_ignored(name)` to `fileinfo.py` (a basename check, `name.startswith("._")` to start),
  and call it before `is_image`/`is_sidecar` at both filter sites in `scan.py` — probably cleanest
  as an early `filenames = [n for n in filenames if not fileinfo.is_ignored(n)]` right after
  `os.walk` yields, so every downstream use of `filenames` in that iteration (images, sidecars,
  `seen` accounting) is automatically clean, rather than threading the check into each filter
  separately.
- **Existing rows**: files already scanned into `files` (and, if any, `xmp_sidecars`) under a
  `._*` name before this ticket lands won't disappear on their own — `_mark_missing` only reacts
  to a file vanishing from disk, not to a name becoming newly-ignored while still present. Needs a
  one-time cleanup pass (delete the `files` row, or mark it in whatever way an already-removed
  file is represented — check whether any real library data currently has such rows before
  deciding how much cleanup machinery this actually needs; it may be zero rows in practice).
- Out of scope for this ticket: general "hidden/junk file" heuristics beyond the one named
  pattern, and any change to `top_level_steps`' directory listing (already unaffected — it only
  ever lists directories, not files).
