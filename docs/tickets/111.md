## What's wanted (user request 2026-09-27)

During the directory scan (the "fullscan" / `scan_all` path), cache metadata on disk so a later scan
of an unchanged directory or file does not have to decode/read it again (the NAS is slow —
project memory: ~15 min for an 800-file directory with hashing):

- a per-directory `index.json` (the directory's own mtime + one record per file directly in it),
- a per-file JSON next to each image, named by appending `.json` (`a.DNG` -> `a.DNG.json`),
  holding that file's record,
- in addition to what `file_metadata.py` already records (mime type, width, height, hash, mtime,
  bytesize, `exif_date`), extract and store per-file EXIF: **exif date, shutter speed, aperture,
  ISO, focal length, camera make**.

## Design notes / decisions to make when picking this up

The user asked for reasonable decisions rather than questions, so these are the intended defaults:

- **Reuse, don't reinvent**: lift the index.json read/write/mtime-fixup logic from
  `file_metadata.py` into a small module under `photoapp/` (that script is standalone and imports
  absl flags at module level; the app should not import a CLI script).
- **Two new fields need extraction and storage**: `focal_length` and `camera_make` (aperture,
  shutter speed, ISO, exif date already exist — see 083/084). Extend `fileinfo` (Pillow EXIF:
  `FocalLength` in the Exif sub-IFD, `Make` in IFD0 — `raw_preview_dng._make_model` already reads
  Make/Model this way) and add two nullable `files` columns via a new migration (`focal_length
  REAL`, `camera_make TEXT`); consider camera model too, since it costs nothing once Make is read.
- **Where the JSON lives**: alongside the images (the `file_metadata.py` precedent and what the
  user described). This writes into the library, which for `/zoo/Pictures` means writing to the
  NAS — so make it **opt-in behind a flag** (e.g. `--write_metadata_json`, default off, mentioned
  in `docs/operations.md`), and never enable it against the real library in tests (project rule:
  real-data checks use a scratch dir).
- **The scanner must ignore the new files**: `index.json` and `*.json` next to an image must not be
  imported as photos or mistaken for sidecars (see 101's basename-pattern ignore list, and
  `image_metadata.py`'s note that `.json` is never an image). Also decide what happens when the
  image is deleted/moved: a stale `<name>.json` is harmless but should be cleaned or ignored.
- **Directory mtime**: writing `index.json` (and per-file JSON) changes the directory mtime, which
  would make the next scan think the directory changed. Copy `file_metadata.py`'s fix: re-read the
  mtime after writing and record the final value. Verify with a two-scan test (second scan reads
  nothing).
- **Cache validity**: a per-file record is reused only if its recorded mtime **and** bytesize match
  the file; a record lacking a key added later (e.g. `focal_length`) is backfilled by re-reading
  only that file's EXIF (same as `file_metadata.py` did for `exif_date`), and the directory is then
  reprocessed even though its own mtime is unchanged.
- **Source of truth stays the database**: the JSON is a cache/interchange file the scan can trust
  and rebuild, not something the app depends on to answer requests.
