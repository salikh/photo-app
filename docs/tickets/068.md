# 068: Batch sync of XMP sidecars that are out of sync with the computed rating

- Type: task
- Status: done
- Priority: future (user request 2026-09-22, answer to question [065](065.md))
- Related: [065](065.md) (the "write on next edit only" decision this complements), [021](021.md) (newest-wins,
  `photos.conflict`), [023](023.md) (both sidecars written), [048](048.md)/[023](023.md) survey (298 conflicting
  Photos measured on the real library)
- Refs: `photoapp/curation.py` (`_apply`), `photoapp/ratings.py` (`resolve`, `refresh_photo`), `photoapp/survey.py`,
  `photoapp/api.py` (`/api/attention`)

Per-photo sidecars only catch up to the computed rating when that Photo is next edited (ticket 065). Some Photos
may never be edited again, so their sidecars can stay out of sync indefinitely: a Photo whose database rating is
newer than its sidecars ("sidecars behind", already listed on the Attention page), and — the case the user
explicitly added — a Photo whose *sidecars disagree with each other* (one DNG/JPG sidecar newer than the other;
already counted as `photos.conflict` and surveyed in ticket 023: 298 Photos on the real library). Add a
**reviewable, explicit batch command** that brings every such Photo's sidecars in line with its currently
computed rating/fav/tags in one step.

## Scope

- Covers both cases in one pass: "sidecars behind the database" and "sidecars disagree with each other" — in
  both, the fix is the same: write the Photo's current resolved rating/fav/tags to its sidecars (exactly what
  `curation._apply` already does on a normal edit).
- **Reviewable before it writes**: a dry-run/preview mode lists every Photo it would touch (path, old sidecar
  values, the value it would write) before anything is changed — reuse `--xmp_dry_run` and/or a `--yes` gate,
  matching the pattern already used elsewhere (`import_ratings --write_xmp`, `curation` dry run).
- Likely shape: a CLI (`photoapp/sync_sidecars.py`, same family as `fullscan.py`/`populate_thumbs.py`) that finds
  every Photo with `conflict=1` (covers both cases already, since `ratings.resolve` sets it for both) and calls
  the existing `curation._apply`-based path (probably a thin wrapper, e.g. `curation.set_rating(conn, settings,
  photo_id, current_rating)` — a no-op "change" that still triggers the sidecar-catch-up write, as verified for
  065) for each. Consider whether it needs its own low-priority queue (populate_thumbs/ticket 066 precedent) since
  it can touch thousands of Photos on the real library.
- A button/endpoint in the app (mentioned in the original question's option 2) can follow once the CLI shape is
  settled; not required for a first version.

## Result (2026-09-22)

`curation.sync_sidecars(conn, settings, photo_id)`: an explicit wrapper around `_apply`, passing
the Photo's own current rating (so `changes` is always empty — nothing is logged/undoable) while
still triggering `_apply`'s write step, which rewrites every sidecar to the desired state
regardless of `changes`. Documented explicitly in its docstring rather than left as an implicit
side effect of the guard condition, per the ticket's own ask.

New `photoapp/sync_sidecars.py` (same CLI family as `fullscan.py`/`populate_thumbs.py`):
`find_conflicting` (every Photo with `conflict=1`, reusing that flag exactly as scoped — covers
both "behind" and "disagree"), `preview`/`format_preview` (path, resolved rating/fav, each
sidecar's current rating/fav with a `<- differs` marker — no writes), and `run` (writes, returns
counts + failures). The CLI defaults to preview-only; `--yes` is required to actually write,
`--xmp_dry_run` still takes precedence even with `--yes` (matches `import_ratings.py`'s
`--write_xmp`/`--xmp_dry_run` double-gate). `--limit=N` for a partial run. No low-priority queue
needed — 298 Photos on the real library (ticket 023's survey) is small enough for a plain loop,
unlike the per-file, potentially-slow-RAW-decode work `populate_thumbs.py` exists for.

Tests (`tests/test_sync_sidecars.py`, `tests/test_curation.py`): `sync_sidecars` rewrites
disagreeing sidecars and logs nothing; respects `--xmp_dry_run`; `find_conflicting`/`preview` show
exactly the conflicting Photo and leave an in-sync one alone; `run` writes, clears `conflict`, and
respects `--limit`; a CLI subprocess test confirms preview-by-default and `--yes` actually
writing. All pass.

**Deliberately not run against the real library**: while testing, I found a live production
server already running (`python -m photoapp --host 192.168.1.11 --port 8080 --v=7`, started
before this session's other changes) against the default `--state_dir`
(`~/.local/share/photos/app.sqlite`, actively being written — its files have minute-old mtimes).
Running `sync_sidecars` against that exact database, even in read-only preview mode, isn't
something to do without the user's own go-ahead given a live service is using it right now — flag
this to them rather than act on it. The command is ready to run (`python -m
photoapp.sync_sidecars` for a preview, `--yes` to write) whenever they choose to.
