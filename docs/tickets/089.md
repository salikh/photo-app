# 089: Export action (Huge-equivalent JPEGs to a chosen folder)

- Type: task
- Status: open
- Priority: not now (user request 2026-09-23)
- Related: [088](088.md) (acts on "all or selected photos in the current view" — the same

  [073](073.md)/[066](066.md) (the background `JobQueue` this should probably run on, rather than

- Refs: `photoapp/api.py` (`/img/{size}/{file_id}`'s `Huge` branch — what "equivalent to Huge"

Add an Export action: generate a JPEG "equivalent to the Huge thumbnail" for every Photo in the
current view (or just the current selection, per [088](088.md)), and write them to a folder the
user confirms via a modal. If every source file is under one common folder, e.g.
`/zoo/Pictures/a/b`, default that modal's field to `/zoo/Exported/a/b`; otherwise leave it empty
and require the user to type one.

## Design notes

- **"Equivalent to Huge" is not one code path** — per `api.py`'s existing `Huge` branch: a RAW file
  goes through the demosaic render path (`thumb_populate`/`previews`, whichever this reuses); a
  non-RAW file already in a browser-viewable format is normally served as **the original bytes,
  unconverted** ("never re-encode a full-size copy on request"). Export explicitly wants **JPEG
  files**, so a non-JPEG original (e.g. a PNG, or a camera format `WEB_EXTENSIONS` accepts but that
  isn't literally `.jpg`) needs an actual conversion step even in the "already viewable" case —
  reusing `Huge`'s "serve the original" shortcut as-is would write out the wrong file type for
  those. Decide explicitly whether every export always re-encodes to JPEG (simple, consistent) or
  only when the source isn't already a JPEG (cheaper, but two code paths to keep straight).
- **Where writes are allowed to land**: everywhere else in this app, all writes are either inside
  `pictures_dir` (XMP sidecars, `.trash/`) or inside the app's own `state_dir`/`thumbs_dir` — this
  is the first feature that writes to an arbitrary, user-supplied absolute path outside all of
  those. Needs an explicit decision, not an assumption: does the target folder need to be
  validated/restricted at all (e.g. refuse a target inside `pictures_dir`/`thumbs_dir`/`state_dir`
  to avoid silently corrupting the library or the app's own cache), or is any path the user types
  into the confirm modal trusted as-is (reasonable for a single-user local tool, but should be a
  stated choice, not a gap).
- **Filename collisions**: with [086](086.md)'s subdirectory-recursive view, or even just "select
  across folders" once [088](088.md) exists, the export set can contain two Photos with the same
  base filename from different subdirectories (e.g. two `IMG_0001.jpg`, one per trip folder).
  Flattening everything into one target folder would silently overwrite one with the other.
  Leaning toward mirroring the source subdirectory structure under the target folder (the same
  pattern `trash.py` already uses for exactly this collision-avoidance reason) rather than
  flattening — e.g. `/zoo/Pictures/a/b/x.jpg` → `<target>/x.jpg` when everything shares one
  folder, or `<target>/<relative-subpath>/x.jpg` when the export set spans subfolders.
- **Should this be a background job**: exporting a whole folder (or a large recursive selection) of
  RAW files means running the demosaic render path for each one — the same CPU cost background
  thumbnail population already treats as worth queuing (tickets 066/073) rather than doing
  synchronously in a request handler. Leaning toward a new `JobQueue` kind (or reusing the existing
  shared queue with a new `kind`, per `docs/design/concurrency-and-jobs.md`'s pattern), with
  progress visible on the existing Jobs page (ticket 074) rather than one long blocking HTTP call.
- **The confirm modal's default-path logic**: "if all source files are from a single folder" needs
  a precise definition — literally the same immediate directory, or the common ancestor directory
  of every selected/in-view Photo's representative file? A folder-view export (not recursive) is
  trivially one folder; a recursive or cross-folder selection needs the *common prefix* of all the
  involved paths, defaulting to empty (ask the user) only when that prefix is the library root
  itself (i.e. no meaningfully narrower common folder).
