## Problem

The user asked for an endpoint reporting the worker's current status (which operation, and the
target file including its directory), shown as a frequently auto-updating element on the Jobs
page, covering both scheduled and interactively-triggered work (raw re-render, directory rescan,
on-demand thumbnail generation).

Most of this already exists (113/114): every background-job kind (`raw_render`, `export`,
`populate_thumb`, `scan_dir`, `prune_jobs`, `purge_trash`) shares one `jobs` table, and
`JobQueue.active()`/`progress()` already give `/api/jobs` a unified view across all of them
regardless of which `JobQueue` instance is asked — on-demand thumbnail generation and RAW
re-render already enqueue into this same table (`api.py`'s `/img/{size}/{file_id}` route calls
`app.state.jobs.enqueue("raw_render", ...)` when nothing is cached), so they already show up.

Two real gaps:

1. **Interactive rescan (the header's "Rescan" button, `POST /api/scan`) is invisible to all of
   this.** It runs through `app.state.scanner` (`scan_lib.ScanManager`), a completely separate
   mechanism from the `jobs` table with its own `Progress` dataclass, polled via a dedicated
   `/api/scan/status` endpoint. It never appears in `/api/jobs`'s `active`/`progress`, so the Jobs
   page has nothing to show for it — exactly the case the user's main use case names ("after
   adding a new directory of photos, trigger rescan and watch its progress on the Jobs page").
   `Progress` also doesn't record which directory a plain (non-whole-library) scan is working on:
   `current_dir` is only ever set by `scan_all`'s per-top-level-step loop, not by a single-directory
   `scan()` call, so even `/api/scan/status` can't currently say "which directory" for the common
   case of rescanning one just-added folder.
2. **The Jobs page doesn't auto-update.** `jobsPage` (`pages.js`) fetches `/api/jobs` once, when
   the page is opened; the user has to manually reload to see progress change.

Additionally, the interactive rescan's progress is duplicated onto every page via the header:
`app.js`'s `renderHeader` always includes a `#scan-status` span, and `rescan()`/`pollScan()` poll
`/api/scan/status` and write into it (plus a toast and an auto-reload of the current folder) from
wherever the Rescan button was clicked. Per the user's explicit go-ahead, this is cleaned up:
status reporting moves to the Jobs page only, and the header keeps only the button that starts a
rescan.

## Design

- `scan.Progress` gains `started_at` (ISO timestamp, set when a run starts), matching the shape
  `jobs.JobQueue.active()` already returns for job-table rows (`started_at`, `duration_seconds`).
  `ScanManager.start()` sets `current_dir` to the requested directory (`rel_dir or "."`) and
  `started_at` immediately, before the background thread starts, so a plain single-directory scan
  reports its directory for its whole run, not just a whole-library scan's per-step loop (which
  keeps overriding `current_dir` per step, as today). `ScanManager._run()` clears `current_dir` in
  a `finally` once the thread is done, so this applies uniformly to both the `scan()` and
  `scan_all()` paths without touching either function's body.
- No new endpoint: `/api/jobs`'s existing `active` field is extended, in `list_jobs()`, with one
  more synthetic entry appended to `active.running` when `app.state.scanner.progress.running` is
  true — same shape as a job-table row (`kind="scan"`, `target=<directory>`, `path=None`,
  `started_at`, `duration_seconds`), plus the scan-specific counts (`files_seen`,
  `files_processed`, `dirs_seen`, `dirs_skipped`, `steps_done`, `steps_total`) as extra keys. A
  second, parallel endpoint would just be dead weight: the Jobs page already fetches `/api/jobs`,
  and `pages.js`'s existing `workerStatusText` already renders any `running` entry with a `target`
  as `"<kind> folder <target> (<duration>)"` with no changes needed — a scan reads as `scan folder
  2026-new (12s)` for free. `/api/scan/status` itself is untouched (still used by
  `tests/test_fresh_install.py`, `photoapp/__main__.py`'s startup log, and `test_scan.py`'s unit
  tests of `ScanManager`/`scan()`/`scan_all()` directly).
- `pages.js`'s `jobsPage` polls `/api/jobs` on an interval (matching the 1.5s cadence the old
  `pollScan` used) and re-renders, stopping once `state.route.page` is no longer `'jobs'` (the app
  is a single-page router with no per-page unmount hook, so this is the existing pattern for
  "did the user navigate away" — `state.route` is updated before a page's loader runs).
- `app.js` cleanup: remove the header's `#scan-status` span, `pollScan`, and `scanTimer`; `rescan()`
  just posts `/api/scan` and toasts whether it started (pointing at the Jobs page for progress) or
  that a scan is already running. The auto-reload-folder-on-scan-completion behavior this removes
  is superseded by the ticket's intended workflow (watch the Jobs page, then revisit the folder).
