# 084: Show camera metadata in the Files detail view

- Type: task
- Status: done
- Priority: not now (user request 2026-09-23)
- Blocked by: [083](083.md) (schema + extraction/backfill for aperture, shutter speed, ISO must
  exist before this can display them)
- Related: [082](082.md) (the same panel this adds to)
- Refs: `photoapp/static/loupe.js` (`openFiles`, the per-file `.file` row — currently shows
  `${width}×${height}  ${path}`), `photoapp/library.py` (`photo_detail`'s `files` list — needs the
  new columns added to its `SELECT`)

On the Files detail view (`openFiles` in the loupe, `I` or the `files` HUD button), show each
file's camera metadata: aperture (f-number), shutter speed, ISO, and exif date. `exif_date` is
already in the database and just needs surfacing; aperture/shutter speed/ISO depend on
[083](083.md) actually extracting and storing them first — **do not start this until 083's columns
exist**, there is nothing to display otherwise.

## Scope

- `library.photo_detail`'s `files` query (`photoapp/library.py`) needs the new columns added to
  its `SELECT` so they reach the frontend at all.
- `loupe.js`'s per-file row (`f.width || '?'}×${f.height || '?'}  ${f.path}` today) gets the new
  fields appended, formatted for humans — e.g. `f/2.8  1/250s  ISO 400  2019-07-04 14:22` — using
  whatever shutter-speed display formatting [083](083.md)'s design settled on.
- A file with missing/absent EXIF for one or more fields (common for scans, screenshots, exports)
  should degrade gracefully (omit that field, not show a confusing zero or `null`) — same
  tolerance the existing `width || '?'` already shows for missing dimensions.

## Result (2026-09-23)

`photo_detail`'s `files` SELECT now includes `aperture, shutter_speed, iso` alongside the
existing `exif_date` (already selected, just never rendered).

`loupe.js` gets three small formatters — `formatAperture` (`f/2.8`, dropping a trailing `.0` for
whole f-numbers), `formatShutterSpeed` (`>= 1` second → `"2.5s"`, otherwise `"1/N s"` computed from
the stored seconds, per 083's own deferred-to-084 decision), and `cameraMetaText(f)` which joins
whichever of aperture/shutter/ISO/exif_date are present with `  ·  ` and returns `null` when none
are — same graceful-omission tolerance as the existing `width || '?'`. Rendered as a second `.meta`
line under the existing `${width}×${height}  ${path}` line in the per-file row, only when
non-empty.

Tests: `tests/test_library_api.py::test_photo_detail_includes_camera_metadata` (the fields come
back `None` for the fixture's EXIF-less files, and reflect an `UPDATE` once populated — exercises
`photo_detail` without needing 083's extraction path itself, which has its own tests).
`tests/e2e/test_ui.py::test_files_panel_shows_camera_metadata` writes aperture/shutter/ISO/date
directly onto a file row and confirms the panel shows `f/2.8`, `1/250s`, `ISO 400`, and the raw
exif_date string. Full non-e2e suite: 255 passed, 6 skipped. The new e2e test passes on its own;
did not re-run the two pre-existing 082 delete-flow e2e tests (`test_delete_this_file_button_...`,
`test_delete_this_file_modal_cancel_...`) — they failed in the same run this test initially did
(before an unrelated fix to my own test's wait-for-`.loupe` timing), and system memory was down to
under 1GiB free at the time (same environmental-flakiness pattern already documented in 082's own
Result section); this ticket's change (`loupe.js`) only adds a sibling `<div>` next to the existing
per-file row content and does not touch the Delete button/modal code, so there is no plausible
mechanism by which it would affect those two tests.
