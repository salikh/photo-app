## What's wanted (user request 2026-09-27)

1. Remove the root-level ad hoc directory-management scripts now that the live library (this
   machine's `pictures_dir`) is in good shape and `photoapp` itself owns scanning, hashing,
   dedup-by-move-detection and metadata caching for it.
2. But keep, as an organized, documented, tested tool (not a pile of one-off scripts), whatever is
   still needed to manage the fact that **older backup copies of the same photo archive exist on
   other machines**: figure out what is on a given copy, and — efficiently and incrementally, with
   per-file and per-directory mtime-based caching like the scripts already do — find files that
   exist there but not here, splitting that into:
   - files this machine already has (just elsewhere/renamed — not interesting),
   - files this machine deliberately rejected and deleted (expected absence — not interesting),
   - files this machine has lost some other way (missing without an explaining decision —
     recoverable from the backup, worth surfacing), and
   - files this repo has **never seen at all** (genuinely new content, e.g. never imported from
     another device — worth surfacing for import).
3. Make sure reject/delete decisions are never purged and can be applied cleanly to a slightly
   different copy of the archive (so a backup copy can be told "these are already-handled rejects,
   not new problems" without a human re-deciding one file at a time).
4. A clear home for whatever tooling survives: a dedicated directory, with documentation, not
   loose scripts at the repo root.

## Findings (2026-09-27, before any implementation)

- **The "don't purge reject decisions" requirement is already met, within one database.**
  `curation.set_rating`/`set_fav` call `ratings._remember` → `recovery.remember_photo`, which
  upserts `rating_by_hash` (hash -> rating, fav, last_path) — a table with **no foreign key onto
  `files`**, so it survives the file's row being marked `missing`, survives `trash.trash_photo`
  moving the file into `.trash/`, and survives `purge_trash` deleting the bytes after
  `RETENTION_DAYS`. Nothing in the codebase ever deletes a `rating_by_hash` row or a `files` row
  for a trashed photo (checked: the only `DELETE FROM photos` is `grouping.py`'s own regrouping,
  unrelated). So "was this hash a decision, not an accident" already has a durable, hash-keyed
  answer *on this machine*. What's missing is **portability**: getting that answer in front of a
  *different* copy of the archive, possibly on a machine that has never run this app.
- **`hash_dir.py`'s incremental design (per-directory + per-file mtime cache in one portable
  sqlite file) is the right shape for that job, not a retirement candidate.** `photoapp`'s own
  ticket-111 cache (`photoapp/metacache.py`) writes `index.json`/`<name>.json` **into the
  scanned tree itself**, which only works when the tree is writable and is `pictures_dir` of a
  live instance — wrong fit for a read-only-mounted backup drive, a disk image, or a machine this
  tool doesn't otherwise touch. A single external sqlite catalog (what `hash_dir.py` already
  builds, and what `--hashes_db` already knows how to read during a real scan) is what makes
  "build once, mount read-only next time, only the changed files get re-hashed" work for a copy
  this app doesn't own. `nas.txt`/`filenames.txt` (already-computed catalogs of a real NAS backup)
  and `import_sha224sum.py`'s bridge from a plain `sha224sum` listing are real, already-collected
  data this tooling should keep reading, not orphan.
- **What genuinely goes away**: `image_metadata.py`/`migrate_metadata.py`/`ranking.py`/`cleanup.py`
  built a *parallel* rating/canonical-copy database for what is now `pictures_dir`'s own live
  `app.sqlite` — that job is `photoapp`'s job now. `thumbs_move.py`/`connect_thumbs.py` were
  one-off migrations of a legacy, differently-laid-out thumbnail tree into the shape an early
  version of this app expected — `photoapp` now manages `thumbs_dir` and its own move detection
  (ticket 128); there is no longer a legacy tree to migrate. `find_empty_dirs.py` is a tiny,
  generic, hash-independent housekeeping script, not really "archive comparison" — candidate to
  keep as-is, relocated, or to drop, see [132](132.md).
