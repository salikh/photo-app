## Current behavior (085) and the problem

Every slider tick (`onchange`) POSTs the full settings row to `/api/files/{id}/raw_settings`, which
writes `files.raw_*` and calls `thumbs.clear` for *every* cached size of that file — a global,
immediate commit with no distinction between "trying a value" and "keeping it." Dragging a slider
is therefore as expensive and as permanent as clicking a (nonexistent) Save button, and there's no
way to see before/after side by side without re-dragging back and forth.

## What the user wants instead (2026-09-24)

1. **Provisional rendering, not global regen**: adjusting a parameter regenerates only a
   provisional/preview thumbnail with the new parameters — it must not clear or touch the real
   cached sizes (`thumbs` table + files under the thumbs dir) or `files.raw_*` until committed.
2. **Compare hotkey**: a key that overlays the current (committed) rendering and the new
   (provisional) rendering at the same position — two images, z-index/visibility swapped by the
   hotkey — so the user can flip back and forth to judge the change.
3. **Leave room for browser-local rendering**: if adjusting brightness/WB/highlight-recovery in the
   browser (canvas/WASM, on the already-downloaded preview image) turns out to be fast enough for
   some/all of these settings, the architecture should allow swapping the provisional-render source
   from a backend round trip to an in-browser one later, without a redesign. Not implemented now —
   just don't paint into a corner.
4. **Explicit Save button**: commits the pending parameter values to the database and triggers the
   real backend thumbnail regeneration (today's `set_raw_settings` behavior) — this becomes what
   Save does, not what every slider tick does.

## Design notes (open — this ticket is to plan, not yet to build)

- **Provisional render contract**: new endpoint (e.g. `POST /api/files/{id}/raw_preview` returning
  an image, or an image URL with the pending settings as query params) that renders on demand
  without writing to `files.raw_*` or the `thumbs` table/cache files at all — must not be
  confused with or reuse the real cache, or a provisional value could leak into the committed
  render.
- **Which size to preview**: almost certainly only whatever size the loupe is currently displaying,
  not all four — rendering four sizes per slider tick would defeat the point. Depends somewhat on
  which shape 093 lands on for the real committed path.
- **Debounce**: slider drag fires many `input`/`onchange` events; the provisional-render request
  needs coalescing (e.g. render only after a short pause, or at most once per animation frame) so
  dragging doesn't hammer the backend with one LibRaw demosaic per event.
- **Compare hotkey mechanics**: both images (committed + provisional) need to be loaded at the same
  geometry in the loupe; hotkey toggles visibility/opacity on keydown (and back on keyup, or as a
  press-to-toggle) — decide which, and whether this is loupe-only or also applies to the grid.
- **Discard on navigate-away**: if the user tunes a file and leaves without pressing Save, no
  provisional render should leak into the real cache and `files.raw_*` must be unchanged.
- **Browser-local rendering**: out of scope to implement here; note it as a future direction in
  `docs/design/thumbnails.md` once this ticket's split (provisional vs. commit) exists, since that
  split is the prerequisite for ever swapping the provisional source to client-side.
