# 066: Background, low-priority population of /zoo/Thumbs (dcraw)

- Type: task
- Status: done
- Priority: user request 2026-09-22, implement now
- Related: [017](017.md) thumbs.py, [028](028.md) RAW previews and jobs, [048](048.md) library scan (thumbnail
  gaps: 2021-2026 and Exported are almost entirely missing), [050](050.md) preloading
- Refs: `photoapp/jobs.py`, `photoapp/thumbs.py`, `photoapp/api.py` (`/api/jobs`, on-demand `raw_render` job),
  `photoapp/static/pages.js` (`jobsPage`, already exists but has never had real data to show)

Proactively fill in `/zoo/Thumbs` for every file that is missing a size, instead of only rendering a thumbnail
the moment a photo is opened. Runs as a background, low-priority, one-at-a-time job so it never competes with
normal use of the app, a running scan, or the on-demand render queue.

## Requirements (as given)

- Low priority: `nice -n19 ionice -c3`.
- Kicked off in the background.
- Only one photo's thumbnails being generated at any given moment (a queue, not parallel workers).
- Queue status visible on the existing "Jobs" page/link (`/api/jobs`), which today never has anything to show.
- Default rendering: `dcraw` for `.DNG` files, except `Thumb` is the embedded JPEG extracted from the DNG
  rather than a dcraw render + resize.

## Default dcraw invocation (measured on a real file, `2022-01-ny/K___5571.DNG`, 4928x3264 sensor)

| Size | Command | Output | Time |
|---|---|---|---|
| `Thumb` (300px) | `dcraw -e -c FILE` | the camera's embedded JPEG, 4928x3264, straight to stdout | 0.1 s |
| `Small`, `Medium` (1000/2000px) | `dcraw -c -h -w FILE` | half-size demosaic (`-h`), camera white balance (`-w`), PPM to stdout | 0.8 s |
| `Huge` (full size) | `dcraw -c -w -q 3 FILE` | full-size, high-quality (AHD, `-q 3`) demosaic, PPM to stdout | 2.7 s |

One dcraw run per size tier (embedded extract, half-size, full-size), each decoded once and then resized down
with Pillow to every size in that tier that is still missing, same as the existing `thumbs.save`. `dcraw` was
not installed on this machine (checked earlier in the project, tickets 028/048); it now is (`apt install dcraw`,
9.28-8) — note this as an operational dependency, alongside the `rawpy`/LibRaw path ticket 028 already uses for
on-demand rendering (that path is unchanged; this ticket is only for the background bulk fill and deliberately
uses `dcraw` as asked, matching the original plan §4.5 wording "`dcraw -c -h -w`, piped into Pillow").

## Design

- **One job per file**, kind `populate_thumb`, in the existing `jobs` table, generating whichever of its
  missing sizes it can in one go (fewest dcraw invocations). Non-RAW files reuse the existing
  `thumbs.render`/Pillow path (no dcraw needed).
- **A queue with exactly one worker**, so at most one file is being processed at a time — this is
  `jobs.JobQueue(..., workers=1)`, reusing the existing class rather than writing a new one.
- **Bug found while designing this**: `JobQueue._claim` selects the oldest queued job regardless of `kind`, so a
  second `JobQueue` instance (this one) sharing the same `jobs` table with the existing on-demand queue
  (`app.state.jobs`, `kind='raw_render'`, 2 workers) would sometimes steal each other's jobs and fail them with
  `KeyError` (unknown kind). Fix `_claim` to only claim jobs whose kind is one of that queue's own handlers.
- **Low priority**: the queue's worker thread(s) lower their own OS scheduling priority once, before pulling any
  job — `os.nice(19)` (Linux applies `setpriority`/`nice` per *thread*, not per process, so this does not affect
  the rest of the app) and `ionice -c3 -p <thread id>` (best-effort, `ionice` may not exist; failures are
  swallowed). Add this as an opt-in `low_priority=True` flag on `JobQueue` so the existing on-demand queue is
  unaffected.
- **Kicked off in the background**: a standalone CLI, `python -m photoapp.populate_thumbs`, in the same family as
  `fullscan.py`/`survey.py`. It scans the `files` table for anything missing a size, enqueues one job per file,
  starts the low-priority single-worker queue, and logs progress until the queue drains. It writes to the same
  sqlite database as the running app (busy-retried, ticket 052), so the Jobs page shows its progress immediately
  without any change to how the app is started. Run it detached: `nice -n19 ionice -c3 python -m
  photoapp.populate_thumbs &` (the script also reduces its own priority, so the wrapper is belt-and-braces).
- Jobs page: no change needed structurally (it already lists every row of `jobs` by kind/file/state/error); the
  new `populate_thumb` rows just show up next to any `raw_render` ones.

## Result (2026-09-22)

- `dcraw` was not installed on this machine; `apt-get install -y dcraw` worked (9.28-8), so the exact commands
  above are measured against the real binary, not guessed.
- `photoapp/jobs.py`: `JobQueue._claim` now scopes its `SELECT` to `kind IN (...)` over its own handlers (the
  bug above was real and would have surfaced the moment this second queue started); `low_priority=True` adds
  `_set_low_priority()` (`os.nice(19)` + best-effort `ionice -c3 -p <thread id>`, Linux applies both per
  *thread*, confirmed with a test that checks only the worker thread's niceness changed, not the caller's).
- `photoapp/thumb_populate.py`: `extract_embedded_thumb`/`render_dcraw` wrap the three commands; `populate_file`
  does at most one dcraw run per tier (embedded, half-size, full-size) and reuses that decode for every size in
  the tier that is missing; falls back to a half-size render for `Thumb` if the embedded extraction fails (a
  DNG with no usable embedded preview); non-RAW files go through the existing `thumbs.render`/Pillow path
  unchanged; `find_missing_files` is one SQL query; `Populator` wraps a `workers=1, low_priority=True`
  `JobQueue`. All take an optional `sizes` subset (added beyond the original todo, small and useful: e.g.
  backfill just `Thumb` everywhere quickly).
- `photoapp/populate_thumbs.py`: `python -m photoapp.populate_thumbs [--limit=N] [--sizes=Thumb,Medium]`,
  logs `queued N files...` then periodic `{state: count}` progress until the queue drains.
- Never overwrites an existing thumbnail (checked with a test: a pre-existing odd-sized `Thumb` file is left
  byte-for-byte alone).
- Tests: `tests/test_jobs.py` (the `_claim` fix, `low_priority`, and that `populate_thumb` rows really do show
  up on `/api/jobs` next to `raw_render` ones), `tests/test_thumb_populate.py` (dcraw wrappers against a real
  DNG when `REAL_DNG` is set — ran and passed — plus fully mocked coverage of `populate_file`/`Populator` so
  the suite does not need the real binary), `tests/test_populate_thumbs_cli.py` (the CLI end to end, `--limit`,
  `--sizes`, never overwriting).
- Run for real: see the ticket's activity log / commit message for when it was kicked off against `/zoo/Thumbs`
  and its early progress.
