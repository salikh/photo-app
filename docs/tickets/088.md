- Refs: `photoapp/static/grid.js` (`toggle`, `renderSelectionBar`, `batchRate`, `linkSelected` —

Selection (`Select` button, click-to-toggle cells) already exists and already scopes **rating**
changes and the "link 2nd as tuning of 1st" action to just the selected Photos
(`renderSelectionBar`'s `batchRate(ids, rating)`/`linkSelected(ids)`). What's missing, per the
user's own example (`filter rejected → select → select a few → Delete` should trash only the
selected ones, not the whole folder): a **Delete** action in the selection bar, and confirmation
that selection continues to behave sanely as filters/folders change around it.

## Design notes

- **Delete already has the right shape to reuse, not reinvent**: `deleteReviewPage`
  (`pages.js`) already does exactly this confirm flow — a Medium-thumbnail grid + "Move N photo(s)
  to trash" button posting `{ids: [...]}` to `/api/photos/trash` (ticket 072) — it's just currently
  hardcoded to "every rejected Photo in `state.route.dir`" rather than an arbitrary id list.
  Generalize it to take an explicit list of Photo ids (the current selection) as an alternative
  entry point, and add a `Delete` button to `renderSelectionBar` (next to `Clear`) that navigates
  there with the selected ids instead of re-deriving "rejected in this dir". This avoids a second,
  divergent confirm-UI pattern.
- **Selection-clearing on filter/sort/dir change (decided: keep today's behavior)**: selection
  already survives the described workflow (filtering happens *before* selecting, so there's no
  ordering hazard there). The reverse case — `app.js`'s `render()` clearing selection
  (`grid.loadFolder`'s `state.selected.clear()` and the `!sameFolder` reload) whenever
  `dir`/`filter`/`sort` changes, including a filter change made *while* a selection is active — stays
  as-is: a selection made under one filter shouldn't silently carry into a different one. No code
  change here; this note exists so the behavior is a documented decision, not an implicit default.
- **Cross-folder selection** (only meaningful once [086](086.md)'s subdirectory toggle exists):
  once the grid can show Photos from multiple subdirectories at once, selection already keys by
  Photo id (not scoped to one dir), so `batchRate`/`linkSelected`/the new `Delete` action should
  work unchanged — the main risk is `grid.loadFolder`'s unconditional `state.selected.clear()` on
  every reload, which already handles "selection doesn't survive navigating to a different view";
  nothing extra needed there once 086 lands, but worth a specific test once it does.
- **Confirm-screen scale**: `deleteReviewPage`'s thumbnail grid is unbounded today (`limit=1000`
  for the whole-dir case) — a large selection reusing the same page should behave the same way; no
  new pagination/limit logic needed unless testing surfaces a real problem.
