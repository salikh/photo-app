# 072: "Delete" flow for rejected photos (removes source files from /zoo/Pictures)

- Type: task
- Status: done
- Priority: not now — needs a few design decisions first (user request 2026-09-22)
- Related: [055](055.md) (rating filter buttons, incl. Rejected), [066](066.md) (background thumb
  population, precedent for a low-priority batch operation on the library)
- Refs: `photoapp/static/filters.js` (Rejected filter), `photoapp/static/route.js`,
  `photoapp/static/pages.js`, `photoapp/static/grid.js`, `photoapp/api.py`, `docs/design/photo-model.md`
  (a Photo can span more than one file), `docs/operations.md` (currently documents `--pictures_dir` as
  "read-only except XMP sidecars" — this ticket would be the first exception)

Add a "Delete" button on the Rejected filter view. It moves to a new screen showing the currently
rejected photos as Medium-size thumbnails, with a single big red "Delete" button that deletes the
underlying source file(s) in `/zoo/Pictures` for every photo shown.

## Why this needs care before it's built

Every other write this app does is either reversible (a rating, undo-able per ticket 056) or additive
(a sidecar, a thumbnail cache entry). This is the first feature that permanently removes original
photo files, with no trash/recycle bin or backup path documented anywhere in this repo
(`docs/operations.md` only backs up the database and `manual_links.jsonl`). A few things should be
decided before or during implementation, not discovered after a bad click:

- **Soft vs. hard delete.** A single big red button with no undo is one accidental (or double-tap,
  mobile) click away from destroying irreplaceable originals. Consider moving files to a
  `<pictures_dir>/.trash/` (or a configurable trash dir) instead of unlinking, at least for a first
  version, with a separate/manual step to empty it. If a hard delete is really wanted, it needs a
  second, deliberate confirmation step (not just the one button) — e.g. a count ("Permanently delete
  14 files?") with a typed confirmation or a second tap.
- **Scope of "the currently rejected photos" shown on the new screen**: the whole library's rejects,
  or only the folder/subtree currently being browsed (matching how the grid and filters are normally
  scoped to one directory)? Leaning toward the current folder, for a smaller blast radius per click.
- **A Photo can be more than one file** (DNG + camera JPG, tuning exports — see photo-model.md). Does
  deleting a rejected Photo delete every member file, or only the representative? A reject is a
  Photo-level rating, so leaning toward every member file, but this needs to be explicit (and shown to
  the user before they click Delete, not discovered after).
- **XMP sidecars**: delete them alongside the image, or leave them orphaned? (the scanner already
  tolerates orphan sidecars by ignoring them, so leaving them is safe but untidy.)
- **Thumbnails in /zoo/Thumbs**: clean them up, or leave them as harmless orphaned cache entries
  (today nothing in the codebase ever deletes a thumbnail).
- **Database state afterward**: reuse the existing `missing=1` mechanism (the same state a file gets
  when a rescan finds it vanished from disk) rather than deleting `files`/`photos` rows outright, so
  the Photo's rating/history stays intact and no new "gone" representation is needed. Ticket 010's
  hash-recovery logic already assumes files can be marked missing without losing history.
- **Path safety**: the delete endpoint must verify every path it is asked to remove resolves under
  `pictures_dir` before unlinking (mirrors the existing check in `ScanManager.start` for a requested
  scan directory) — defense in depth against a crafted request.

## Result (2026-09-23)

Resolved the two open questions not covered by the Decisions: **scope is the current folder**
(the ticket's own leaning, for a smaller blast radius per click), and **thumbnails are left
alone** (matches the codebase's existing "nothing ever deletes a thumbnail" behavior).

New `photoapp/trash.py`: `move_to_trash` (mirrors subdirectory structure, defense-in-depth path
check mirroring `ScanManager.start`'s, avoids clobbering an earlier trashed file at the same
relative path), `trash_photo` (moves every live file of a Photo plus each file's sidecars,
marks the files `missing = 1`, refuses a Photo that is not rated reject), `trash_photos` (batch,
reports per-Photo failures without stopping the rest). `POST /api/photos/trash` (same
`{ids: [...]}` shape as the existing batch-rating endpoint) re-checks server-side, exactly as
required.

**A real bug found and fixed before it shipped**: `.trash/` is a dot-prefixed folder, and this
app already has a "hidden folder" convention (ticket 054) that scans a dot-folder but excludes it
from the listing. Applying that same rule to `.trash/` would have meant the very next scan
re-discovered a trashed photo's still-correctly-rejected sidecar as a *brand new, live* Photo —
silently un-trashing it. Wrote the scan-then-check test first
(`test_a_trashed_photos_sidecar_is_not_rediscovered_by_a_scan`), watched it fail (Photo count
went up by one), then fixed `scan.top_level_steps` and `_scan_subtree`'s `os.walk` to exclude
`.trash/` from scanning entirely, not just from the listing. Written up in
[docs/design/trash.md](../design/trash.md) since this is exactly the kind of subtle interaction
those docs exist to capture.

Frontend: `route.js` gained `hrefPage(page, dir)` and `parse()` now carries a `dir` for
`!`-prefixed pages (previously only `browse` routes had one) — needed so the review screen knows
which folder it was opened from. `pages.deleteReviewPage`: fetches the folder's rejected photos
via the existing `/api/photos?filter=rejected` (no new listing endpoint needed), a `.review-grid`
of Medium renders (bigger cells than the normal Thumb grid, per the decision), and a confirm
button placed in its own `.delete-confirm` section below all of them — reusing normal document
flow for the "scroll past everything first" requirement rather than any special scroll-tracking
JS. `app.js`'s toolbar shows the "Delete" link (styled `.danger`, reused for the confirm button
too) only when `route.filter === 'rejected'`.

Tests: `tests/test_trash.py` (path mirroring, collision avoidance, path-escape rejection, the
missing=1 states, batch error reporting, the scan-revival bug above), `tests/test_more_api.py`
(the endpoint end to end), two e2e tests in `tests/test_ui.py` (the full click-through-confirm
flow with real file assertions; the empty-review-screen case). Full non-e2e suite: 233 passed.
Targeted e2e run for the two new tests: both passed; a full e2e run was in progress at the time of
this write-up.

## Decisions

- Let's implement this as a move to trash directory (with remembering the path of the files, so ideally trash directory should contain the subdirectory structure equivalent to the one under Pictures/). Trash directory should Pictures/.trash. All of photo files, including DNG, JPG and XMP should be moved.
- There should be a separate and fully automatic step of deleting files in Trash directory after some time (e.g after 1 week). This may be okay to be moved to a separate ticket, also dependent on the worker queue.
- The review screen should contain the medium-size rendering of all photos to be deleted, the count of all deleted files and a big red button that is in a place different from the original "Delete" button, e.g. the confirmation delete button should be at the bottom, thus requiring user to scroll through all thumbnails before they can click on confirmation button.
