# 136: Question — how automated should applying known decisions to a different copy be?

- Type: question
- Status: done (2026-09-27)
- Blocks: [137](137.md)
- Related: [131](131.md) (epic), [135](135.md) (produces the report this acts on)

## Context

[135](135.md)'s "already handled" bucket says a file on the target copy has a hash this machine
already rejected and deleted. [137](137.md) needs to decide what "apply that decision to the
target copy" actually does. Candidates, least to most automated:

- **A**: report only (what [135](135.md) already does) — the user deletes matched files on the
  target copy by hand, using the report as a checklist.
- **B**: generate a review script (same pattern as the old `cleanup.py`/`find_empty_dirs.py`: print
  `rm -v --` commands to a file for the user to read and run themselves) — nothing this tool runs
  actually touches the target copy.
- **C**: move matched files on the target copy into a `.trash`-like holding area *on that copy*
  (mirroring `photoapp/trash.py`'s own move-not-delete precedent) when given an explicit
  `--apply` flag, but never delete outright.
- **D**: actually delete matched files on the target copy outright when given an explicit,
  separately-confirmed flag.

Also relevant: the "lost" bucket ([135](135.md) #3) is the opposite direction — recovering a file
*from* the target copy *into* `pictures_dir`. Should that ever be automatic (option C/D-equivalent
but copying inward), or always a reviewed, by-hand step given it's a write into the live library
this app otherwise treats as precious?

And the "never seen" bucket: should matched-new files be staged somewhere (e.g. a holding directory
under `pictures_dir`, ready for the next scan) automatically, or only listed for the user to copy
in by hand?

## Question

1. For "already handled" (safe-to-delete-on-target) matches: A, B, C, or D above?
2. For "lost" (recoverable-into-this-machine) matches: copy automatically (with `--apply`), or
   report/script only?
3. For "never seen" matches: stage into the library automatically (with `--apply`), or
   report/script only?
4. Should any of this require the target copy to be reachable as a live filesystem path (a mounted
   drive), or does it need to also support "the target is a remote machine I only have SSH/rsync
   access to" — i.e. does the apply step need to be able to emit rsync/ssh commands instead of
   doing local file operations directly?

## Answer

1. A (report) by default, either B or C or D by explicit user option.
2. Report by default, import by explicit user option. In the report, include the path or dir
   of the local copy to be recovered.
3. Report by default, include the heuristic output on where the never seen photos would be imported.
   If the 'import' command (actually cp or rsync) can be short (e.g. just a couple of directories),
   print the suggested command to the user in the report text.
   Import by explicit user option, but allow to override the heuristic on the target location,
   and allow to import smaller parts, e.g. by subdirectory, in order for the override flag to
   have clear and limited scope.
4. This is crucial: the script should be able to work with a copy (snapshot) of the "local/main" database
   copied to the remote machine. Accordingly, there should be a good format for snapshotting the local photo
   database for remote repo sync script operation on the remote machine without direct access to the "local"
   installation. To make the local/remote words take their regular meanings, it should be possible
   to snapshot the photo database into a portable file (maybe sqlite database file, but maybe something else),
   that allows the archive management scripts to construct reports and make actions (emit action scripts
   or take actions immediately) just based on the archive repo and the snapshot file.
   - It is also conceivable (please confirm with the user if you think this is a good path forward) to consider
   both 'local' and 'remote' archives two separate instances of the same photo management software,
   and consider how to synchronize two partially overlapping photo libraries. This may require additional
   novel considerations, e.g. filling/guessing the "author" of the photo and making decisions based on that,
   so I'd consider the a future work, not necessary right now.
   - In short, always assume the archive directory is accessible locally, but do not assume that photo
   database is always accessible, instead, design a database snapshot to create and copy to the target
   system that holds the 'remote' photo archive. So it is okay to assume that either database OR its snapshot is accessible locally.

## Answer (2026-09-27, confirmed)

1. **"already handled"**: option B — [137](137.md) emits a review shell script (`rm -v --` lines,
   same pattern `find_empty_dirs.py` already uses), never deletes anything on the target copy
   itself. This tool typically won't even have reliable write access to "another machine."
2. **"lost"** (recoverable into this machine): a script by default (`cp -v --` lines that preserve
   the target copy's relative directory structure under `pictures_dir`), *plus* an explicit
   `--apply` flag that performs the copy directly — copying in is additive, not destructive, so it
   gets the same trust level `photoapp` already gives its own additive writes (a sidecar, a
   thumbnail). Never silent: `--apply` still prints every file it copies.
3. **"never seen"**: same as "lost" — script by default, `--apply` copies straight into
   `pictures_dir` (preserving relative structure), ready for the next ordinary scan. No special
   "pending import" state.
4. **Remote/SSH**: out of scope for v1. The target must be a live local filesystem path (a mounted
   drive, a disk image loop-mounted, or literally `pictures_dir` of a photoapp instance on this
   same machine). When `--apply` isn't used, the generated script's `cp`/`rm` lines are ordinary
   shell, so a user comfortable with `rsync`/`ssh` can already adapt them by hand; a real
   remote/SSH mode is a candidate for a later ticket if it turns out to be needed, not built
   speculatively now.
