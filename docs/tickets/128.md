# 128: Move/rename detection should keep the file's identity and move its thumbnails

## What's wanted

When a picture is renamed or moved (still inside `pictures_dir`), a scan should recognise it by content
hash against the **whole database** and keep the file's identity -- the same `files.id`, hence its
Photo, rating/fav, tags, `raw_*` settings, crop, `thumb_rev`, manual links and `exported_from_file_id` --
instead of leaving the old path `missing=1` and creating a brand-new, unrated row.

As part of the same operation, the already-generated artifacts that are keyed by the picture's name must
be **moved to the new name**, so the thumbnail tree keeps matching the picture tree: every existing
`thumbs_dir/<Size>/<old path>.jpg` is renamed to the new path and its `thumbs.path` row updated, and the
`PreviewDNG` cache (`thumbs_dir/PreviewDNG/<old path>.preview.dng`) is moved the same way. Without this,
the old thumbnails are orphaned and the new name re-renders from scratch (or waits on the RAW job queue).

## What already exists

- `scan._scan_files` matches files by **exact path** (mtime + bytesize unchanged means skip). A moved
  file is simply a path it has never seen: it gets a new `files` row, and `_mark_missing` later marks the
  old row `missing=1`. The Photo/rating is effectively lost.
- `recovery.recover` (ticket 010) is the only rename/move handling: it restores **rating/fav** from
  `rating_by_hash` for an unrated new row, and only when unambiguous. It does not touch paths, identity,
  or thumbnails.
- The `files_hash` index exists, so a hash lookup across the whole database (not just the scanned scope)
  is cheap -- which is exactly the "check against a full database" the report asks for.
- Thumbnails are keyed by source path (`thumbs.thumb_path(thumbs_dir, size, file_path)`), as is the
  `PreviewDNG` cache (`raw_preview_dng.path_for`). Nothing renames them on a move.

## Design

- Detection happens in `_scan_files`, on the main DB-writer thread, for a file that is **not already
  known by path** (`old is None`) and has a non-NULL record hash. Query the whole `files` table by hash
  (`SELECT id, path FROM files WHERE hash = ?`) and keep candidates whose file is **gone from disk**
  (`not os.path.exists(os.path.join(pictures_dir, old_path))`). This filesystem check is what makes a
  limited subdirectory rescan still detect a move whose old path lives in a directory that was not part
  of this scan (its row may still say `missing=0`).
- Apply only when **exactly one** candidate remains -- the same deliberately conservative rule as
  `recovery.py` (a wrong automatic repoint is worse than leaving one path missing a scan longer). With 0
  or >1 candidates, keep today's insert-new-row behaviour.
- Apply = **repoint the existing row**, not insert: `UPDATE files SET path=?, <all refreshed metadata>,
  missing=0 WHERE id=old_id`. Keeping `files.id` preserves Photo membership, `photos.original_file_id`/
  `representative_file_id`, rating/fav, tags, every `raw_*`/crop/`thumb_rev` column, `xmp_sidecars.file_id`
  and `exported_from_file_id` for free.
- Followup thumbnail move, in `thumbs.py`: `move_thumbnails(conn, thumbs_dir, old_path, new_path)` renames
  each existing `thumbs_dir/<Size>/<old>.jpg` to the `<new>.jpg` (parent dirs created, `os.replace`) and
  updates the matching `thumbs` rows; `raw_preview_dng.move(thumbs_dir, old_path, new_path)` does the
  same for the preview DNG. `_scan_files` therefore needs `thumbs_dir` threaded in (it already gets
  `pictures_dir`/`conn`); `_scan_subtree` already has it in hand.
- Scope of the change is limited to `_scan_files`, which every path (`scan`, `scan_all`, the nightly
  `scan_dir` job, `fullscan.py`) already goes through, so nothing else needs its own handling. Grouping,
  rating resolution, sidecar sync and `dir_mtimes` continue to run exactly as today with the new path.
- Ambiguity: if the same content exists in two places (a genuine copy, or two files that share a hash),
  there is either more than one live candidate row or more than one new file claiming one candidate; both
  are skipped and today's behaviour applies. A move whose old name was immediately reused for different
  content is also not detected (the old path still exists), again matching `recovery.py`'s caution.
- The per-file metadata JSON cache (ticket 111) lives next to the image and is moved/ignored by the
  scanner already, so it needs no handling here. The old directory's `index.json` self-corrects on its
  next scan.

## Outcome

`scan.py` gained `_find_move_source` (whole-DB hash lookup, one gone candidate only) and `_apply_move`
(repoint the row, then `thumbs.move_thumbnails` + `raw_preview_dng.move`); `_scan_files` threads
`thumbs_dir` in, counts the batch's new-file hashes so duplicates are ambiguous, and returns the
moved-from directories that `_scan_subtree` adds to its changed set. `thumbs.move_thumbnails` and
`raw_preview_dng.move` are new. Tests in `tests/test_moves.py` cover rename-in-place, a cross-directory
move caught by a scoped rescan, copy/ambiguity being left alone, and thumbnails + PreviewDNG following.
The existing hash-recovery tests were updated: a real move now keeps its rating/fav by identity (no
recovery needed), and recovery is still covered via a genuinely-gone row. `docs/design/scanning.md`
documents the rule.

## Open questions

- Should a genuine **copy** (old file still present) also link the new file to the original's identity
  (as an additional linked file of the Photo), or stay a separate Photo? This plan keeps today's
  behaviour (separate) and only handles true moves; confirming this is not needed to proceed.
