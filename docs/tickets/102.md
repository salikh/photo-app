## What's wanted (user request 2026-09-24)

Ticket 094 already split RAW tuning into "provisional preview" vs. "commit," but the provisional
preview still round-trips to the backend for every debounced tick (`GET .../raw_preview`, a real
LibRaw demosaic server-side, `half_size=True` to keep it bearable). This epic moves that
provisional render into the browser instead, using LibRaw-Wasm, for a tuning experience with no
network latency per tick and no backend CPU cost while dragging:

1. When the tuning UI is opened for a RAW file (today: the Files panel's raw-settings block;
   the user notes this location may move later — this epic should not assume it stays there),
   the client downloads a **lossy, size-reduced version of the DNG** — not the Medium JPEG ticket
   094 uses today, and not the full original DNG (too large/slow to transfer and decode for an
   interactive tuning loop) — see [104](104.md) for producing and caching it, blocked by the open
   question in [103](103.md).
2. The client feeds that lossy DNG to LibRaw-Wasm and renders a displayable preview locally,
   re-rendering entirely in-browser (no backend request) as the user adjusts whichever parameters
   LibRaw-Wasm exposes — see [105](105.md).
3. On Save, the client's pending tuning values are persisted (as today, `raw_settings.set`) and
   the backend re-renders the *committed* thumbnails from the **original, full-quality DNG** using
   the same parameters — not from the lossy preview DNG, which exists only to make the interactive
   loop fast, never to be the source of a real thumbnail — see [106](106.md).
