## What's wanted

Implements whatever [136](136.md) answers, for each of [135](135.md)'s three actionable buckets
("already handled", "lost", "never seen" — "already have it" needs no action). At minimum:
report/script generation (option A/B territory) for every bucket, reviewable before anything
touches either copy; a real `--apply` mode only if [136](136.md) calls for one, gated the same way
`trash.py`/`xmp_dry_run` gate every other real write in this app (dry-run by default, explicit flag
to actually act, and — for anything touching `pictures_dir` itself — logged the same way an
activity-log-worthy change would be, even though this runs outside the live server).

For files staged into `pictures_dir` (the "lost"-recovery and "never seen"-import cases): land them
somewhere the next scan picks up normally (no special-casing needed in `scan.py` — a plain file at
a plain path), preserving the target copy's relative directory structure the way `move_to_trash`
mirrors it for `.trash/`. Do not invent a new "pending import" state in the database; a copied-in
file becomes a completely ordinary, unrated file the next time the library is scanned.

Verify against a real comparison, not just synthetic test trees, before calling this done — build
two small temp libraries, diverge them a rejected file and a never-seen file, and confirm all three
buckets come out right end to end.

## Done (2026-09-27)

- `tools/archive/catalog_lib.py` (new, no absl flags): the shared, flag-free classification
  library both `compare.py` and `apply.py` build on -- `load_live`/`load_target`/`classify`/
  `compare`/`compare_reverse`/`format_report`/`format_reverse_report` (moved out of `compare.py`,
  which is now a thin CLI wrapper) plus `plan`/`format_script`/`apply_copies` (this ticket).
  Splitting the logic out this way keeps compare.py and apply.py from duplicating the same
  classification code, and makes every pure function directly unit-testable despite both CLI
  scripts defining required flags of their own.
- `tools/archive/apply.py`: `--live`/`--target_db`/`--target_root`, `--apply`. Per [136](136.md)'s
  answer: `rejected` is always a printed `rm -v --` script line, never executed by this tool;
  `lost`/`new` are printed `cp -v -n`-equivalent lines by default, and actually copied (Python's
  own copy, never overwriting an existing destination) when `--apply` is given. `pictures_dir`
  comes from this app's own `config.Settings.load()`, not a separate flag -- a copy-in can't land
  anywhere other than where the running app actually expects it.
- Verified end to end for real (not just synthetic test data), matching [135](135.md)'s manual
  check: a real library scanned, one photo rejected+trashed, exported; a real `catalog.py` run of
  a second tree with the kept file, the (elsewhere-undeleted) rejected file, and a brand-new file.
  Dry run printed the right script and touched nothing; `--apply` copied the new file in and left
  the rejected target file alone; a rescan after the copy showed it as a completely ordinary,
  unrated Photo -- confirming the "no pending-import state" claim in `apply.py`'s docstring.
- `tests/test_archive_apply.py`: `catalog_lib.plan`/`format_script`/`apply_copies` unit-tested
  directly (skip "have", `rm` vs `cp -n`, never-overwrite, rejected never touched); `apply.py`
  itself only as a subprocess (same required-flags reasoning as [135](135.md)'s tests) -- dry run
  vs. `--apply`, repeatability/skip-existing, and the post-import rescan check above.
- One incidental fix while getting the suite green: [130](130.md)'s
  `test_dev_requirements_cover_every_import_of_the_tests` flagged `catalog_lib` as an
  unrecognized third-party import (it's a local, non-package module reached via a `sys.path`
  append, not installed by pip) -- added to that test's known-local exclusion list, alongside
  `photoapp`/`tests`.
