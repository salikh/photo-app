# 126: Bug: "Rescan" fails with "scan failed: no item with that key"

- Type: bug
- Status: open (filed 2026-09-26)
- Related: [127](127.md) (rescan scope, same button), [111](111.md) (metadata JSON cache, introduced
  the code path)
- Refs: `photoapp/scan.py` (`_scan_files`, `_lookup_files`), `photoapp/api.py` (`/api/scan`),
  `photoapp/static/app.js` (`rescan`, `pollScan`)

## What's reported

Clicking **Rescan** shows the toast `scan failed: no item with that key`.

## Root cause (reproduced)

`_scan_files`'s ticket 111 cache path does `file_hash = old["hash"]` (to reuse a hash when a file is
unchanged but its on-disk `index.json` record is missing/incomplete). But `old` comes from
`_lookup_files(conn, rel_dir, filenames)`, whose default columns are
`id, path, mtime, bytesize, missing` -- **no `hash`**. Any file that has a DB row but no usable
cache record hits this and raises `KeyError: No item with that key`, which `scan()` wraps as
`progress.error` and the UI toasts.

Reproduction: populate the DB with a scan (`scan.scan` with the cache off), then run the API scan
(which now defaults `write_metadata_json` on) over the same dirs -- `2024/trip/index.json` does not
exist yet, so the old-but-unchanged row takes the `old["hash"]` branch and fails. This is exactly
the state of an existing library after the ticket 111 default was flipped to on.
