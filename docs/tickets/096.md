# 096: Exports live in the library, linked to their originals

- Type: epic
- Status: done
- Depends on: [089](089.md) (export feature this reworks), [083](083.md)/[085](085.md) (per-file
  metadata precedent), [manual_links.py] role machinery already reserved for this
  (`LINK_ROLES = ("tuning", "export")`, `db.py`'s migration comment `'tuning' | 'export' (link)` —
  never wired up until now)
- Refs: `photoapp/export.py` (`default_target`, `validate_target`, `dest_path`, `export_file`),
  `photoapp/manual_links.py` (`link`, role='export' already a valid value, never actually used by
  anything), `photoapp/jobs.py` (the `jobs` table already records `file_id`+`target` per export
  job — `DONE_RETENTION_DAYS = 7`, so a completed job's row disappears after a week), `photoapp/
  scan.py`/`load_worker.py` (single-file import, to reuse instead of waiting for the next full
  scan), docs/reqs/photo-manager-requirements.md (`/zoo/Pictures/Exported/` already exists as a
  pre-app, non-empty library subfolder — about 4,114 images per the 2026-09-21 scan)

Priority: not now (user request 2026-09-24)

Today's export (089) writes a Huge-equivalent JPEG to `/zoo/Exported/...` — a sibling of
`pictures_dir`, outside the scanned library, so exported files are invisible to the app until (if
ever) someone points a separate scan at that tree. This epic makes exports land inside the library
and connects each exported file back to the photo it came from.

## What's wanted

1. Export target moves from `/zoo/Exported` to `/zoo/Pictures/Exported` (inside `pictures_dir`, so
   it gets scanned/browsed like any other folder).
2. A newly-exported file is imported into the database immediately (not left for the next full
   scan) — see [098](098.md).
3. Each exported file is connected to its original so the UI can jump from one to the other — see
   [098](098.md) (going forward, using the export job's own record) and [100](100.md) (one-off,
   for what already sits in `/zoo/Pictures/Exported` with no such record).
4. Since a folder now receives exports from possibly-different source folders over time (and
   `/zoo/Pictures/Exported` already has unrelated pre-existing content), a same-basename collision
   is a real possibility — needs a renaming strategy, not just today's straight basename copy —
   see [099](099.md).

## Architecture (resolved 2026-09-24 by [097](097.md): Option B)

The exported file stays its **own** `Photo` (own row, own `representative_file_id` = itself),
naturally browseable via `/api/photos?dir=...` wherever it physically lives — not merged into the
original's `Photo` the way a manually-linked tuning edit is. A new nullable column,
`files.exported_from_file_id REFERENCES files(id)`, is the sole cross-reference: set on the
exported file's row, pointing at the source file it came from. The UI (Files panel / loupe) shows
an "exported from: [link]" affordance when it's set, navigating to the original's own photo/
folder. `manual_links`' `role='export'` stays unused — it was reserved for the merge-into-one-Photo
shape this epic decided against.
