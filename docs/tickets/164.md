## The bug

Epic 156 shows the lens from the standard EXIF `LensModel` tag (0xA434). On these Pentax files that
tag is **absent**, so the Files pane shows no lens even though `exiftool` prints one:

    % exiftool K___3853.DNG | grep -i lens
    Lens Type : smc PENTAX-DA 18-135mm F3.5-5.6 ED AL [IF] DC WR
    Lens ID   : smc PENTAX-DA 18-135mm F3.5-5.6 ED AL [IF] DC WR

The name is not stored anywhere in the file. Pentax writes only a two-byte **code** — a series
number and a lens id, e.g. `8 215` — in its MakerNote, and ExifTool turns that code into a name with
its own lens database. Confirmed on the real library: `K___3853.DNG` has no `LensModel` tag, and the
string `PENTAX-DA`/`18-135` does not appear anywhere in its 23 MB; only the code does. The same
holds for the PEF files (`4 252`).

## Where the code lives (both verified against real files)

- **DNG**: IFD0 tag `0xC634` (`DNGPrivateData`) starts with `PENTAX \0` + byte-order marker
  (`MM`/`II`); the MakerNote IFD follows at offset 10. Its tag `0x003F` (`LensRec`) holds the code
  in its first two bytes (e.g. `08 d7` = `8 215`).
- **PEF**: the Exif IFD tag `0x927C` (`MakerNote`) starts with `AOC\0` + byte-order marker; the IFD
  follows at offset 6, tag `0x003F` again (e.g. `04 fc` = `4 252`).

Both are big-endian in the real samples; the little-endian marker must be handled too.

## Design overview (detail in each child ticket)

- **Vendor the code table, as approved** (ticket 165): a generated `photoapp/pentax_lens.py` mapping
  `(series, id)` to the lens name, taken from the installed ExifTool's `%pentaxLensTypes`, with a
  `NOTICE.md`/`third_party_licenses` entry for ExifTool's GPL/Artistic terms. This is the same
  "vendor third-party data with its notice" practice already used for LibRaw-Wasm.
- **Parse and decode in `fileinfo`** (ticket 166): `read_pentax_lens(filepath)` reads the MakerNote
  bytes from either source above, pulls the `LensType` code, and decodes it. `read_image_metadata`
  calls it when the standard `LensModel` is absent and the file is RAW, so new scans get the lens.
  The ExifTool quirks (series 4→7, 7→8, 11↔13 fallbacks) are reproduced.
- **Existing rows self-heal cheaply** (ticket 167): a PEF/DNG scanned before this has
  `lens_model = NULL` with an otherwise-complete cache record, so today a scan reuses it and never
  fills the lens. `metacache.record_lacks_lens` marks such a record, `index_lacks_keys` reprocesses
  the directory, and `_scan_files` patches just the lens via `read_pentax_lens` — deliberately
  **not** a full `read_image_metadata` re-read, which would mean re-opening every RAW through
  LibRaw (hours across 29k DNG, see ticket 163's note on backfill cost).

## Non-goals

- **Standard `LensModel` files.** Unchanged; the MakerNote path only runs when that tag is absent.
- **Disambiguating `.1` sub-variants** (Sigma/Tokina lenses that share a code, resolved by other
  MakerNote tags). Only the base code is decoded; the base name is shown.
- **Writing lens data to files or sidecars.** Display/cache only, like every other metadata field.

## Outcome

Done — 165-167 all landed. The real `K___2502.DNG` now decodes to `smc PENTAX-DA 35mm F2.4 AL` and

`record_lacks_lens` MakerNote probe (no full RAW re-read). The lens table is vendored from ExifTool
with a NOTICE/license entry. Full non-e2e suite green (474 passed, 3 skipped, with `REAL_DNG`/
`REAL_PEF` set).
