# 052: Retry on 'database is busy' with backoff, then a clear error toast

- Type: task
- Status: done
- Related: [048](048.md), [051](051.md)
- Refs: user request; `photoapp/api.py`, `photoapp/db.py`, `photoapp/static/api.js`, `photoapp/static/util.js`

The web app and a running scan (or a second app instance) write to the same sqlite database. When
one of them holds the write lock, the other fails with `sqlite3.OperationalError: database is
locked` (or `busy`) after SQLite's default 5 s wait, and the user sees a raw failure. Make the web
app retry with a growing delay, and if the database stays busy, fail clearly.

## Behavior

- On a 'database is locked' / 'busy' error, the API retries the whole database operation with
  exponential backoff (for example 0.1 s, 0.2 s, 0.4 s ... capped at a few seconds each) until about
  **one minute of total delay** has passed.
- After that it returns **HTTP 500 "internal server error"** with a short message, and the web UI
  shows that message as a **toast** (an error toast, like the other failures).
- Other errors are not retried.

## Result (2026-09-21)

- `db.retry_busy` (doubling delays 0.1 s .. 4 s, about `--busy_retry_seconds` = 60 s in total, clock and sleep injectable),
  `db.DatabaseBusy`, `db.is_busy` (only "locked/busy" errors are retried), `connect(busy_timeout=)`.
- `api.py`: `db_route` decorator re-runs a whole route function (so all 17 database routes are covered), `run_db` for the
  batch route and the async image route; the connection is rolled back before each retry and the sleeping happens outside the
  in-process lock, so other requests are not stuck; after the budget: HTTP 500 "internal server error: database busy".
  The batch route uses one batch id for every attempt so one undo covers it.
- **Retrying must not leave anything half-done.** A rating edit now takes the database write lock (`BEGIN IMMEDIATE`)
  before it touches any sidecar, so a busy database fails first and nothing is written to disk (found while writing the
  browser test: the first version rewrote the sidecars, then failed the database step, and the page said "failed" while the
  files had changed); the first-seen sidecar backup is reused when an attempt is repeated; a link/unlink decision is appended
  to `manual_links.jsonl` only after the database commit, so it cannot be logged twice.
- Background writers (scan, jobs, `fullscan`) use a long busy timeout (60-120 s) inside sqlite instead.
- UI: every 5xx answer shows its message as an error toast (`api.js`), and unhandled request failures toast too
  (`unhandledrejection`, "cannot reach the server" for a network failure); the optimistic rating change is reverted.
- Also fixed on the way: `Settings.from_flags` passed its arguments by position (two were swapped); it now uses names, with a test.
- Tests: `tests/test_busy.py` (helper, waits and succeeds exactly once with first-seen backups recorded, gives up with the 500,
  reads work while locked, the in-process lock is free while retrying, batch id, link log, nothing on disk changes when busy,
  no new sidecar when busy), `tests/e2e/test_ui.py` (busy: toast, revert, works after release).
