# 108: Busy indicator while LibRaw-Wasm renders the RAW tuning preview

- Type: task
- Status: open
- Related: [105](105.md) (the local LibRaw-Wasm render this indicates), [107](107.md) (the
  hover/Shift compare model and `ui.tuning`/`ui.rowPreview` overlay pattern this follows)
- Refs: `photoapp/static/loupe.js` (`requestPreview`, `schedulePreview`, `discardPending`,
  `build()`'s `ui.tuning`/`ui.rowPreview` overlay elements), `photoapp/static/rawTuning.js`
  (`RawTuningSession.render` — the actual `open()`+`imageData()` work this indicates; can take
  a few seconds on a first render for a given file, since it also fetches 104's preview DNG and
  the vendored WASM module has to compile fresh in that browser context)

## Problem (user request 2026-09-25)

Between a slider tick and the tuned preview updating, there's no feedback that anything is
happening — `RawTuningSession.render()` (`photoapp/static/rawTuning.js`) can take a noticeable
moment (worse on a cold `RawTuningSession`: first fetching [104](104.md)'s preview DNG, then
compiling the vendored WASM module) with nothing on screen to say so. The user asked for a busy
indicator (a sand-timer icon or similar) while LibRaw-Wasm is working on a render.

## What's wanted

A visible busy indicator (e.g. a small spinner) shown for the span of `requestPreview`'s call to
`RawTuningSession.render()` — from the moment a debounced slider/control change starts a render
until that call resolves, whichever way:

- Shown as soon as a render actually starts (after `schedulePreview`'s 200ms debounce elapses),
  not merely because a slider moved.
- Hidden once `render()` resolves, whether it produced a local preview (`ui.tuning.src` updated)
  or fell back to the network path (`requestPreviewNetwork`) — scoped to "LibRaw-Wasm is working",
  not the network fallback's own (separate, pre-existing) image-load wait.
- Must not get stuck showing if superseded by a later render (rapid slider drags) or by the panel
  closing/navigating away mid-render (`discardPending`).
