# 132: Question — which legacy scripts actually survive, and where do they live?

- Status: open
- Blocks: [133](133.md)

## Context

[131](131.md)'s Findings walk through what each root script did and whether `photoapp` (plus the
new tooling in [134](134.md)-[137](137.md)) already covers that job. The recommendation, script by
script:

| Script | Recommendation | Why |
|---|---|---|
| `hash_dir.py` | **keep**, relocate to `tools/archive/catalog.py` | still the right tool for an incremental hash catalog of a tree this app doesn't own (a backup drive, another machine) |
| `hash_dir2.7.py` | **drop**, unless a real Python-2-only machine still needs it | `hash_dir.py` (py3) covers the same job; keeping two implementations in sync is exactly the "ad hoc" cost being removed |
| `import_sha224sum.py` | **keep**, relocate | small, and bridges an already-collected `sha224sum` listing (e.g. from a machine with no Python 3) into the catalog format |
| `find_empty_dirs.py` | **keep**, relocate | generic housekeeping, unrelated to hashing, still useful after cleaning up a backup |
| `image_metadata.py`, `migrate_metadata.py`, `ranking.py`, `cleanup.py` | **drop** | built a parallel rating/canonical-copy database for what is now `pictures_dir`'s own live `app.sqlite`; [135](135.md)/[137](137.md) replace the cross-copy part of this job |
| `connect_thumbs.py`, `thumbs_move.py` | **drop** | migrated a legacy thumbnail tree layout into the shape an early version of this app expected; no longer applicable |
| `update.sh`, `METADATA_SOURCES.md` | **drop** (superseded by [138](138.md)'s README) | describes/drives the scripts above |
| `nas.txt`, `filenames.txt` | **keep as data**, not code — move under `tools/archive/` or leave at the repo root, whichever the user wants findable; not deleted either way | a real, already-computed catalog of an actual backup; [135](135.md) should be able to read it directly |

## Question

1. Does this match what you actually still reach for? In particular: is `hash_dir2.7.py`'s Python
   2.7 compatibility still needed for a real machine, or can it go?
2. `cleanup.py` (dedup-within-one-tree, pick a canonical copy, emit an `rm` script) is being
   dropped as "superseded by the live library's own dedup" — but it could equally be useful for
   thinning duplicates *within a backup copy itself* before comparing it against this machine.
   Keep a version of that idea (relocated, using [134](134.md)'s decision export so a duplicate
   that is a known reject isn't accidentally kept as "the" canonical copy), or drop it entirely?
3. Where should the surviving tools live: `tools/archive/` (a new subdirectory of the existing
   `tools/`, alongside `check_images.py`/`measure_navigation.py`) or somewhere else?
4. `nas.txt`/`filenames.txt`: keep them tracked in this repo (they are large — `nas.txt` is
   ~1,015,000 lines; check whether git/jj already treats them reasonably) at the repo root,
   move them under the new directory, or move them out of the repo entirely (e.g. into
   `state_dir`, alongside other data this repo's `.gitignore` already excludes)?
