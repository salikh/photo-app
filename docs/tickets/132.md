script:

| Script | Recommendation | Why |

## Question

1. Does this match what you actually still reach for? In particular: is `hash_dir2.7.py`'s Python
   2.7 compatibility still needed for a real machine, or can it go?
2. `cleanup.py` (dedup-within-one-tree, pick a canonical copy, emit an `rm` script) is being
   dropped as "superseded by the live library's own dedup" — but it could equally be useful for
   thinning duplicates *within a backup copy itself* before comparing it against this machine.
   Keep a version of that idea (relocated, using [134](134.md)'s decision export so a duplicate
   that is a known reject isn't accidentally kept as "the" canonical copy), or drop it entirely?
3. Where should the surviving tools live: `tools/archive/` (a new subdirectory of the existing
   `tools/`, alongside `check_images.py`/`measure_navigation.py`) or somewhere else?
4. `nas.txt`/`filenames.txt`: keep them tracked in this repo (they are large — `nas.txt` is
   ~1,015,000 lines; check whether git/jj already treats them reasonably) at the repo root,
   move them under the new directory, or move them out of the repo entirely (e.g. into
   `state_dir`, alongside other data this repo's `.gitignore` already excludes)?

## Answer

1. Yes, looks very reasonable. No need to keep `hash_dir2.7.py`.
2. Cleanup.py by itself is no longer necessary, but its code maybe folded into remote repo sync script.
BTW, let's create a separate ticket about remote repo script. I have a few things in mind:
- merge the functionality of hash_dir.py and file_metadata.py so that the script simply have some
options to control what metadata to extract.
- rely more extensively (recommend it stronger to user, always use if available) on index.json and photo.json
mtime-gated metadata caches. It works very well in practice (both incrementality and speedup are crucial),
but there is no need to have separate tools for minimal and more rich metadata cases.
- the remote repo sync script should emit a report by default (do nothing, describe the state in details),
and have options to either emit the shell script with actions and progress indicator (current behavior of
cleanup.py and other scripts), or just do the actions (with some safety guardrails to avoid losing data
e.g. when the repo is modified concurrently)
- the remote repo script should have suggested actions for many situations, instead of current suite
of scripts that each cover just one case. Some cases are listed below.
- duplicates on the remote side (remote/remote): suggest deletion with some user-tunable heuristics, similar to the currently
implemented path ranking logic
- move detected (local/remote): suggest moving the file to bring remote in sync with local directory
- reject deleted (local reject delete/remote exists): suggest executing reject deletions remotely
- unseen detected (not seen locally/exist in remote): suggest importing to local repo, with some heuristic
rules on picking import path based on remote path
3. tools/ directory is good, but let's organize by purpose. tools/archive sounds good for the remote repo sync script
and its usage instruction. The current tools should go into a subdirectory of its own, tools/testing and tools/performance perhaps?
4. filenames.txt and nas.txt files should not be in the repo at all. Just delete them. I will consider cleaning up git history
to purge them from the history later.

## Answer (2026-09-27, confirmed)

The recommendation in the table above stands, with these specifics settled:

1. `hash_dir2.7.py` is dropped — no live Python-2-only machine in play. `hash_dir.py` (Python 3)
   covers the job.
2. `cleanup.py`/`ranking.py` are dropped too, not kept in a relocated form. [135](135.md)'s
   hash-based comparison already collapses duplicate content into one entry naturally (a hash is a
   hash regardless of how many paths hold it on the target copy); a separate "pick one canonical
   copy and delete the rest" pass inside a single backup adds real scope for a want that turned out
   marginal on reflection. Can be revisited later as its own ticket if a backup with heavy internal
   duplication actually turns up.
3. Location: `tools/archive/` (new, alongside the existing `tools/check_images.py`,
   `tools/measure_navigation.py`).
4. `nas.txt`/`filenames.txt` stay exactly where they are, at the repo root — `.gitignore`'s
   `/*.txt` already keeps them untracked, so there is nothing to move for version control's sake,
   and moving large working files for tidiness alone isn't worth the churn. [135](135.md)/[137](137.md)
   document how to point at them directly (`nas.txt` is sha224sum-format, ingested the same way
   `import_sha224sum.py`, relocated, already does).

Final surviving set in `tools/archive/`: `catalog.py` (was `hash_dir.py`), `import_sha224sum.py`,
`find_empty_dirs.py`. `metadata_db.log`/`update.log` (empty/stale, untracked) are deleted as
tidiness, not because anything in this epic replaces them.

One thing this surfaced that isn't in the table: `photoapp/import_ratings.py`'s docstring and one
test (`tests/test_import_ratings.py::test_image_metadata_records_the_time_of_the_rating_source`)
reference `image_metadata.py` directly (the test even `importlib.import_module`s it). Since
`image_metadata.py` is dropped, [133](133.md) also: drops that one test (its subject, `rating_time`,
is a helper of a script that no longer exists; the schema-level behavior it exercised is still
covered by `import_ratings.py`'s own `metadata_db_with_times`-based tests in the same file) and
rewords `import_ratings.py`'s docstring to describe the expected input schema inline instead of
pointing at a script that is no longer in the tree.
