# 090: Question: should adjustable RAW settings (085) affect only the background dcraw cache, or the on-demand rawpy path too?

- Type: question (answered)
- Status: done
- Blocks: [085](085.md)

## Context

Ticket 085 wants per-file, adjustable RAW rendering settings (sliders on the Files detail view,
regenerating thumbnails on change). This app has two separate, deliberately different RAW
rendering paths (`docs/design/thumbnails.md`):

- **On-demand** (`photoapp/previews.py`, `rawpy`/LibRaw) — serves most `/img/...` requests.
- **Background bulk population** (`photoapp/thumb_populate.py`, ticket 066) — uses the external
  `dcraw` binary, and is the only place `dcraw` settings apply at all.

A slider that only changes the background/dcraw cache has an inconsistent, delayed effect: the
*next* on-demand render (e.g. after ticket 079's cache-clear, or after the file is later evicted
and re-requested) goes back through `rawpy` and ignores the setting entirely, until the background
worker happens to repopulate that size again. Threading equivalent parameters through
`previews.render`'s `raw.postprocess(...)` call as well (LibRaw supports similar knobs: exposure/
brightness, highlight recovery, white balance) would make both paths honor the setting
consistently, at the cost of more implementation work and two code paths to keep parameter-mapped.

Note, either way: the `Thumb` size (`extract_embedded_thumb`) is the camera's own already-baked
embedded JPEG — no RAW setting, dcraw or rawpy, can affect it. A slider that appears to do nothing
to the grid thumbnail is expected, not a bug, and should be explained in the UI.

## Question

When a per-file RAW setting changes, should the effect be:

- **A. Background/dcraw cache only** — simpler, reuses ticket 079's clear-and-regenerate mechanism
  as-is, but what you see can lag or silently revert to default depending on which path last
  rendered that particular size.
- **B. Both paths** — thread equivalent parameters through `previews.render`'s rawpy
  `postprocess()` too, so on-demand renders always reflect the current per-file setting. More
  work: a parameter-mapping layer between the dcraw flags and LibRaw's `postprocess()` kwargs, and
  every renderer call site needs the per-file settings looked up, not just the background job.

## Answer

- The choice of dcraw is not absolute -- we just need a way to convert DNG images to JPG with adjustable settings, of if LibRaw works for that, let's go with that. If parameters requiere dcraw, let's go with dcraw for the tuned thumbnail renderings. The split of dcraw in batch and LibRaw in online processing is a legacy artifact, not an intended state, it would be better to merge the two codepaths and used the same processing code.

- Background thumbnail generation should used raw conversion parameters, if any is at non-default value, so the result should not depend on whether it is done via online or offline or worker processing.

- The embedded JPG extraction should only be used for smallest Thumb size, and only for initial rendering when no tuning parameters were set and now prior thumbnail was available. If an older version of thumbnail already exists (so user can see at least some thumbnail while waiting for an updated one), then all thumbnail sizes including Thumb size should go through raw conversion, and take the tuning parameters during the conversion.

## Resolution (2026-09-23)

Option **B**, and further than B proposed: not just "thread settings through both paths" but merge
the two RAW renderers into one, with LibRaw/`rawpy` as the implementation used by both the
on-demand and background paths (the dcraw/rawpy split documented in `docs/design/thumbnails.md` as
"deliberate, not to be unified" is retracted — that document needs a correcting note, see below).
`dcraw` the external binary is no longer required for the three settings ticket 085 shortlisted
(all three have direct `rawpy` `postprocess()` equivalents); it stays available as a fallback only
if some *future* setting turns out to need a `dcraw`-only capability, not used by default.

Two further points that reshape 085's implementation, not just its scope:

1. **Background/online parity**: the background populator (`thumb_populate.py`) must read and apply
   the same per-file settings columns as the on-demand path — whichever one renders a given
   file+size first, the bytes must be identical. No path may silently apply defaults where the
   other would apply a tuned setting.
2. **`Thumb`-size special case**: embedded-JPEG extraction (`extract_embedded_thumb`, free —
   nothing is demosaiced) is now only used for a **true first render** of `Thumb`: no tuning
   parameters set (all at default) *and* no prior `Thumb` file already on disk. Once either
   condition is false — settings have been tuned away from default, or a `Thumb` already exists
   from an earlier render (so the user has something to look at while a fresh one is produced) —
   `Thumb` is regenerated through the same demosaic/raw-conversion path as the other sizes, so a
   tuning change is now visible even at `Thumb` size (this removes 085's earlier "a slider does
   nothing to the grid thumbnail" limitation for the *steady-state* case; it still holds only for a
   photo's very first, never-before-rendered `Thumb`).

085 has been rewritten to carry this forward as its implementation plan and is now unblocked.
`docs/design/thumbnails.md`'s "two paths, deliberately not unified" section has been marked
superseded, pointing here.
