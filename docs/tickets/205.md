## What's wanted (as given)

Export to Google Photos as a new album. Decided in a /grilling session 2026-10-10.

## Decisions

- An optional step of the existing Export flow (full view or selection): first render into
  `Exported/` (mirroring the Pictures tree; those copies stay), then upload. Album name confirmed in the
  export modal, default derived like the export folder name.
- **API reality (docs checked 2026-10-10):** since March 2025 the Library API sees only albums and items
  this app created, so the album picker lists only albums this tool made; no favourites/star write; item
  `description` <= 1000 chars; 50 items per `batchCreate`, serial; identical bytes dedupe to one media
  item, so re-running is safe and no local tracking is needed.
- Default is a NEW album; 'add to existing' picks from ranked app-created albums; same-name warning with
  a choice. Append-only, in grid order. No album bookkeeping in the photo DB (Google Photos is
  authoritative; a later sync epic may bring albums back as tags).
- Photos: the rendered export JPEG, with EXIF copied (ticket 207) -- a hard prerequisite, since Google
  dates items from EXIF. GPS is off on every export and must be ticked explicitly each time (208); it
  governs the file in `Exported/` too.
- Videos: original, hardlinked/copied to `Exported/`, uploaded as is; the file to upload comes from one
  function so later video tunings can replace it.
- Auth: one-time CLI loopback flow, secrets in `state_dir`; not in the web app.
- Tests: fake Google server; never real uploads.
- Out of scope: captions, favourites, sync from Google, album tags, interleaving (see 216).
