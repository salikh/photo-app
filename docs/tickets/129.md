# 129: Rotate a photo from the loupe (per-file, non-destructive, applied on view)

- Type: enhancement
- Status: in progress
- Related: [115](115.md)/[116](116.md) (non-destructive crop, same per-file/render layer and
  `thumb_rev` mechanism), [119](119.md) (`thumb_rev` cache-busting), [085](085.md)/[102](102.md)
  (per-file RAW tuning; rotation is deliberately *not* a RAW setting), [118](118.md) (EXIF
  orientation in the preview DNG), [125](125.md) (export applies crop for real)
- Refs: `photoapp/crop.py` and `photoapp/raw_settings.py` (the per-file-setting pattern this
  copies), `photoapp/thumbs.py` (`_open`/`render`/`render_raw_sizes`/`make`/`ensure`),
  `photoapp/previews.py` (`_oriented`, `embedded_preview`, `render` -- the EXIF/metadata
  orientation this must not touch), `photoapp/export.py`, `photoapp/library.py`, `photoapp/api.py`,
  `photoapp/static/loupe.js`

## What's wanted

A button in the loupe HUD that turns the displayed image **90° to the left** (counter-clockwise),
repeatedly: each press adds another 90° left, so 4 presses return to 0°. The rotation is stored
per *file*, like the crop and the RAW settings, and is applied **when the image is rendered/viewed,
for every size**, as a final transformation.

## Answer to the design question (2026-09-27)

Per-file (like crop/RAW settings), not per-Photo (like rating). Rationale from the user: the button
mostly exists to fix bad orientation data / data-handling inconsistencies on a specific file, and a
file is where such a defect lives. It is therefore **DB-only**, not written to XMP sidecars (rating
is; crop and RAW settings are not, and rotation belongs with them).

## What already exists

- The per-file setting pattern is `crop.py`/`raw_settings.py`: nullable `files` columns, a small
  module with `get`/`set`/`validate`/`is_default`, a `POST /api/files/{id}/...` route that clears
  every cached thumbnail and bumps `files.thumb_rev`, and `thumbs.py` threading the setting into
  `_open`/`render`/`make`/`ensure` so all sizes respect it. `library._photo_json` carries the
  representative file's value to the client; `photo_detail` carries it per file.
- **Metadata orientation is already handled, and stays untouched**: `thumbs._open` calls
  `ImageOps.exif_transpose` for non-RAW files, and `previews._oriented`/`embedded_preview` apply
  LibRaw's `sizes.flip` for RAW. Rotation is applied *after* those, as the final transform, so the
  two never mix: the metadata orientation says how the sensor/browser should present the frame,
  the new value says "the user wants it turned from there".
- The loupe already has one interactive full-frame overlay for crop (`loupe.js`'s `.crop-shade`),
  positioned over `ui.img`'s content box and hidden while zoomed/in crop mode. That is the only
  client code that needs to know about rotation, because the shaded rectangle is expressed in
  source-frame coordinates.

## Design

- **Storage**: one nullable `files.rotation` INTEGER column, in **degrees counter-clockwise**,
  normalized to `0`/`90`/`180`/`270`; `NULL` and `0` both mean "not rotated", and `0` is normalized
  back to `NULL` on write (mirrors `crop`'s whole-frame → `NULL`). New module `photoapp/rotation.py`
  with `get`, `is_default`, `normalize`, `validate`, `apply(img, rotation)` (`img.rotate(rotation,
  expand=True)` — positive = counter-clockwise, matching the column), and `set` (validate, normalize,
  `UPDATE files SET rotation = ?, thumb_rev = thumb_rev + 1`, commit). Only multiples of 90 are
  accepted, so no interpolation/quality question arises.
- **Rendering**: `thumbs._open` applies `rotation.apply(...)` **last**, after `_apply_crop(...)`, so
  the order is: metadata orientation → raw-render settings → crop → rotate. `render`,
  `render_raw_sizes`, `make` and `ensure` take a `rotation` argument alongside `settings`/`crop`,
  and `api.py`'s `/img/{size}` handler fetches it with the other two. A whole-frame rotation is a
  lossless `expand=True` turn of the already-decoded bitmap, so no size needs special casing.
- **Saving clears the cache**: `POST /api/files/{id}/rotation` (body `{rotation: int}`) stores it,
  `thumbs.clear`s every size, and returns `{rotation, rev}` like `/crop`. The HUD button rotates the
  representative file optimistically, then reconciles from the response and refreshes the grid cell
  and filmstrip thumb (`refreshCellThumb`/`strip.refreshThumb`, same as `saveCrop`). `thumb_rev`
  makes every `imgUrl` cache-bust automatically (ticket 119).
- **Client payload**: `library._photo_json` includes `rotation` (representative file's value) and
  `photo_detail`'s per-file rows include it. `loupe.js` stores it on the `photo` object.
- **Crop shade after rotation**: `positionCropLayer` keeps using the displayed image's
  `getBoundingClientRect()`, but the rectangle is transformed from source-frame to displayed-frame
  coordinates by a small pure helper `rotateRect(rect, rotation)` (90° CCW: `{x: y, y: 1-(x+w),
  w: h, h: w}`; 180°: `{x: 1-(x+w), y: 1-(y+h), w, h}`; 270°: `{x: 1-(y+h), y: x, w: h, h: w}`).
  Crop mode itself keeps working in the *rotated* displayed frame, so saving a crop while rotated
  stores it in the (rotated) frame it was drawn in — and `updateCropShade` therefore treats a
  rotated file's crop rect as already being in source coordinates only for the no-crop default; see
  Open questions.
- **Export**: `export.export_file` applies rotation too, for the same reason ticket 125 makes a
  cropped export render rather than copy `Huge` (a finished, out-of-app artifact should look like
  what the app shows). A rotated file takes the render path even when uncropped.
- **Button**: a HUD `⟲` button ("rotate left 90°") next to `crop`, plus the unbound lowercase `R`
  as its shortcut, recorded in `help.js`.

## Open questions

- **Crop + rotation together**: the crop rectangle is stored in the source frame it was drawn in.
  While the loupe is *rotated*, crop mode draws over the rotated display, so a crop saved then is
  in the rotated frame, yet rotation is applied after cropping at render time — i.e. a crop drawn
  while rotated would rotate with the image again. The plan keeps crop mode usable with rotation 0
  (the overwhelmingly common case, since rotation is an orientation fix) and shades correctly by
  transforming the stored rect; it does not attempt a re-entrant "draw crop in rotated frame" model.
  Confirming this is sufficient is not needed to proceed.
- **Provisional RAW tuning overlay**: `ui.tuning` (the `raw_preview`/LibRaw-Wasm provisional render
  over the committed image) is a transient comparison aid and is not rotated in this plan; the
  committed image (and every thumbnail size) is. If it proves distracting on a rotated RAW being
  tuned, the same `rotation.apply` can be added to the `raw_preview` route and a CSS transform to
  the overlay as a follow-up.
