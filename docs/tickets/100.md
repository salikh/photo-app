# 100: One-off backfill — link pre-existing exports to their originals

- Type: task
- Status: open
- Blocked by: [099](099.md) (defines `files.exported_from_file_id`, the column this ticket sets)
- Related: [096](096.md) (epic), [099](099.md) (makes this unnecessary for anything exported after
  it lands — this ticket is only for the backlog that already exists)
- Refs: `photoapp/jobs.py` (the `jobs` table — `DONE_RETENTION_DAYS = 7`, so only export jobs
  finished in roughly the last week are still there; older ones are already pruned), `photoapp/
  export.py` (`within_dir`/`dest_path` — the relative-structure mirroring a job's `target` and a
  manually-moved file both follow), library facts in [[project-photo-manager]] (`/zoo/Pictures/
  Exported` already had about 4,114 images as of the 2026-09-21 scan, predating this app)

The user is manually moving the old export destination's content from `/zoo/Exported` into
`/zoo/Pictures/Exported`, **preserving relative file structure** (2026-09-24) — so a file that was
at `/zoo/Exported/2020/trip/img.jpg` ends up at `/zoo/Pictures/Exported/2020/trip/img.jpg`. Once
that move is done, `/zoo/Pictures/Exported` holds a mix of: (a) exports this app actually produced
(via 089's job queue, before 098/099 existed), (b) whatever pre-dated this app entirely (the
requirements doc's pre-existing `Exported/` library folder). Neither kind has a `Photo`/link
connecting it to its original yet. This ticket is the one-off pass that backfills that connection
for everything already there, run once (not a standing job).

## Tier 1: match against the still-live job log (free, exact, no heuristics)

Any export job less than ~7 days old (`jobs.DONE_RETENTION_DAYS`) is still in the `jobs` table with
its exact `file_id` (source) and `target` (original destination path, under the *old*
`/zoo/Exported/...`). Since the manual move preserves relative structure, a job's `target` maps to
its new location by replacing the `/zoo/Exported` prefix with `/zoo/Pictures/Exported` (mirroring
what `export.py`'s own `within_dir` mirroring already does) — **not** an exact path match, since
the file has physically moved. For every completed export job still in the table: compute the
moved-to path, check the file actually exists there now, and if so link it to `file_id` directly —
exact, no ambiguity. This covers only the most recent week of app-driven exports; everything older
falls through to tier 2.

## Tier 2: filename heuristics + dhash for everything else

For the remainder (older app-driven exports whose job rows are already pruned, and anything that
predates this app):

- **Candidate narrowing by filename**: an exported file's basename usually still resembles its
  source's basename (089's `dest_path` reuses `thumbs.thumb_relpath`'s basename; older, pre-app
  exports may follow their own, unknown convention) — use it to narrow candidates from the library,
  not as a sole match (too many false positives/negatives to trust alone, especially across
  whatever renaming scheme other tools used).
- **Confirmation by dhash**: compute a perceptual hash (dhash) of the exported file and compare
  against dhash of filename-narrowed candidate originals to confirm a real visual match (an export
  is a re-encoded, possibly resized/cropped copy, so expect *near*, not exact, equality — needs a
  distance threshold, not exact hash equality). Check first whether the legacy tooling mentioned in
  docs/reqs/photo-manager-requirements.md (`file_metadata.py`'s per-directory `index.json`, keys
  including `dhash`) already computed and still has usable dhash values for the library, before
  recomputing from scratch.
- **No confident match**: leave unlinked rather than guessing — this is a best-effort pass, not a
  guarantee every pre-existing export gets connected.
