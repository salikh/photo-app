# 077: Filter/sort changes should not be their own browser-history stop

- Type: task
- Status: done
- Priority: not now (user request 2026-09-22)
- Related: [055](055.md) (rating filter buttons), [056](056.md) (a rating change can also move the
  route's `filter`/`photo` state)
- Refs: `photoapp/static/route.js` (`parse`/`href`, the whole view state already lives in
  `location.hash`), `photoapp/static/app.js` (lines ~38, ~60, ~160: filter/sort changes),
  `photoapp/static/loupe.js` (line ~258: closing the loupe; line ~138: `show()` already uses
  `history.replaceState` for photo-to-photo navigation — the precedent this ticket follows)

Pressing the browser's Back button should always return to the previously viewed **folder**, not
undo the last filter (or sort) change. Today it does the latter: every filter button, sort
change, and Shift+digit filter shortcut sets `location.hash = href(...)` (`app.js` lines 38, 60,
and 160), and assigning `location.hash` always pushes a new history entry — so a session of
"folder → Rejected filter → Unrated filter → ★5 filter" leaves four Back-button stops for what the
user experienced as browsing one folder.

## Fix

Use `history.replaceState` for a filter/sort change instead of `location.hash = ...`, so it
updates the URL and the app's state without creating a history entry — exactly what `loupe.js`'s
`show()` already does for stepping between photos inside the loupe (line 138), which is the
precedent to follow: `history.replaceState(null, '', href(route))`. Folder navigation (breadcrumbs
and folder-grid links, both plain `<a href="#...">` elements, per normal anchor-click behavior)
keeps pushing a history entry as it does today — that's the one kind of navigation that *should*
be a Back-button stop.

One wrinkle: `replaceState` does not fire the `hashchange` event, and `app.js` currently relies on
`window.addEventListener('hashchange', render)` to re-render after a hash change. The three
call sites that switch to `replaceState` need to call `render()` (or update `state.route` and
redraw) directly, the same way `show()` already re-renders itself around its own `replaceState`
call rather than depending on `hashchange`.

## Scope question: what about opening/closing a photo?

The user's request named filter switching specifically. Opening a photo from the grid and closing
it back to the grid *also* each push a history entry today (`grid.js`'s photo links are normal
`<a href>` elements; `loupe.js` line 258 closes with `location.hash = ...`) — only navigation
*between* photos inside an open loupe already avoids this (via the existing `replaceState` at line
138). Whether open/close should also become non-history (so Back always means "previous folder",
full stop) or should stay as its own Back-button stop (so Back from a photo returns to the grid,
which some users may expect) is a judgment call worth confirming rather than assuming — flagging
it here rather than changing it silently.

## Result (2026-09-22)

Resolved the open/close-photo scope question as **no**: left `loupe.js`'s close (line 258)
unchanged, still pushing a history entry, matching the user's request (filter/sort specifically)
and confirmed by the *existing* test `test_url_state_survives_reload_and_back_closes_loupe`, which
already asserts that Back after closing the loupe reopens it — changing that behavior would have
broken a test that encodes a real, presumably intended, expectation.

`app.js`: all three sites (the filter-button `go()`, the sort `<select>`'s `onchange`, and the
Shift+digit shortcut handler) now do
`history.replaceState(null, '', href(...)); render();` instead of `location.hash = href(...)`.
`render()` re-derives the route from `parse()` (which reads `location.hash`, already updated by
`replaceState`), so it behaves identically to the `hashchange`-triggered render it replaces —
including the existing `sameFolder` fast path in `render()`, which already treats a filter/sort
change as "not the same view" and reloads the folder, same as before.

Added `test_back_after_filter_and_sort_changes_returns_to_the_previous_folder` to
`tests/e2e/test_ui.py`: real folder navigation (clicking through `folders a` links) into
`2024/trip`, two filter changes and a sort change (all via the now-`replaceState`d paths), then one
`page.go_back()` — lands cleanly back at `2024`, not on an intermediate filter state. Ran the full
`tests/e2e/test_ui.py` file afterward to check for regressions elsewhere (loupe open/close,
photo-to-photo navigation, filter/sort-in-URL tests all still pass).
