## Findings (2026-10-10, from Google's docs)

- Quota: 10,000 Library API requests per project per day (uploads count; media-byte reads are separate).
  One photo = 1 upload request, plus 1 `batchCreate` per 50, so roughly 9,000 photos/day: not a concern.
  429 -> back off exponentially.
- Refresh tokens: a Cloud project with external user type and **Testing** status gets refresh tokens
  that **expire in 7 days**; 'In production' status is not subject to that rule. Tokens also die when
  revoked or unused for 6 months; 100 refresh tokens per account per client id (oldest silently dies).
- Verification: Google's authorization page says apps using the Photos APIs go through OAuth
  verification, and unverified apps show an 'unverified app' screen. The docs fetched do NOT say whether
  an unverified, In-production, single-user app is allowed to keep working, nor how the scopes are
  classified. **Unresolved without trying it on the user's own Cloud project.** Design consequence: the
  CLI treats `invalid_grant` as 'run google_auth again' with a clear message, so either outcome (7-day
  re-consent or none) is workable; setup docs (215) tell the user to publish the consent screen to
  'In production' and click through the warning.
- Scopes needed: `photoslibrary.appendonly` (upload, create album) and
  `photoslibrary.edit.appcreateddata` (add to an existing app-created album);
  `photoslibrary.readonly.appcreateddata` (list our albums).
- Favourites: no write found in the docs. `albums.list` returns only app-created albums (confirmed).
- Loopback redirect is not mentioned on the page; the 'desktop app' client type with
  `http://127.0.0.1:<port>` is Google's standard installed-app flow.
