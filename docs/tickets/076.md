# 076: Nightly rescan becomes one queued job per top-level directory

- Type: task
- Status: done
- Priority: not now — depends on [073] (user request 2026-09-22)
- Related: [073](073.md) (the load-adaptive worker that would actually run these jobs),
  [051](051.md) (incremental per-year scanning, the precedent this builds on), [010](010.md)
  (original nightly-scan ticket)
- Refs: `photoapp/scan.py` (`NightlyScan`, `scan_all`, `top_level_steps`, `_scan_subtree`),
  `photoapp/jobs.py`, `photoapp/__main__.py`

Today `NightlyScan` (`scan.py`) calls `ScanManager.start()` at 3am (`--nightly_scan_hour`), which
runs `scan_all` synchronously, top to bottom across every top-level directory, right then, at
normal priority, whether or not the machine is otherwise busy. Once [073]'s load-adaptive worker
exists, replace the immediate full scan with: at 3am, enqueue one job per top-level directory
(reusing `scan.top_level_steps`, the same unit `scan_all` already iterates one directory at a
time) into the job queue, and let [073]'s worker drain them over time, low-priority, only when
load allows — so a rescan still happens every night but never forces itself onto a busy machine at
3am, and can spill into the following day if it needs to rather than blocking anything.

## Design notes / open decisions

- The `jobs` table's `file_id` column is an integer keyed to `files.id` for every existing job
  kind (`raw_render`, `populate_thumb`); a scan job's unit of work is a directory name, not a file
  id. This needs either a schema change (a nullable `payload`/`target TEXT` column) or some other
  way to represent "which directory" — this is the central design decision here, not a detail.
- Each top-level directory is already its own complete, safely-interruptible unit of work (see
  `_scan_subtree`'s docstring) — this property is exactly what makes turning it into one job per
  directory sound, so no change is needed there.
- Dedup: `JobQueue.enqueue` already skips a duplicate `kind`+`file_id` that's still queued/running
  — the equivalent for a directory-scan job (whatever key ends up representing "which directory")
  needs the same guarantee, so a slow previous night's leftovers don't pile up against a fresh
  night's batch. Alternative: before enqueueing the new night's jobs, clear any of last night's
  scan jobs still queued (a directory that never got scanned isn't lost — its `dir_mtimes` row is
  unchanged, so it'll be picked up whenever it is next worked, including the following night's
  batch).
- `--nightly_scan_hour` still decides when the nightly *enqueue* happens; the actual work is now
  decoupled from that clock.
- The manual **Rescan** button and `fullscan.py` are unaffected — they still call
  `scan_all`/`scan` directly and immediately, at normal priority; only the automatic nightly
  trigger changes.

## Result (2026-09-22)

**Schema**: added a nullable `jobs.target TEXT` column (migration in `db.py`) instead of repurposing
`file_id`. `JobQueue.enqueue(kind, file_id=None, target=None)` now dedupes on `kind` + `file_id` +
`target` together (via sqlite `IS`, so `NULL` compares correctly) — every existing call site is
unaffected since it only ever passed `file_id`, leaving `target` `NULL`.

**One shared low-priority queue**: rather than giving `scan_dir` its own queue, `api.create_app`
now builds one `app.state.background_jobs` (`low_priority=True`, `workers=1`) that both
`thumb_populate.Populator` (via a new optional `queue=` constructor argument — `add_handler`,
also new on `JobQueue`, registers its handler on it instead of building a private queue) and a new
`scan_dir_job` handler register on. [073]'s `LoadAdaptiveWorker` supervises this one queue, so
thumbnail population and directory rescans share the same idle-time budget rather than competing
for CPU independently. `populate_thumbs.py` is untouched (it still builds its own private queue
when no `queue=` is given).

**`scan_dir_job`** calls `scan.scan()` directly (not through `ScanManager`) with `recursive =
(target != ".")`, matching `top_level_steps`'s `[(".", False)] + [(name, True) for name in ...]`
exactly. Routing through `ScanManager.start(rel_dir=".")` was considered and rejected: that method
treats a falsy/`"."` `rel_dir` as "scan everything" (`scan_all`), not "just the root's own files,
non-recursively" — using it here would have made the root's own job silently trigger a full
whole-library scan. Calling `scan.scan()` directly sidesteps that entirely and also avoids a second
layer of threading (`ScanManager` spawns its own thread per scan; the job already runs on the
queue's own worker thread). This does mean a background `scan_dir` job and a manual Rescan-button
click are no longer mutually exclusive via a shared lock the way two manual scans are — sqlite's
own writer serialization (WAL + `busy_timeout`) handles the concurrency safely, and "a busy database
while a scan runs" is already documented as normal; this wasn't given a dedicated test since it's
the same coexistence the rest of the app already relies on.

**`NightlyScan`** now takes `(queue, pictures_dir, hour, wait=None)` and calls the new
`enqueue_nightly_scan(queue, pictures_dir)` instead of `manager.start()`. Dedup means a slow
previous night's still-queued jobs are simply left alone (matches the ticket's "alternative"
leaning) rather than cleared.
