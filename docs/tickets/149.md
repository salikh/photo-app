# 149: `catalog.py --write_metadata_json` writes full EXIF metadata, field set flag-controlled

- Type: task
- Status: not started (implement after epic 144)
- Priority: user request 2026-09-29
- Related: [141](141.md) (`--write_metadata_json` itself: reads/writes only `hash`/`mtime`/
  `bytesize`, merging into but never computing the rest of a record), [111](111.md) (`photoapp/
  metacache.py`'s `REQUIRED_KEYS`, the full field set `photoapp`'s own scanner writes)
- Refs: `tools/archive/catalog.py` (`process_directory`), `photoapp/fileinfo.py`
  (`read_image_metadata` — `mime_type, width, height, exif_date, aperture, shutter_speed, iso,
  focal_length, camera_make, camera_model`), `photoapp/metacache.py` (`REQUIRED_KEYS`)

## Problem

Ticket 141 made `catalog.py --write_metadata_json` read/write only the fields this tool computes
itself (`hash`, `mtime`, `bytesize`) into `index.json`/`<name>.json`, explicitly *preserving* but
never *computing* the rest of a `photoapp`-shaped record (width, aperture, camera make, ...) — a
deliberate scope decision at the time, since re-deriving that was out of scope for what was asked.
The user now wants `catalog.py` to actually compute the full field set too (reusing
`photoapp.fileinfo.read_image_metadata`, already how `photoapp`'s own scanner gets it), so a tree
cataloged only by this tool (never scanned by `photoapp` itself) still ends up with a complete
cache — not asked for now, implement after epic 144 is done.

## What's wanted

- `catalog.py` gains the ability to read/write the full `metacache.REQUIRED_KEYS` set, not just
  `hash`/`mtime`/`bytesize` — reusing `photoapp.fileinfo.read_image_metadata` the same way
  `photoapp/scan.py`'s own scan does when a file isn't already cache-valid.
- Which fields are actually read/written is controlled by command-line flags/config, not an
  all-or-nothing switch — the point being made is that a user cataloging a huge, slow-to-read (e.g.
  network-mounted) backup tree may want to skip the cost of decoding every image for EXIF while
  still getting the (cheap) hash cached, or vice versa.

## Design notes / open decisions (to pin down at implementation time, not now)

- Exact flag shape: candidates include a single `--metadata_json_fields=hash,exif,dimensions`
  comma-list (groups, not 12 individual booleans — matching `populate_thumbs.py`'s existing
  `--sizes` precedent for a similar "which subset" flag) vs. one boolean per
  `metacache.REQUIRED_KEYS` field. Lean toward the grouped-comma-list precedent unless a real need
  for per-field granularity shows up.
- Whether `--write_metadata_json` (ticket 141, currently a plain boolean) becomes redundant with
  the new flag's default (e.g. an empty/default field list still implies at least `hash`, so
  reading/writing the cache at all stays gated by one on/off flag, with the new one only
  controlling *which extra fields* get computed beyond that) — needs to compose cleanly with 141's
  existing merge-not-replace behavior (a field this run doesn't compute must still be left alone if
  already present from a `photoapp` scan or an earlier catalog run).
- `read_image_metadata` decodes the image (a real cost for a RAW file, per ticket 066's dcraw
  timing notes) — confirm the cost is actually worth gating behind a flag on real data before
  assuming it, rather than just asserting it.
