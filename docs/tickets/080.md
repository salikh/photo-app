# 080: Prioritize the currently-open folder in the background thumbnail queue

- Type: task
- Status: open
- Priority: not now (spun out of ticket 069's investigation, 2026-09-23)
- Related: [069](069.md) (the investigation this comes from, with real measurements of the cost
  this would avoid), [073](073.md) (the load-adaptive worker whose walk order this would change),
  [066](066.md) (`thumb_populate.find_missing_files`, the current strictly-path-ordered walk)
- Refs: `photoapp/thumb_populate.py` (`find_missing_files`, `Populator.enqueue_missing`),
  `photoapp/jobs.py` (`JobQueue`), `photoapp/api.py` (`/api/dirs`, `/api/photos`, `/img/...`)

Ticket 069 confirmed and quantified that opening a folder the background populator hasn't reached
yet is genuinely slow (measured: 77–142 ms warm, 100 ms–4.6 s cold per RAW file's embedded
preview, on real library files) — ticket 073's load-adaptive worker fixes this *over time* for the
whole library, but it walks missing files in plain path order
(`find_missing_files`'s `ORDER BY f.path`), with no notion of "what is someone looking at right
now." A folder outside that walk's current position is exactly as slow to open as before 073
existed.

## Idea

When the app serves `/api/dirs` or `/api/photos` for a folder (i.e., someone is browsing it),
bump that folder's still-missing files to the front of the background queue, so the next idle
window works on what's actually being looked at instead of wherever the path-order walk happens
to be. The on-demand render path (`/img/...`) already handles the immediate request either way;
this is purely about what the *background* worker picks up next.

## Design notes (not resolved — this is a stub, not a scoped plan)

- Where "priority" lives: the `jobs` table has no priority column, and job order is currently
  implicit (`_claim`'s `ORDER BY id`, i.e. enqueue order). A real fix likely needs either a
  priority column, or a separate "enqueue this directory's missing files now, ahead of the queue"
  path.
- Cheap approximation worth considering before a real priority mechanism: on a folder browse,
  synchronously call something like `enqueue_missing` scoped to just that directory (fast, a
  handful of files) so its jobs land at the *back* of the queue but exist — better than nothing,
  much simpler than true prioritization, though it does not actually jump the queue.
- How much this matters in practice once 073 has been running for a while (most of the library
  populated, only genuinely new/never-visited folders affected) — worth a fresh look at real usage
  before investing in a full priority mechanism.
