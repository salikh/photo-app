# 146: New `link_exports` job kind: scope `export_backfill`'s dhash heuristic to one directory

- Type: task
- Status: done
- Priority: user request 2026-09-29
- Related: Epic [144](144.md); [145](145.md) (schedules this job after a move into `Exported/`);
  [100](100.md) (`export_backfill.py`, the heuristic this reuses); [099](099.md) (real-time export
  linking — this job is for photos that reach `Exported/` some other way, e.g. a move)
- Refs: `photoapp/export_backfill.py` (`backfill_by_dhash`), `photoapp/api.py` (job handler
  registration, `app.state.background_jobs`)

## What's wanted

Item 5 of epic 144: when photos are moved into a directory under `Exported/` (ticket 145 detects
this), try to link each one to the original it was exported from, using the same dhash heuristic
`export_backfill.py`'s tier 2 already applies library-wide as a one-off script — but scoped to just
the directory that changed, as a standing job kind rather than a manual one-off run.

## Design

- `export_backfill.backfill_by_dhash` gains an optional `dir_prefix` parameter: when given, the
  `unresolved` query is scoped to `path LIKE dir_prefix || '/%' OR path = dir_prefix` instead of
  the whole `Exported/` subtree; the `library_rows` candidate search stays unscoped (an export's
  original can be anywhere in the library, not just near where the export landed). `None` keeps
  today's whole-tree behavior for the standalone script unchanged.
- New job handler `link_exports_job(conn, job)` in `api.py`, registered on
  `app.state.background_jobs` (the low-priority queue `scan_dir`/`populate_thumb` already share —
  this does real image I/O like `populate_thumb`, so it belongs there, not the on-demand queue).
  `job["target"]` is the directory to scope to; the handler calls
  `export_backfill.backfill_by_dhash(conn, settings.pictures_dir, settings.thumbs_dir,
  dir_prefix=job["target"])` and logs the (matched, unmatched) counts, matching `scan_dir_job`'s
  own logging convention.
- Only tier 2 (dhash) is run here, not tier 1 (`backfill_from_job_log`) — tier 1 is specifically
  about `photoapp`'s own now-superseded pre-099 export jobs, not applicable to a photo that arrived
  in `Exported/` via a move.
