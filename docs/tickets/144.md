## What's wanted (as given)

1. On selection active, a "Move to folder" button. The modal's folder input is preselected with
   the current folder; if the typed folder doesn't exist, a second modal confirms creating it, and
   only creates it on confirmation.
2. Moving a photo moves every one of its image files and all of their sidecars (XMP and the ticket
   111 per-file JSON) together.
3. `PHILOSOPHY.md` updated: file operations (trash/deletion/move) happen only by explicit user
   action.
4. After a move, immediately schedule a rescan of both the source and destination directories.
5. If the destination directory's path starts with `Exported`, try to establish the
   exported-from link using the existing heuristic (`export_backfill.py`'s dhash matching) —
   organized as a new job kind, scoped to one directory, scheduled right after the move.

## Why this is a real stance change, not just a feature

`PHILOSOPHY.md` currently states flatly: "**originals are never moved, renamed, or deleted**" —
true today only because every existing write is either a sidecar, or `trash.py`'s move into
`.trash/` (itself reversible, retained for a week). A user-directed "move to another folder within
the library" is a new kind of write this codebase has never made before. It's still consistent with
the *reasoning* behind that line (every move/deletion this app makes is deliberate, reviewable, and
never silent — see ticket 072's `docs/design/trash.md`), so ticket 148 revises the wording rather
than treating this as a violation of it: explicit, user-initiated file operations were always the
intent: `PHILOSOPHY.md`'s own "So, going forward" section says a change that touches an original
file "earns the same scrutiny ticket 072's delete flow got before it shipped" — this epic is that
scrutiny.

## Design overview (detail in each child ticket)

- **Move semantics**: moving "a photo" moves every *live* file belonging to its Photo (RAW+JPEG
  pairs, a linked tuning file, etc. — not just the representative one), matching
  `trash.trash_photo`'s per-Photo granularity, not per-file. Each file's sidecars (every
  `xmp_sidecars` row for that `file_id`, plus its `<name>.json` metadata cache file if present) move
  alongside it, matching `trash._move_file_and_sidecars`.
- **Destination is always inside `pictures_dir`** (unlike `export.py`'s target, which can be
  anywhere) — this is reorganizing the library, not producing a copy outside it. The target
  directory string is normalized with `library._norm_dir`, the same validation `/api/dirs`/
  `/api/photos` already apply.
- **File identity survives the move**: unlike a plain filesystem `mv` a later scan would have to
  *rediscover* via ticket 128's hash-matching (which can be ambiguous for duplicate content, and
  leaves the UI showing a stale/broken thumbnail until that scan runs), the move endpoint updates
  `files.path` directly and reuses `thumbs.move_thumbnails`/`raw_preview_dng.move` (ticket 128's own
  cache-following machinery) synchronously, so the grid reflects the move immediately without
  waiting for the scheduled rescan. Rating, tags, crop, RAW settings, manual links and
  `exported_from_file_id` all key off `file_id`, so none of them need touching.
- **What's deliberately left to the scheduled rescan** (item 4): `xmp_sidecars` row bookkeeping
  (path/file_id linkage) and directory-mtime-driven housekeeping. The move endpoint moves the
  sidecar *files* themselves (item 2) but does not hand-maintain the `xmp_sidecars` table's rows —
  a non-recursive scan of both directories reconciles that the same way it would for any externally
  moved file, and is cheap since only those two directories actually changed.
- **Collisions**: a destination path already occupied gets a numeric suffix before the extension
  (`name-2.ext`, ...), the same disambiguation `export.resolve_dest_path` already does for a
  different reason — a fresh implementation in `move.py`, not a reuse of that function directly,
  since its "reusable export" special case doesn't apply here and would be actively wrong for a
  move (silently overwriting an unrelated file).
- **A file already in the destination directory** is left alone (no-op for that one file), not an
  error — the rest of the batch still proceeds.

## Non-goals (this epic)

- No undo for a move (unlike a rating change or a batch delete's review screen) — reversible in
  principle by moving back, but not wired into `state.undoStack`. Flag if this turns out to matter
  in practice; not asked for here.
- Moving a photo to a location *outside* `pictures_dir` is out of scope — that is what Export
  already does, for a copy, not an original.
