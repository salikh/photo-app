# 081: Automatic purge of Pictures/.trash after a retention window

- Type: task
- Status: done

- Related: [072](072.md) (the Delete flow that populates `.trash/`), [073](073.md) (the

- Refs: `photoapp/trash.py` (`TRASH_DIRNAME`, `trash_dir`), `photoapp/scan.py`
  (`enqueue_nightly_scan`, the `prune_jobs` precedent), `photoapp/api.py` (`background_jobs`)

Ticket 072's decision: "There should be a separate and fully automatic step of deleting files in
Trash directory after some time (e.g. after 1 week). This may be okay to be moved to a separate
ticket, also dependent on the worker queue." This is that ticket.

## Shape (following ticket 075's precedent closely)

- A new job kind (e.g. `purge_trash`), enqueued alongside `scan_dir`/`prune_jobs` in
  `scan.enqueue_nightly_scan`, handled on `api.py`'s shared `background_jobs` queue — reuses
  [073](073.md)'s load-adaptive worker, so this never competes with interactive use either.
- Walks `trash.trash_dir(pictures_dir)`, deleting any file older than a retention window (the
  decision's own example: 1 week) by mtime (the move's mtime, i.e. when it was trashed — moving a
  file preserves neither creation nor a "trashed at" timestamp by default, so this needs to either
  rely on the filesystem mtime surviving the move as-is, or `trash_photo` could write a small
  marker; check which `shutil.move` actually does before assuming).
- Removing a now-empty subdirectory afterward (so `.trash/2019/trip/` does not linger forever as
  clutter once everything in it is gone) is a nice-to-have, not required.
- Needs a real decision on the retention window being configurable (`--trash_retention_days`,
  matching `jobs.DONE_RETENTION_DAYS`'s style) vs. a hardcoded constant like ticket 075 used.

## Result (2026-09-23)

Checked mtime empirically before trusting it (a throwaway script: backdate a file's mtime, move
it, compare before/after) — **mtime is not bumped** by a same-filesystem move (`shutil.move` is a
rename; POSIX renames leave mtime untouched). **ctime is** (metadata-change time), so
`trash.purge_trash` uses `os.stat(path).st_ctime` instead — same intent as the decision (a plain
filesystem timestamp, no new tracking state), just the one that's actually true. Written up in
[docs/design/trash.md](../design/trash.md) since this is exactly the kind of thing worth a real
explanation, not a silent substitution.

`trash.purge_trash(pictures_dir, retention_days=RETENTION_DAYS, now=None)`: single `os.walk(...,
topdown=False)` pass — deletes files past the window, then (since subdirectories are visited
before their parent in that walk order) attempts to `rmdir` each directory once its own files are
handled, so a directory that emptied out removes itself in the same pass without a second walk.
`.trash/` itself is never removed even if empty. `now` is injectable (ctime cannot be backdated
through a normal syscall the way mtime can, so tests simulate an "old" file by moving `now`
forward instead of the file).

Wired in exactly like ticket 075's `prune_jobs`: a `purge_trash` job kind, enqueued alongside
`scan_dir`/`prune_jobs` in `scan.enqueue_nightly_scan` (deduped the same way), handled on
`api.py`'s shared `background_jobs` queue — so it's drained by ticket 073's load-adaptive worker
and never competes with interactive use. Retention is a module constant
(`trash.RETENTION_DAYS = 7`), matching `jobs.py`'s `DONE_RETENTION_DAYS`/`FAILED_RETENTION_DAYS`
precedent rather than a new flag.

Tests: `tests/test_trash.py` (deletes past-retention files, keeps within-retention ones, removes
emptied subdirectories but never `.trash/` itself, a no-trash-yet library is a no-op),
`tests/test_jobs.py` (the job runs through a real `create_app`/`background_jobs`, leaving a
freshly-trashed file alone), `tests/test_more_api.py` (updated the nightly-enqueue job-count
assertions for the new job kind). Full non-e2e suite: 243 passed.
