- Type: task
- Status: done

- Related: [084](084.md) (displays what this ticket extracts/stores — do not build display logic

- Refs: `photoapp/fileinfo.py` (`read_image_metadata`, `read_exif_date` — the existing pattern to

Extract and store camera metadata per file: aperture (f-number), shutter speed (exposure time),
ISO, and exif date. `exif_date` already exists (`files.exif_date`, read by
`fileinfo.read_exif_date`) — this ticket is about the three that don't: aperture, shutter speed,
ISO. Display is [084](084.md), deliberately a separate ticket per the user's own request — this
one is schema + extraction + backfill only.

## Design notes

- **Where they live**: `files`, not `photos` — like `width`/`height`/`mime_type`/`exif_date`,
  these are properties of one physical rendition, not the logical Photo (a DNG and its camera JPG
  can legitimately have different exposure metadata if one was reprocessed).
- **Extraction mechanism**: extend `fileinfo.read_image_metadata` (or add a sibling function) using
  the same `img.getexif()` / `exif.get_ifd(_EXIF_IFD_POINTER)` pattern `read_exif_date` already
  uses — this already works for RAW files today (the EXIF/IFD0 header parses even though Pillow
  cannot fully decode a DNG's image data, which is exactly why `exif_date` already works for RAW).
  Relevant EXIF tags: `FNumber` (33437) for aperture, `ExposureTime` (33434) for shutter speed,
  `ISOSpeedRatings`/`PhotographicSensitivity` (34855) for ISO — confirm the exact tag IDs/fallbacks
  against Pillow's `ExifTags` module rather than trusting this list blindly.
- **Shutter speed representation**: EXIF `ExposureTime` is a rational (Pillow returns an
  `IFDRational`). Storing it as `REAL` seconds is simplest for the database, but display wants
  "1/250" for fast speeds and "2.5s" for slow ones — decide whether that formatting lives in
  `photoapp/static/*.js` (compute from the raw seconds) or gets a second stored column; leaning
  toward computing at display time from stored seconds, one column, no duplication.
- **Backfill**: existing files won't have these until re-read. Two options, worth deciding
  explicitly rather than defaulting to the more expensive one: (a) force a full re-scan the way an
  earlier migration did for RAW sizes (`UPDATE files SET bytesize = -1 WHERE ...` to make the next
  scan re-read everything) — simple, but `docs/design/scanning.md` documents scanning as I/O-latency
  bound and slow across the real library (measured 2.2–21 files/s); or (b) a dedicated, lightweight
  backfill script (`photoapp/backfill_exif.py`? same CLI family as `sync_sidecars.py`) that only
  opens each file and reads its EXIF header — no hashing, no grouping, no thumbnail work — which
  should be far cheaper than a real rescan and could run as a one-off. Leaning toward (b).

## Result (2026-09-23)

Confirmed the tag IDs against Pillow's `ExifTags.TAGS` before trusting them: `FNumber` = 33437
(0x829D), `ExposureTime` = 33434 (0x829A), `ISOSpeedRatings` = 34855 (0x8827) — the ticket's own
guesses were right, but this was checked, not assumed. Went with (b) for shutter speed (one
`REAL` seconds column, formatting into "1/250" left to [084](084.md)'s display code) and (b) for
backfill (a dedicated script, not a forced rescan), both the ticket's own leaning.

`fileinfo.read_camera_metadata(img)`: same `getexif()`/`get_ifd(_EXIF_IFD_POINTER)` pattern as
`read_exif_date`, so it already works for RAW files for the same reason that one does. One real
wrinkle found while writing tests, not anticipated by the design notes: `ExposureTime` (and
`FNumber`) can come back from Pillow as either an `IFDRational` (a real camera file, e.g. the
`/zoo/Pictures` DNG this was checked against: aperture 8.0, shutter 1/45s, ISO 6400) *or* a plain
`(numerator, denominator)` tuple (EXIF written and immediately re-read through Pillow's own
`getexif()`/`save(exif=...)`, as this ticket's own test fixtures do) — `float()` accepts the
former but raises on the latter. Added `_exif_rational_to_float` to handle both rather than
assuming every rational looks the same.

`read_image_metadata` now returns a 7-tuple (`mime_type, width, height, exif_date, aperture,
shutter_speed, iso`); updated its one caller (`scan._scan_files`) and the `_upsert_file` SQL, plus
two now-stale 4-tuple unpacks in `tests/test_previews.py`.

New `photoapp/backfill_exif.py`: `find_unbackfilled` (files where all three are still `NULL`),
`backfill` (opens each just far enough to read EXIF — no hashing, no grouping, no thumbnail work
— and writes what it finds, committing every 200 rows). A file with genuinely no camera EXIF
(scans, screenshots, PNGs) is attempted again on every run rather than being remembered as "tried"
— a deliberate trade-off to avoid a new tracking column for what stays a cheap no-op either way.
`--backfill_limit`, not `--limit`: `photoapp.sync_sidecars` already defines `--limit`, and absl
flags are process-global — a test file importing both modules directly (this ticket's tests need
to, to call the functions, not just invoke a subprocess) would hit a `DuplicateFlagError`
otherwise; found by actually running the suite, not by inspection.

**Not run against the real library yet**, matching ticket 068's precedent: the same live
production server (`~/.local/share/photos/app.sqlite`) is still running, and while this backfill
is purely additive and safe in principle, writing to that database isn't something to do from an
automated session without it being asked for specifically. `python -m photoapp.backfill_exif` is
ready whenever wanted.

Tests: `tests/test_previews.py` (extraction from a constructed EXIF JPEG covering the tuple case,
absent-EXIF graceful `None`s, and a real DNG via `REAL_DNG` covering the `IFDRational` case),
`tests/test_backfill_exif.py` (unbackfilled-file listing, actual backfill, idempotency/does-not-
touch-already-populated, `--backfill_limit`, a CLI subprocess round trip). Full non-e2e suite:
254 passed.
