# 056: Photos whose rating stops matching the filter disappear from view (v1)

- Type: task
- Status: open
- Priority: v1, do now (user request 2026-09-21)
- Depends on: [055](055.md) Rating filter buttons
- Related: [031](031.md) Loupe keyboard, [032](032.md) Batch rating, [046](046.md) Swipe rating, [057](057.md)

When a filter is active and the user changes a photo's rating so that it no longer matches, the photo
**disappears from the view**. This is the culling flow: filter `Unrated`, rate a photo, and it is gone
and the next one is in front of you; filter `★3`, promote or demote a photo, and it leaves the set.

## Today

The rating change only updates the badge in place (`updateCell`); the photo stays in `state.photos` and
in the grid. Paging asks the server for `offset = state.photos.length`, so removing photos locally would
make later pages skip some: the offset must be counted separately (loaded count from the server).

## Behavior

- **Grid:** the cell leaves at once (a short fade), the "N of M photos" text and the counts ([057](057.md))
  update.
- **Loupe:** after the rating is set the photo leaves the list and the loupe shows the **next** photo (the
  previous one if it was the last); the position counter follows (`3/40` becomes `3/39`); if it was the
  only one, the loupe closes back to the grid with "no more photos in this filter". The URL follows.
- **Keyboard and phone:** same for the rating keys, `X`, and swipe up/down ([046](046.md)); a swipe that
  rates a photo out of the filter advances like a swipe to the next photo.
- **Batch rating** (grid selection): the rated photos that no longer match leave; the selection clears.
- **Only when it no longer matches.** `All`: nothing leaves. `Unrated` + rate 0: it stays. `★3` + rate 3
  again: it stays. Fav/tag changes matter only for filters that depend on them (`fav`, conflict).
- **Undo (`U`)** brings the photo back **at its original position** and the loupe shows it again; batch
  undo brings all of them back. Undo when the photo would still not match the filter is not possible
  to see, it returns to the list in its place.
- **Failed write:** the optimistic removal is reverted (the photo returns at its position) and the error
  toast shows, as for other failed writes.
- **Newer data** (a rescan, another device) is not applied live; it shows on the next load.
- A photo that left is not lost: `All` shows it, and the activity log lists the change.

## Design points

- Keep the removed entries (photo + original index) in a small "left the view" stack tied to the undo
  stack, so undo re-inserts in the right place without refetching.
- Optimistic removal and the ordered edit queue: removal happens when the edit is queued (the user sees
  it immediately) and is undone if the request fails.
- Do not reload the whole list after each edit (slow, and it loses the loupe position).
- Interaction with fast keyboard use: several ratings in a row must each advance exactly one photo.
